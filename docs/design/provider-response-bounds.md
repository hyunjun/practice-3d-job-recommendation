# 공개 채용 응답의 읽기 한도 — 72단계

설계안 1. 기준 커밋: `c7830112dc2da58d002da7698cd82147a5272876`.
승인 여부와 각 참여자의 판단은 별도 검증 기록에 이 문서의 SHA-256과 함께 남깁니다.

## 목적과 확인한 근거

여러 채용 API가 공유하는 `fetchBoardJson`은 응답 전체를 읽고 JSON으로 해석한 뒤에야 제공자별 공고 수·필드를 검사합니다. 기존 HTML 수집에는 8MiB 한도가 있지만 JSON 읽기에는 바이트 한도가 없습니다. HTTP 오류와 HTML의 다른 출처 이동을 거부하는 경로도 읽지 않은 본문을 명시적으로 취소하지 않습니다.

이는 현재 소스에서 확인한 차이입니다. 실제 서비스의 메모리 부족·연결 고갈 사고를 재현했다는 뜻은 아닙니다. 응답 크기에 따른 작업량을 제한하고 거부한 응답의 연결 자원을 해제하는 것이 이번 목적입니다.

보존된 57·61·63·64단계의 개별 JSON HTTP 응답 1,448개를 압축본 안에서 읽었습니다. 서로 다른 본문은 1,296개입니다. 모든 바이트 수·SHA-256과 요청 기록을 대조했습니다. 1,304개 요청 기록에는 길이와 해시가, 나머지 144개에는 해시가 있습니다. 모두 성공 HTTP 상태였고 JSON 해석에 성공했습니다. 이것만으로 각 응답이 전체 목록 검증을 통과했다는 뜻은 아닙니다.

가장 큰 개별 응답은 2026-09-26의 SpaceX 게시판 29,492,267바이트였습니다. 64MiB는 확인한 1,448개를 모두 포함하며 최대 기록의 약 2.28배입니다. 여러 게시판을 합친 캐시는 제외했습니다. 추가로 읽은 비 JSON 본문 84개도 JSON 표본에 합치지 않았습니다. 과거 일부 출처의 자료이며 모든 현재 출처나 향후 크기를 보장하지 않습니다.

## 응답 읽기 계약

1. JSON은 **응답 하나당 67,108,864바이트(64MiB)**까지 허용합니다. HTTP 압축 해제 후 실제 본문 스트림에서 읽은 바이트를 문자 해석 전에 셉니다. 공백·사용하지 않는 필드도 포함합니다.
2. 정확히 한도인 정상 JSON은 허용합니다. 한도를 넘기는 청크는 보관·문자 해석·JSON 해석 전에 거부합니다. 일부 바이트나 공고만 잘라 성공으로 반환하지 않습니다.
3. JSON 크기 초과는 실제 스트림 바이트만으로 판단하며, `Content-Length`로 선행 거부하지 않습니다. 헤더가 없거나 부정확하거나 압축 전송을 나타내더라도 실제 읽은 바이트에 같은 규칙을 적용합니다.
4. 기존 `Response.json()`의 UTF-8 대체 문자 처리와 맨 앞 BOM 처리를 유지합니다. 청크 사이에 한국어·이모지·BOM 바이트가 나뉘어도 정상 처리합니다. JSON MIME·charset·최종 출처에 새로운 제한을 추가하지 않습니다.
5. HTML은 기존 **8,388,608바이트(8MiB)**, 엄격한 UTF-8 해석, `Content-Length` 선행 검사와 동일 출처 규칙을 유지합니다. 공통 읽기 도구를 사용하더라도 JSON과 HTML의 차이를 보존합니다.
6. 기존 요청·전체 수집의 취소 신호와 마감 시간을 유지합니다. 청크를 받을 때마다 시간 제한을 새로 시작하지 않습니다.
7. 두 읽기는 같은 내부 스트림 도구를 사용합니다. `MAX_BOARD_JSON_BYTES`, `MAX_BOARD_TEXT_BYTES`는 각각 위의 고정 한도입니다. 테스트는 실제 `fetchBoardJson`·`fetchBoardText`와 이 한도를 검사합니다. 테스트용 환경변수나 제품 API의 한도 변경 기능은 추가하지 않습니다.

## 실패와 본문 해제

- JSON 크기 초과: `BoardFetchError`, `게시판 응답이 수집 크기 제한을 넘었어요.`
- JSON 본문 읽기가 중간에 실패함: `BoardFetchError`, `게시판 응답을 끝까지 읽지 못했어요.`
- JSON 본문을 읽는 동안 전달받은 신호가 취소됨: 원인이 앱에서 만든 `BoardFetchError`라면 메시지 최대 500자와 기존 `retryAfter`를 새 `BoardFetchError`에 보존합니다. SmartRecruiters·공식 사이트의 전체 수집 시간 초과 메시지도 이 규칙을 따릅니다. 공유 원인 객체를 변경하거나 그 원인의 목록·상세 단계를 전파하지 않습니다.
- 그 밖의 취소 원인이 `TimeoutError`임: `BoardFetchError`, `게시판 조회 시간이 초과되었어요.`
- 그 밖의 취소: `BoardFetchError`, `게시판 조회가 취소되었어요.`
- 끝까지 읽은 JSON의 문법 오류·빈 본문: 기존 `게시판 응답 형식을 확인하지 못했어요.`
- HTTP 실패: 기존 `BoardResponseError`와 HTTP 상태·절대 `Retry-After` 시각을 유지합니다. 헤더를 받기 전의 `fetch` 실패 처리도 유지합니다.
- HTML의 기존 크기·본문 없음·다른 출처 이동 메시지와 엄격한 UTF-8 정책을 유지합니다.

원문 본문·JSON 파서의 입력 발췌를 오류 안내에 넣지 않습니다. 필요한 원인은 내부 `cause`에 둘 수 있습니다.

HTTP 실패, 크기 초과, 중도 읽기 실패, HTML 출처 거부로 버릴 본문은 취소합니다. 이미 reader를 얻었다면 그 reader를 취소합니다. reader의 잠금은 성공·실패의 모든 경로에서 해제합니다. 본문을 끝까지 읽은 뒤의 JSON 문법 오류에는 다시 취소할 본문이 없습니다.

취소 자체가 동기 예외·Promise 거절·끝나지 않는 Promise를 반환해도 원래 실패를 바꾸거나 응답 실패 처리를 무기한 지연시키지 않습니다. 이미 결정한 HTTP·크기 초과 오류는 뒤이어 발생한 신호 취소로 바꾸지 않습니다. 취소 거절을 관찰해 처리하며, 다른 요청과 공유하는 취소 제어기를 강제로 중단하지 않습니다. HTTP 상태와 재시도 시각은 본문 정리 전에 결정합니다.

## 기존 수집·사용자 상태 보존

- 크기 초과는 해당 요청의 조회 실패입니다. 새 HTTP 상태나 제공자 전체 재시도 시각을 만들어 넣지 않습니다.
- 기존 제공자 큐의 동시 실행·시작 간격·429 및 `Retry-After` 대기 정책을 유지합니다.
- 전체 목록의 실패와 상세 본문의 실패를 기존 경계에서 구별합니다. 공유 오류 객체를 수정하지 않습니다.
- 목록이 너무 크거나 중간 페이지가 실패하면 이전 정상 스냅샷을 유지하고 게시 확인을 미확인 상태로 처리합니다. 일부 목록을 전체 목록·0건·게시 종료로 해석하지 않습니다.
- 상세 본문이 너무 크면 이전 본문과 원래 확인 시각을 유지합니다. 이미 확인한 목록의 유효성까지 소급해 지우지 않습니다.
- 다른 정상 게시판은 완료할 수 있습니다. 재시도 대기 후 완전한 정상 응답이 오면 기존 원자적 교체 규칙으로 복구합니다.
- 검색·필터·저장 공고의 원문·출처·저장일·메모·지원 상태를 보존합니다.

제공자 URL·페이지 규약, 공고·게시판 수 제한, 갱신 주기, 캐시 형식, 직군 분류, 화면 배치는 바꾸지 않습니다.

## 검증과 단계 합의

Fable은 테스트만 작성·실행하며, 주 담당은 제품 구현·통합·문서, Astra는 독립 설계·소스·근거 검토를 맡습니다. 최종 설계에는 독립 의견과 이견의 해결을 기록하고 세 담당자의 명시적 승인을 연결합니다.

필수 검증 범위는 다음과 같습니다. 최종 테스트 파일·실행 명령·소스 해시를 구현 검토에서 고정합니다.

- 실제 `ReadableStream`을 이용한 바이트 한도의 경계, 잘못된 헤더, 청크 경계와 UTF-8/BOM, 빈·잘못된 JSON, 중도 실패·취소·네이티브 및 앱 수집 시간 초과.
- 네이티브 Node `fetch`와 소유한 루프백 HTTP 서버를 이용한 압축 해제 후 크기 제한·헤더 수신 후 취소. 외부 제공자는 호출하지 않습니다.
- 취소가 실패하거나 끝나지 않을 때의 원래 오류·재시도 시각·후속 요청 진행.
- 실제 제공자·수집기에서 큰 목록·중간 페이지·상세 실패의 원자성, 이전 시각·게시 확인·재시도·복구·재시작 보존.
- 실제 공유 HTTP 읽기를 통과하는 DEV·PROD E2E: 기존 자료 → 갱신 실패 → 검색·필터·저장 기록 보존 → 정상 복구. 데스크톱과 좁은 화면에서 사용자가 보는 제목·개수·안내를 명시적으로 검사합니다.
- JSON의 잘못된 UTF-8은 기존 대체 문자 처리를, HTML은 기존 엄격한 거부를 검사합니다. JSON의 과장된 길이 헤더는 작은 실제 본문을 거부할 이유가 되지 않습니다. 끝나지 않는 작은 본문은 전달받은 마감 시간으로 종료합니다.
- 정상 제공자 스키마에 맞는 큰 응답을 사용합니다. 한도 검사가 빠져도 다른 스키마 오류 때문에 검사가 우연히 통과하지 않아야 합니다.
- 전체 타입·단위 검사(`npm run check`)와 빌드(`npm run build`).
- DEV·PROD에서 신규 `response-bounds.spec.ts`와 기존 `providers`, `lever-pagination`, `bulk-inventory`, `posting-presence`, `source-integrations`, `public-coverage`, `catalog-progress`, `catalog-lifecycle`, `catalog-observations`, `http-cache` E2E를 실행합니다.

검사 범위 확장·재실행은 새 실패·변경·구체적인 미해결 우려가 생겼을 때 합니다. 전체 단위 검사가 통과한 뒤 같은 검사를 이유 없이 반복하지 않습니다. 직전 단계의 전체 E2E 통과를 이번 변경의 전체 E2E 실행으로 보고하지 않습니다. 지도·이력서·순위 알고리즘 등 변경되지 않은 영역의 전체 브라우저 검사는 이번 필수 범위에 포함하지 않습니다.

독립 의견을 조정한 결정:

- JSON의 길이 헤더 선행 거부 제안은 실제 스트림만 세는 규칙으로 조정했습니다. HTML의 기존 헤더 정책은 유지합니다.
- 중도 읽기 실패와 JSON 문법 오류를 구별합니다. 앱의 수집 시간 초과는 새 오류에 문구·재시도 정보를 보존해 다른 요청의 오류 단계를 섞지 않습니다.
- 공통 내부 도구에서 디코딩 차이를 보존합니다. JSON 출처·MIME 제한과 HTML 디코딩 안내의 추가 변경은 포함하지 않습니다.
- 작은 테스트 한도만 검사하지 않고 실제 제품 진입점과 한도를 검사합니다.
- 처음 제안된 단위 검사 중복 실행과 전체 E2E 재실행 대신 전체 단위·타입·빌드와 위의 관련 E2E를 사용합니다. 실패의 기대값을 낮추거나 실패한 사례를 제외하는 조정이 아닙니다.

구현 검토와 최종 검증 합의는 같은 소스·테스트·설계·실행 근거 해시에 연결합니다. 필요한 검사의 실패·누락·미해결 이견을 통과로 바꾸지 않습니다.

## 운영 한계와 완료 후 정리

이는 응답당 입력 바이트 한도입니다. 이미 전달된 청크 하나, 압축 해제기의 내부 버퍼, 해석된 객체·스키마 복사·기존 캐시, 동시에 읽는 다른 응답, 여러 페이지의 합계까지 하나의 메모리 한도로 묶지 않습니다. 4개의 응답이 각각 한도까지 읽히면 입력만 256MiB일 수 있습니다. 동기 JSON 해석을 도중에 중단하거나 일정 CPU 시간을 보장하지 않습니다.

검증·합의 후 변경을 별도 커밋으로 보존합니다. 재사용할 소스·조사 결론·실패 및 최종 검사 결과·합의 기록은 Git에 남깁니다. 새로 조회한 날짜 있는 참고 원본은 무시되는 로컬 보관 자료로 유지하고, 기존 보호 원본·관측 기록은 변경하지 않습니다. 단계에서 만든 임시 소스 사본·빌드·캐시·브라우저·로그·화면·보고서·worktree·소유 프로세스는 보존 확인 후 모두 정리합니다. 사용자 확인용 8787 서버는 꺼둡니다.
