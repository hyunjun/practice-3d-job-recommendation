# 저장 화면 복귀와 로컬 기록의 일치

설계안 02 · 2026-10-01. 기준 소스는 `2d7bd3a2a4e6708e35d66af14099f5021eddffbc`이며, 별도 README 교정 커밋 `6a83147`은 제품·테스트를 바꾸지 않았습니다. 주 담당·Astra·Fable의 독립 조사와 논의 내용을 반영한 검토안입니다. 같은 문서 해시에 연결된 세 참여자의 명시적인 승인을 별도 단계 기록에 남기며, 문서의 존재만으로 구현·검증 승인을 추론하지 않습니다.

## 문제와 사용자 결과

현재 저장 기능은 초기 조회와 BroadcastChannel·이전 localStorage 키의 알림으로 화면을 갱신합니다. 알림이 없거나 전달되지 않으면 다른 탭에서 저장한 내용이 로컬 데이터베이스에 있어도, 돌아온 화면에는 이전 목록·메모·지원 상태가 남을 수 있습니다. 내보내기도 그 화면의 내용을 사용합니다.

같은 ID의 저장 공고를 다른 탭에서 교체하면 열린 상세 창의 공고 본문·회사·지원 링크는 예전 상태인데 메모·지원 상태만 새 기록을 가리킬 수 있습니다. 저장소 읽기에 실패한 뒤 입력 없이 재연결하면, 나중에 삭제된 공고를 편집할 때까지 이전 재시도의 복원 허용 상태가 남는 문제도 있습니다.

이번 단계는 **저장 화면으로 돌아오면 현재 로컬 기록을 확인하고, 작성 중인 입력과 명시적인 복원 선택을 지키며, 화면·백업·상세가 같은 기록을 설명하게 하는 것**을 목표로 합니다. 로컬 기록 확인으로 외부 채용 조회나 원문 수집을 시작하지 않습니다.

## 설계 근거

- HTML Standard의 BroadcastChannel 수신 대상은 메시지 수신 자격이 있는 객체로 한정됩니다. Window의 Document는 fully active여야 하며, 이 알림은 데이터베이스의 영구 변경 기록이 아닙니다.
- MDN의 `visibilitychange`는 브라우저 탭·다른 앱으로의 이동 등을 설명합니다. 이벤트 이름뿐 아니라 실제 `document.visibilityState`를 확인합니다.
- `pageshow`에는 최초 탐색·브라우저 뒤로/앞으로·일부 정지된 모바일 페이지 복귀가 포함됩니다. 배경 탭이나 사전 렌더링에서도 발생하므로 화면이 보인다고 가정하지 않습니다.
- Window의 `focus`는 창으로 초점이 돌아오는 신호입니다. 개별 입력 요소마다 발생하는 초점 이동을 전부 저장소 갱신 신호로 취급하지 않습니다.

2026-10-01에 다음 공식 문서의 실제 응답을 읽고 원문·조회 기록을 보존했습니다.

- https://html.spec.whatwg.org/multipage/web-messaging.html#broadcasting-to-other-browsing-contexts
- https://developer.mozilla.org/en-US/docs/Web/API/Document/visibilitychange_event
- https://developer.mozilla.org/en-US/docs/Web/API/Window/pageshow_event
- https://developer.mozilla.org/en-US/docs/Web/API/Window/focus_event

## 갱신 요청과 완료

기존 저장 controller의 수명 안에서 다음 신호를 받습니다.

| 신호 | 처리 |
| --- | --- |
| Document가 visible로 바뀜 | 현재 로컬 기록 확인 요청 |
| 보이는 Window가 focus를 받음 | 현재 로컬 기록 확인 요청 |
| 보이는 문서의 persisted pageshow | 재사용된 문서의 복귀 확인 요청. 최초 탐색의 persisted=false는 초기 읽기가 담당 |
| 앱 안에서 다른 화면에서 저장 화면으로 이동 | 같은 controller에 확인 요청. 매 render마다 요청하지 않음 |
| BroadcastChannel·이전 저장 키 알림 | 기존의 빠른 확인 경로 유지 |
| 숨겨진 문서의 복귀 이벤트 | 해당 이벤트 때문에 추가 읽기를 시작하지 않음 |

연속된 복귀 이벤트는 예약된 한 작업으로 합치고 실행 시에도 visibility를 확인합니다. hook 정리 시 예약 작업과 이벤트 핸들러를 해제합니다. 주기적 polling이나 이후 변경 신호를 버리는 긴 cooldown은 추가하지 않습니다.

현재 연결 수명 안에서 controller는 동시에 하나의 전체 읽기만 수행합니다. 읽기가 시작된 뒤 추가 요청을 받으면 뒤따르는 읽기가 필요하다는 상태를 보존합니다. 메모리상의 요청 번호와 읽기 직전에 확보한 번호 등으로 해당 읽기가 어느 요청까지 처리하는지 구분합니다. 여러 요청은 합칠 수 있지만, 먼저 시작한 읽기가 끝났다는 이유로 나중의 요청을 버리지 않습니다. 연속된 실제 변경이 계속 들어오는 경우까지 영원히 두 번만 읽는다는 제한은 두지 않습니다.

| 요청 당시 상태 | 필요한 결과 |
| --- | --- |
| 정상·대기 중 | 현재 연결로 읽어 전체 결과 반영 |
| 초기 열기·읽기 중 | 요청을 보존하고 초기 읽기 이후 처리. 대기 입력이 없어도 누락하지 않음 |
| 로컬 저장·대기 입력이 있음 | 입력을 유지하고 성공적으로 저장한 뒤 처리 |
| 다른 전체 읽기 중 | 병렬 읽기를 만들지 않고 필요한 후속 읽기까지 합침 |
| 가져오기·보관 원본 정리 중 | 기존 배타적 작업을 유지하고 종료 후 처리 |
| 저장소 오류 | 오류·초안·마지막 정상 결과 유지. 복귀 이벤트가 재시도하거나 다시 연결하지 않음 |
| 연결 종료·교체 | 이전 연결의 결과·오류가 새 상태를 덮어쓰지 않음 |

명시적인 **현재 기록으로 다시 비교**는 완료 의미가 있는 결과를 사용합니다. 반환값은 해당 요청을 반영한 읽기가 수락된 경우의 `refreshed`와 그 시점의 snapshot, 작업 대기 때문에 완료하지 못한 `deferred`, 읽기 실패 또는 기존 오류 때문에 읽을 수 없는 `failed`와 오류 코드, 이전 연결이 종료된 `stopped`를 구분합니다. hook은 결과를 그대로 전달하며, 기다린 뒤 다른 시점의 `getSnapshot()`으로 바꾸지 않습니다.

이미 읽는 중이면 그 요청을 포함하는 후속 읽기까지 기다립니다. 본인의 요청을 처리한 정상 읽기가 수락되면 이후의 무관한 알림이 계속 들어오더라도 그 결과로 완료합니다. 전체 갱신 흐름이 조용해질 때까지 모든 호출을 붙잡지 않습니다. 자동 알림마다 기다리는 호출을 만들 필요는 없으며, 알림용 요청과 명시적 비교의 완료를 구분합니다.

초기 연결·대기 저장·배타적 작업 때문에 읽을 수 없으면 무기한 기다리지 않고 `deferred`를 반환하되 갱신 요청은 남깁니다. 읽기 도중 로컬 입력이 생기면 반환된 기준 자료 아래에 초안을 유지하고, 아직 완료하지 못한 비교를 `deferred`로 끝낸 뒤 정상 쓰기가 진행되게 합니다. 오래된 ready snapshot을 즉시 반환한 뒤 새로 비교했다고 안내하지 않습니다. 비교 화면은 성공한 snapshot에서만 비교·선택 초기화와 성공 안내를 하며, 대기·실패·종료에서는 현재 선택을 유지하고 읽기 표시를 끝냅니다.

연결을 종료하거나 교체하면 이전 수명의 기다리는 비교를 즉시 `stopped`로 끝냅니다. 네이티브 읽기가 나중에 끝나더라도 그 성공·실패를 관찰해 처리할 뿐 새 수명에 반영하지 않습니다. 초기 open이 끝난 뒤 첫 읽기가 대기 중인 연결도 소유 대상으로 관리해 닫고, open 자체가 늦게 끝나면 그때 도착한 이전 연결을 닫습니다. 이전 작업의 finalizer가 새 작업·오류·요청 상태를 지우지 않습니다.

초기 읽기 직전까지 알려진 요청은 초기 읽기로 처리할 수 있지만, 읽기 시작 이후 들어온 요청은 초기 결과 수락 후 반드시 다시 처리합니다. 요청 없이 시작했다면 일반 초기 읽기만 수행합니다. 정상 쓰기 종료·가져오기 또는 원본 정리 종료·읽기 소유권 해제에서 필요한 후속 작업으로 넘기며, 끝난 Promise를 아직 실행 중인 작업으로 남기지 않습니다.

## 변하지 않은 내용과 실제 변경

같은 ID만으로 이전 객체를 재사용하지 않습니다. 검증된 공고 전체가 같을 때 기존 job 객체를 유지하고, 공고·회사·메모·지원 상태·저장일 전체가 같을 때 saved record를 유지합니다. 순서·길이·모든 항목이 같을 때만 records 배열도 유지합니다.

따라서 다른 탭으로 갔다 돌아왔지만 내용이 그대로라면, 가져오기에서 고른 항목·파일의 변형·필터·페이지가 유지되고 잘못된 목록 변경 안내가 나오지 않습니다. 실제 내용·순서가 바뀌면 기존의 재비교·재선택 절차를 유지합니다.

가져오기 미리보기의 유효성에는 기록 외에 occupied 수와 읽을 수 없는 ID의 집합도 포함합니다. 기록 배열이 같아도 이 정보가 달라지면 예전 선택 가능 여부·수용량을 그대로 적용하지 않습니다. 보관 원본만 달라지면 보관 정보는 갱신하되 관련 없는 가져오기 선택을 무효화할 필요는 없습니다.

완전히 같음을 확인한 활성 기록과 작은 상태 정보에는 이전 snapshot을 재사용해 불필요한 알림을 줄입니다. 단, 원문 보관 자료는 해석하지 않은 보존 대상입니다. 배열 재사용을 위해 보관 원본 전체를 매번 직렬화하거나 정규화하지 않습니다. 원본 객체의 동등성을 확인하지 못하면 새 보관 정보를 보수적으로 알릴 수 있으며, 그래도 활성 records 배열이 같고 수용량·읽을 수 없는 ID가 같다면 가져오기 선택은 유지합니다. 실제로 바뀐 보관 정보·오류·phase는 기록 배열이 같더라도 화면에 반영합니다. 임의의 opaque 원본까지 동일하다고 추정해 알림을 생략하지 않습니다.

## 입력·복원과 저장 원칙

새로 읽은 데이터는 아직 저장하지 못한 로컬 입력 아래의 기준 자료가 됩니다. 읽기 도중 새 메모를 입력해도 초안을 덮어쓰지 않습니다. 다른 탭의 별도 필드 변경은 데이터베이스의 최신 기록에 patch를 적용하는 기존 방식으로 유지합니다.

삭제된 공고를 되살릴 권한은 사용자가 **그 대기 입력을 다시 시도한 한 번의 작업**에 한정합니다. 기존 삭제 우선·대기 입력 합치기를 수행한 뒤, 그 시점에 남은 update 항목에만 허용하며 ID 전체나 연결 전체에 허용하지 않습니다. 허용된 apply 시도를 시작할 때 권한을 소비하고, 성공·실패·늦은 완료·일반 재연결이 이를 다시 주지 않습니다. 새로운 명시적 재시도는 새 시도를 허용할 수 있습니다.

입력 없는 재연결은 미래의 편집을 복원하도록 허용하지 않습니다. 재시도 이후 새로 생긴 무관한 작업에도 이전 권한을 물려주지 않습니다. 아직 시도하지 않은 같은 대기 항목에 합쳐진 최신 타이핑은 그 작업의 초안으로 유지할 수 있지만, 작업이 끝난 뒤의 별도 편집에는 권한이 남지 않습니다.

다른 탭이 공고를 지웠고 로컬 초안이 실패했다면 오류·초안·내보내기·닫기 경고를 유지합니다. 명시적인 재시도 전에는 복귀 이벤트가 공고를 다시 만들지 않습니다. 사용자가 선택한 삭제가 앞선 실패 편집보다 우선하는 기존 처리도 유지합니다.

IndexedDB 버전·저장 형식·savedAt·원래 조회 시각·순서·이전 데이터 이전 표식은 변경하지 않습니다. 저장 완료는 transaction의 완료를 기준으로 합니다. 가져오기의 전체 원자성·예상한 기록과의 비교·한도 검사, 보관 원본 삭제의 정확한 대상 비교는 계속 적용합니다. 반영은 성공했지만 이후 읽기가 실패한 경우를 반영 자체의 실패로 표시하지 않습니다. 기존 오류 코드와 사용자 안내를 유지하며 불필요한 새 오류 분류를 만들지 않습니다.

기존 `SavedStore.read()`는 이전 탭이 다시 쓴 가상 공고를 원본 그대로 보관하고 활성 목록에서 제외하는 transaction을 포함합니다. 이를 우회하거나 단순 readonly 조회로 바꾸지 않습니다. 그 과정의 quota·abort도 오류로 유지합니다.

## 열려 있는 상세와 앱 내 이동

상세를 열 때 **저장 목록에서 열었는지**, **탐색 결과에서 열었는지**를 구분합니다.

- 저장 목록에서 연 상세는 현재 저장 기록의 공고·회사와 메모·지원 상태를 함께 반영합니다. 같은 ID의 교체에도 제목·본문·보상·원문 링크가 이전 버전과 섞이지 않습니다.
- 탐색 결과에서 연 상세는 그 탐색 공고를 보여주는 기존 의미를 유지합니다. 같은 ID의 저장 기록이 바뀌었다는 이유로 탐색 공고를 과거 저장 스냅샷으로 바꾸지 않습니다.
- 저장 목록에서 연 공고가 제거되면 마지막으로 실제 표시한 공고를 저장되지 않은 상세로 유지합니다. 임시 render나 아직 화면에 반영되지 않은 snapshot으로 fallback을 바꾸지 않습니다. 저장된 상태·메모 조작은 사라지며 자동으로 다시 저장하지 않습니다. 사용자가 새로 **기회 저장**을 누르면 바로 그 화면에 표시한 공고·회사를 저장합니다. 렌더링과 저장 callback이 같은 표시 자료를 사용합니다.
- 아직 저장하지 못한 초안이 남은 경우에는 초안 보존·오류·명시적인 재시도 원칙이 우선합니다.
- 기존 상세 닫기·키보드 초점 복귀를 유지합니다.

상세의 출처는 열 때 정하며, 이후 hash가 바뀌거나 저장된 ID가 존재한다는 이유로 다시 추정하지 않습니다. 앱 내 저장 화면 진입은 안정된 callback/controller를 사용합니다. hook이 매 render 새로 만든 함수를 effect 의존성으로 넣어 읽기·render가 반복되는 구조를 만들지 않습니다.

## 독립 검증의 요구 결과

Fable이 기존 검사를 확인해 다음 실제 결과를 검증합니다. 기대값은 fixture의 명시적 값과 사용자가 보는 결과로 정하며 제품 함수로 정답을 만들지 않습니다.

1. 알림 채널 생성 실패와 수신 누락을 각각 만든 뒤, 다른 탭의 메모·지원 상태·추가·삭제가 각 복귀 신호와 앱 내 저장 화면 진입으로 반영됩니다. 원래 날짜·공고·회사와 CSV·JSON 내용도 일치합니다.
2. 숨긴 상태의 이벤트·일반 입력 요소의 초점 이동·persisted=false pageshow로 불필요한 읽기가 생기지 않고, 정해진 이벤트 묶음의 읽기 횟수와 동시 읽기가 제한됩니다. 읽기가 시작된 뒤의 변경·요청도 최종 값에 반영됩니다. 이후의 독립된 복귀 요청을 cooldown으로 버리지 않습니다.
3. 초기 snapshot을 확보한 뒤 완료가 지연된 동안의 요청은 초기 연결 후 처리됩니다. 대기 입력이 없는 경우도 포함합니다.
4. 로컬 쓰기·읽기·가져오기 중의 복귀가 초안을 덮어쓰거나 병렬 저장을 만들지 않습니다. 실패 입력은 유지되며 명시적 재시도 전 데이터베이스를 복원하지 않습니다.
5. 입력 없이 재연결한 뒤 다른 탭에서 지운 공고를 새로 편집하면 missing 처리와 명시적 복원 선택을 거칩니다. 다른 작업의 복원 권한도 잘못 상속하지 않습니다.
6. 진행 중인 읽기와 겹친 명시적 재비교는 실제 새 snapshot을 기다립니다. 그 요청을 처리한 뒤의 무관한 갱신을 기다리지는 않습니다. 대기·실패·종료를 새 비교의 성공으로 안내하지 않으며, 종료한 수명의 비교는 늦은 읽기와 무관하게 끝납니다.
7. 변경 없는 복귀가 가져오기 선택·변형·필터·페이지를 보존하고 실제 공고·회사·메모·상태·순서·수용량·읽을 수 없는 ID 변경은 미리보기를 무효화합니다.
8. 보관 정보만 바뀐 경우와 이전 탭의 가상 항목도 정확하게 반영합니다. 변경되거나 복구된 원본을 예전 삭제 확인으로 지우지 않습니다.
9. 저장 상세를 열어 둔 동안의 교체·삭제·명시적 새 저장에서 표시와 저장한 스냅샷이 일치합니다. 탐색에서 연 상세의 출처와 키보드 초점도 유지합니다.
10. stop/start·StrictMode 정리 이후의 늦은 결과나 예약된 이벤트가 새 연결을 덮어쓰거나 추가 작업을 시작하지 않습니다.
11. 가상 500개 저장 자료에서도 전체 내용·페이지·기존 게시 내용 비교가 유지됩니다. 로컬 갱신 때문에 추가 `/api/` 요청이 생기지 않습니다.
12. Fable이 네이티브 브라우저의 실제 뒤로 이동도 별도로 관찰합니다. BFCache를 기본적으로 끄는 테스트 실행 옵션을 해당 관찰용 브라우저에서만 제외하고, 같은 document 표식·실제 pageshow.persisted·돌아온 메모를 기록합니다. BFCache로 복원되지 않았다면 재로드 경로로 분류하고 그 사실을 남기며, 재로드를 BFCache 성공으로 합산하지 않습니다. 어떤 경로이든 돌아온 화면의 현재 기록은 명시적 기대값으로 검사합니다.

전체 타입·단위 검사·빌드와 최종 합의한 관련 E2E 파일을 개발·배포 모드에서 각각 실행합니다. 같은 최종 소스·테스트·검증 계획의 해시로 세 참여자가 구현을 승인한 뒤 실행하며, 실패가 생기면 원인을 구분해 전원 논의하고 필요한 재검증을 합니다.

두 모드에서 갱신된 저장 상세, 유지된 가져오기 선택, 보호된 실패 초안의 실제 데스크톱·320px 모바일 화면을 확인합니다. 실제 실행 파일·결과·실패·재시도·건너뜀·화면·소유 프로세스를 기록하고, 같은 최종 근거에 세 참여자가 모두 승인해야 검증 완료입니다.

## 범위와 한계

이 변경은 로컬 저장 기록의 일치성을 다룹니다. 외부 공고 수집·현재 게시 여부 확인·클라우드 동기화·같은 필드의 동시 편집 충돌 해결은 새로 구현하지 않습니다. 모든 알림이 없는 동안 복귀 신호도 없다면 지속적인 실시간 갱신을 보장하지 않습니다. 마지막 읽기 이후의 변경에는 이후의 신호가 필요합니다.

직접 발생시킨 lifecycle 이벤트 검사는 실제 브라우저의 BFCache 복원 증거와 구분합니다. 실제 복원을 보고하려면 같은 document가 유지됐고 `pageshow.persisted`가 true였음을 확인해야 합니다. 재로드를 복원으로 세지 않으며 브라우저별 전체 적합성을 주장하지 않습니다.

실제 자료·검증 화면·상세 로그는 무시되는 `.local/`에서 다룹니다. 단계의 결과·실패·합의와 재사용할 도구를 Git에 보존한 뒤 재현 가능한 임시 파일과 소유 프로세스를 정리합니다. 당시 공식 문서 원문과 기존 수집·관측 원본은 별도 보존하며 무결성을 대조합니다.
