# 회사별 조회 상태와 시각의 근거

74단계 설계안. 기준 소스는 `0f9428b8ce3818e2fa0cebc1a981f075ddb18799`입니다. 설계·구현·검증 승인은 각각 같은 문서·소스·실행 근거의 해시를 검토한 뒤 별도 기록합니다.

## 문제와 사용자에게 보이는 결과

저장 화면에서 A 회사의 게시 목록 조회가 실패한 뒤 공개 탐색으로 이동하면, 서버는 A의 재시도 대기를 지키고 다른 회사 B의 공고부터 수집합니다. 현재 카탈로그는 A의 목록 조회 실패를 반영하지 않아 A를 `ok / unavailable`로 표시할 수 있습니다. 정상 본문 조회 이력이 없는 A의 `lastSuccessAt: null`도 데이터 안내창에서 B의 정상 조회 시각으로 바뀝니다. 이전 본문이 아직 30분 이내라면 A를 최신 데이터처럼 표시할 수도 있습니다.

실제 서비스 함수를 메모리 캐시와 가상 회사 두 곳으로 실행해 이를 재현했습니다. 06:00의 A 목록 조회 실패와 06:10 재시도 제한이, 06:00:30에 B만 수집한 카탈로그에서는 빠졌습니다. 서버 재시작 후에도 같은 상태이며 A의 본문 요청은 발생하지 않았습니다.

이번 개선은 회사별 실패·확인 시각·재시도 근거를 정확히 전달하고, 이번 수집의 진행률과 전체 회사의 현재 실패 상태를 구분합니다.

## 회사별 상태

1. 본문 캐시와 게시 목록 캐시의 미해결 실패를 함께 확인합니다. 실제 수집 대기 중인 회사가 아니면 미해결 실패가 있는 회사는 `status: error`입니다. 상태를 합성할 때 캐시에 가상의 본문 시도나 실패를 쓰지 않습니다.
2. 양쪽에 실패가 있으면 `checkedAt`이 더 최근인 실패를 표시합니다. 시각이 같으면 본문 실패를 선택합니다. `message`와 회사별 `checkedAt`은 반드시 선택한 같은 실패 기록에서 가져옵니다. 실패 이후의 목록 조회 성공으로 이전 본문 실패의 시각을 바꾸거나 실패를 지우지 않습니다.
3. 실패가 있는 회사의 사용 가능한 본문은 `dataStatus: stale`이며 공고에도 이전 조회 표시를 적용합니다. 원래 공고·점수 산출의 입력·회사별 개수·본문 정상 조회 시각은 유지합니다. 본문이 없거나 보존 기간을 넘으면 `unavailable`, 개수는 0입니다.
4. 재시도 기한이 지난 것만으로 실패를 해제하지 않습니다. 실제 성공 기록이 해당 실패를 대체해야 합니다.
5. 본문 정상 수집은 기존 목록 캐시 초기화 규칙에 따라 이전 목록 실패도 대체합니다. 목록만 정상 확인하면 목록 실패만 해소합니다. 본문이 원래 유효기간 안에 있고 본문 실패가 없다면 최신 표시로 돌아갈 수 있지만, 본문 시각·내용·비교 가능 기간은 연장하지 않습니다.
6. 정상 빈 본문 목록도 성공입니다. 이후 실패로 이전 공고를 되살리지 않습니다. 일반 출처의 30분, 일 단위 출처의 24시간 신선도와 모든 출처의 최대 24시간 보존 규칙은 유지합니다. 정확히 24시간은 보존하고 1ms 뒤 제외합니다.

## 시각과 재시도

| 필드 | 의미 |
| --- | --- |
| 카탈로그 회사별 `lastSuccessAt` | 해당 회사의 마지막 정상 **본문** 스냅샷 시각. 정상 빈 목록도 포함하며 없는 경우 명시적 `null` |
| 실패 회사의 `checkedAt` | 화면에 표시하는 실패를 실제로 확인한 시각. 다른 성공 시각과 섞지 않음 |
| 정상 회사의 `checkedAt` | 보유한 본문 조회 기록의 시도 시각. 본문 기록이 없는 경우에만 실제 목록 조회 기록 사용 |
| `catalog.fetchedAt` | 현재 사용 가능한 본문 스냅샷의 정상 시각 중 최댓값 |
| `catalog.checkedAt` | 수락한 회사별 본문·목록 시도 시각 중 최댓값. 응답 시각이나 전체 회사의 동시 성공 시각이 아님 |
| 실패 회사의 `retryAt` | 해당 회사의 본문 작업에 실제로 적용되는 공유 재시도 가능 시각 |
| `catalog.refreshAfter` | 회사별 본문 작업 가능 시각 중 최솟값. 한 회사의 긴 대기로 다른 회사까지 막지 않음 |

각 작업은 자기 작업의 기존 갱신 기한과, 다른 작업에 실패가 있다면 그 실패의 유효 재시도 기한을 모두 지킵니다. 실패 기한은 `checkedAt + 60초`와 기록된 `retryAt` 중 늦은 시각입니다. 저장된 오류의 `retryAt`이 `null`이거나 60초보다 짧아도 다른 작업으로 최소 간격을 우회하지 않습니다. 양방향으로 같은 계산을 사용합니다.

다른 작업이 성공 상태라면 그 작업의 정상 재조회 간격을 공유하지 않습니다. 정상 목록 확인 직후 본문을 처음 수집할 수 있어야 하며, 일 단위 출처도 같습니다. 더 긴 Retry-After는 유지하고, 누락된 지수 대기를 추정하거나 시각을 현재 시각 기준으로 다시 만들지 않습니다.

이 기한은 명시적인 재조회가 허용되는 하한입니다. 일반 조회가 정상 본문의 기존 캐시 수명을 무시하고 매번 수집한다는 뜻은 아닙니다. 시계 되돌림에는 기존 작업별 벽시계 규칙을 적용합니다.

## 이전 응답과 화면

`lastSuccessAt: null`은 확인 이력이 없다는 명시적 값입니다. 다른 회사의 시각으로 대체하지 않고 `확인 기록 없음`을 표시하며 날짜 속성도 만들지 않습니다.

필드가 없는 이전 응답은 기존 신선도 계산과 같은 규칙으로 처리합니다. 그 회사 공고의 유효한 조회 시각 중 가장 오래된 것을 먼저 사용하고, 해당 시각도 없을 때만 정상·사용 가능 게시판의 기존 전체 시각 대체 규칙을 허용합니다. 오류·미확인 게시판의 이력을 다른 회사의 성공 시각으로 만들지 않습니다. 이 정책은 신선도 계산과 공유하고, 공고별 시각 검색은 행마다 반복하지 않습니다.

데이터 안내창의 전체 시각은 `최근 게시판 조회 시도`로 표시하고 게시 목록·공고 내용 조회를 포함하며 회사별 정상 시각과 다르다는 뜻을 설명합니다. 회사별 실패 원인·그 실패의 시도 시각·재시도 시각·본문 정상 확인 이력은 같은 행에 표시합니다.

검색·필터·선택 도시와 저장한 원문·메모·지원 상태는 상태 갱신·재시도·재시작 뒤에도 유지합니다. 이번 변경 자체가 사용자 데이터를 서버로 보내거나 외부 요청을 추가하지 않습니다.

## 진행률과 HTTP

`collection.waiting`에 실제 포함된 회사만 `pending`입니다. 다른 회사가 수집 중이어도 재시도 대기로 제외된 회사는 `error`이며 이번 진행의 `total`·`completed`에 포함하지 않습니다. 대기 중인 회사는 기존 데이터의 나이와 역사적 시각을 유지하되 이전 실패를 새 시도의 결과처럼 표시하지 않습니다. 대기 상태의 `retryAt`은 `null`입니다.

진행 막대의 접근성 값은 이번 수집의 대상·종료 수만 읽습니다. 전체 카탈로그의 미해결 실패 수는 별도의 문장에서 현재 상태임을 명시합니다. “0개 종료, 1개 실패”처럼 서로 다른 집합을 하나의 진행률로 읽게 하지 않습니다.

같은 회사 상태 규칙을 일반 카탈로그·진행 시작·진행 변경분·재시작 후 캐시에 적용합니다. 진행 조회와 상태 합성은 새 수집을 시작하지 않습니다. 실패 기한이 지나도 모니터링만으로 다시 수집하지 않습니다.

완료 후 사용할 정상 본문 스냅샷이 하나도 없으면 기존 `CATALOG_UNAVAILABLE` / `CATALOG_EXPIRED`와 HTTP 503·재시도 계약을 유지합니다. 목록 확인만으로 정상 빈 카탈로그를 만들어내지 않습니다. 진행 중에는 기존 부분 결과와 202 계약을 유지합니다.

회사 상태나 그 근거가 바뀌면 JSON 표현과 ETag도 바뀌어야 합니다. 대기 중 같은 표현의 조건부 조회는 304를 사용할 수 있으며, 그 자체로 외부 회사의 정상 본문 시각을 갱신하지 않습니다. `Prefer`, `Cache-Control`, 진행 요청의 최소 간격과 기존 실패 처리는 유지합니다.

## 검증 요구

테스트 담당은 구현에서 기대값을 가져오지 않고 가상 회사·고정 시각·명시적 요청 수와 화면 문구로 검사합니다.

- 목록부터 실패한 A와 정상 B의 혼합 카탈로그, 재시작, A의 `null` 이력과 실패의 원인·시도·재시도 시각.
- 양쪽 실패의 순서·같은 시각·새 목록 성공 뒤 남은 본문 실패. 최신 오류의 짧은 대기와 다른 오류의 긴 대기가 함께 있는 경우.
- `null`·짧은 재시도 기록의 양방향 최소 간격: +59,999ms에는 차단, +60,000ms에는 허용. 반대 방향은 `errorPhase: content`를 사용해 목록 실패 복제로 결함을 가리지 않음. 정상 작업의 독립 간격·더 긴 대기도 검사.
- 아직 젊은 본문과 정상 빈 본문의 보존, 목록만 회복·본문 회복의 구분, 일반·일 단위 출처, 각자의 정확한 신선도·보존 경계.
- 대기 중인 B와 재시도 제외 A를 함께 두고 진행의 대상·종료·변경 회사·접근성 문구와 모니터링 요청 수를 확인.
- `null`과 이전 `undefined` 응답을 별도 화면 자료로 검사. 자기 회사의 오래된 공고 시각이 다른 회사의 새 전체 시각보다 우선하는지 확인.
- 실제 서비스·HTTP의 일반/진행/캐시·ETag·304·실패 503, 실제 브라우저의 저장 화면 → 탐색 → 재조회 흐름과 사용자 상태 보존. 영향받는 흐름은 1440px·320px에서 확인.

필요한 타입 검사·전체 단위 검사·빌드와 관련 E2E의 개발·배포 실행을 최종 소스 기준으로 완료합니다. 실패를 통과로 바꾸거나 기대값을 낮추지 않습니다. 이 범위 밖의 모든 브라우저 검사를 실행했다고 보고하지 않습니다.

## 근거와 범위

2026-09-30에 다음 공식 문서의 원문과 조회 기록을 확인했습니다.

- [RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3): Retry-After와 후속 요청 대기. [§15.6.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6.4): 503과 재시도 안내.
- [RFC 9111 §4.2.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2.4): 오래된 응답 사용의 제약. [§4.3.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3.4): 선택된 저장 응답에 대한 304 갱신.

30분·24시간은 이 서비스의 공고 정책이며 HTTP 표준이 정한 기간이 아닙니다. 카탈로그 JSON 재검증과 외부 공고 원문 확인은 별도입니다.

제공자·캐시 형식·관측 기록·수집 동시성·목록/본문 직렬 실행은 바꾸지 않습니다. 이번 설계에서 명시한 오류 최소 간격 일치 외에 수집 정책을 확장하지 않습니다. 공개 카탈로그를 실제로 받은 시점에 상태를 반영하며 별도 화면 사이에 즉시 상태를 전파하는 새 통신을 추가하지 않습니다. 초기 진행 응답의 지연과 새 회사 확장은 별도 후보로 남깁니다.
