# 저장 공고 제거의 실행 취소

80단계 설계 D2 · 기준 커밋 `163e73ecee9a5fd51ed69f146fa6e01fa9ca6432`.

승인은 주 담당·GPT-6 Astra Max·Claude Code Fable 5.1 Max가 검토한 이 문서의 정확한 해시와 각자의 판단을 연결한 별도 합의 기록으로 관리합니다. 후보 평가·프로세스 종료·문서 작성만으로 승인된 것으로 간주하지 않습니다.

## 문제와 선택 근거

상세 창에서 저장한 공고를 제거하면 창은 계속 열려 있지만 실행 취소 알림은 창 밖에 표시됩니다. `showModal()`이 나머지 페이지를 비활성화하므로 그 버튼을 누를 수 없습니다. 기존 알림의 실행 취소는 7초 뒤 사라집니다. 이후 상세의 `기회 저장`은 메모가 비어 있고 지원 상태와 저장 시각이 초기화된 새 기록을 만듭니다.

원래 기록 전체를 보유한 것은 일시적인 알림의 callback뿐입니다. 다른 안내가 알림을 교체해도 이 복구 경로가 없어집니다. 실행 취소 시 저장소가 작업을 거절하면, 현재 Toast는 오류 안내를 생성한 뒤 `onDismiss`로 그 안내까지 닫을 수 있습니다.

이는 공고 본문 자체보다 사용자가 작성한 메모·지원 기록의 복구에 영향을 주는 문제입니다. 주 담당의 별도 조사에서 확인한 Himalayas 게시 기한 보존 문제는 다음 독립 후보로 남깁니다. 게시 기한을 회사의 지원 마감으로 단정하거나 두 변경을 한 단계에 섞지 않습니다.

## 보존할 기록과 수명

1. 실제로 저장되어 있던 공고의 제거 요청이 기존 저장 컨트롤러에 수락됐을 때, **제거 직전 앱의 유효한 저장 기록 전체**를 보존합니다. 공고·회사·ID·메모·지원 상태·최초 저장 시각과 아직 저장 중인 유효한 입력을 포함합니다. 수집 갱신이나 객체 변경으로 이 원본을 바꾸지 않습니다.
2. 거절된 제거, 이미 없는 기록의 제거, 다른 탭에서 발생한 제거는 새 복구 기록을 만들지 않습니다. 기존 복구 기록도 교체하지 않습니다.
3. 현재 문서에서 보관하는 것은 **복구를 진행 중인 기록 1개(P)**와 **가장 최근에 제거한 기록 1개(L)**, 최대 두 개입니다. P와 L은 서로 다른 제거 세대이며 같은 공고 ID의 다른 내용일 수도 있습니다.
4. 평소 수락된 제거는 L을 교체합니다. 사용자가 L의 실행 취소를 요청하고 P가 비어 있으면 L을 P로 옮긴 뒤 기존 저장 컨트롤러에 요청합니다. 컨트롤러가 로딩·한도 등의 이유로 거절해도 P는 유지합니다.
5. P가 남아 있으면 다른 L의 복구를 시작하지 않습니다. 먼저 어느 기록의 복구를 완료하거나 닫아야 하는지 표시하고 L을 유지합니다. 두 번째 복구나 새 저장을 조용히 실행하지 않습니다. 다음 제거는 여전히 L을 교체할 수 있으며 이 범위를 안내합니다.
6. P는 해당 원본이 트랜잭션 완료 결과에서 확인됐거나, 사용자가 그 복구 기록을 명시적으로 닫았거나, 아래의 동일 원본 재제거 규칙으로 새 세대에 보존된 경우에만 해제합니다. 요청 수락·낙관적 화면 등장·비동기 실패·단순한 작업 제외만으로 해제하지 않습니다.
7. 실행 취소에는 자동 만료 시간을 두지 않습니다. 7초 이상 경과, 창 숨김, 다른 모달 열기, 탐색·저장·비교 간 이동, 일반 안내 알림으로 P나 L이 사라지지 않습니다.
8. 새로고침·새 탭·앱 종료 뒤의 휴지통이나 백업은 추가하지 않습니다. 화면에는 “복구 대기 1개와 최근 제거 1개를 이 탭을 열어 둔 동안 보관해요. 최근 제거는 다음 제거 시 바뀌어요.”라는 범위를 안내합니다. 실행 취소 원본만 남았다고 종료 경고를 새로 만들지는 않습니다. 기존 미저장 작업의 종료 경고는 유지합니다.
9. 같은 공고의 저장 버튼은 복구 기록이 남아 있으면 원래 기록을 복원하는 동작임을 표시합니다. 그 ID에 P와 L이 모두 있으면 이미 요청한 P를 우선합니다. P가 다른 ID라 L을 시작할 수 없으면 이유를 표시하고 새 빈 기록을 만들지 않습니다. 해당 복구 기록을 명시적으로 닫은 뒤에만 일반적인 새 저장 동작을 사용할 수 있습니다.

## 복구 결과와 실패

일반 저장 API는 유지하고, 복구용으로 결과를 추적하는 좁은 추가 경로를 둡니다. 예시는 `addTracked(record)`이며, 기존 `change`의 가드·큐·`store.apply`를 공유합니다. 별도의 쓰기 경로·강제 덮어쓰기·용량 제한 우회·영속 이력을 만들지 않습니다.

수락 결과의 Promise는 해당 대기 추가 작업에 속합니다. UI callback을 저장 트랜잭션의 오류 처리 안에서 실행하지 않습니다. 일반 저장·메모 갱신·제거 호출은 기존 반환 규칙을 유지합니다.

| 결과 | 의미와 복구 기록 |
| --- | --- |
| 요청 거절 | 기존 `loading`, `busy`, `limit`, `unreadable` 등의 이유를 반환합니다. P와 원본을 유지하고 현재 조작 가능한 영역에 이유와 재시도 경로를 표시합니다. |
| `noop` | 현재 앱의 같은 ID 기록 때문에 새 추가를 큐에 넣지 않았습니다. 이것만으로 디스크 저장이나 원본 복원을 증명하지 않습니다. 현재 기록을 보존하고 P를 유지합니다. |
| `settled` | 현재 연결 세대의 `store.apply`가 트랜잭션 완료 후 반환한 기록 전체가 원본과 동등합니다. 확인한 기록을 반환하고 P를 해제할 수 있습니다. 이 요청이 새 행을 삽입했다고 단정하지 않습니다. |
| `conflict` | 완료 결과의 같은 ID 기록이 원본과 다릅니다. 현재 기록을 덮어쓰거나 합치지 않고, 원래 메모가 복원되지 않았음을 알리며 P를 유지합니다. |
| `superseded` | 나중에 수락된 같은 ID의 제거 또는 재시도 정리로 이전 추가 의도가 대체됐습니다. 이미 시작된 쓰기가 취소됐다는 뜻은 아닙니다. 아래 세대 규칙에 따라 원본을 유지하며, 이 결과만으로 P를 지우지 않습니다. |

1. 저장 가드와 동등성 판단은 한곳에서 재사용합니다. 비교할 때는 양쪽의 유효한 기록을 같은 스키마 형태로 정규화해 객체 키 순서 차이를 충돌로 오인하지 않습니다. 보관한 원본 자체는 변경하지 않습니다. 비교 대상은 메모·지원 상태·저장 시각·회사·공고 전체입니다.
2. 수락된 작업은 먼저 낙관적으로 표시될 수 있습니다. `accepted: true`를 영구 저장 완료라고 알리지 않습니다. 저장소 반환값이 추가 작업에 맞지 않는 등 확인할 수 없는 결과는 성공으로 처리하지 않습니다.
3. 비동기 쓰기 실패·중단은 끝난 복구 결과가 아닙니다. P와 기존 대기 작업을 유지하고 기존 저장 실패·재시도·내보내기·종료 경고를 사용합니다. 재시도는 보존된 작업을 다시 처리하며 같은 원본의 추가를 하나 더 넣지 않습니다.
4. 삭제 쓰기가 아직 끝나지 않은 상태의 실행 취소, 삭제 실패 후 실행 취소도 기존 제거·추가 순서를 따릅니다. 이전 실패 작업이 다른 탭의 새 메모를 덮어쓰도록 권한을 확대하지 않습니다.
5. 현재 큐와 확정 기록을 반영한 뒤 결과를 한 번만 전달합니다. `stop` 후 `start`나 재시도에서 대기 작업과 결과 추적은 유지하고, 이전 연결 세대의 늦은 응답은 무시합니다. 중복 누름은 같은 추가를 반복 요청하지 않습니다.
6. 복구 기록의 닫기는 이미 수락된 작업의 취소가 아닙니다. P/L을 닫거나 화면을 바꿔도 진행 중인 쓰기와 기존 오류는 유지합니다. 복구 패널이 사라진 뒤에도 열린 모달에서 저장 실패와 재시도에 접근할 수 있어야 합니다.

## 같은 공고의 재제거와 충돌

- P의 원본과 **내용 전체가 같은** 현재 기록을 사용자가 다시 제거하면, 그 현재 기록을 새로운 L로 보존하고 이전 P 세대와 복구 요청을 대체할 수 있습니다. 늦은 이전 결과가 새 L을 지우거나 제거 의도를 되돌리지 않아야 합니다.
- 같은 ID라도 내용이 다르면 서로 다른 원본입니다. 예를 들어 P의 메모가 `ORIGINAL`이고 다른 탭에서 다시 저장한 현재 메모가 `NEWER`일 때, `NEWER`를 제거하면 그 기록은 L이 되고 `ORIGINAL`은 P에 남습니다. 이후 P를 명시적으로 다시 시도해 복원할 수 있어야 합니다.
- 같은 ID의 제거가 이전 추가 요청을 대체하면 그 요청 결과를 무효화합니다. P를 유지해야 하는 충돌 흐름에서는 다시 시도 가능한 상태로 돌리며 자동으로 다시 추가하지 않습니다.
- 다른 ID의 제거는 P를 소비하지 않고 L만 교체합니다. 한도 때문에 P 복구가 거절된 뒤 다른 기록을 제거하고 P를 재시도할 수 있어야 합니다. 뒤의 제거에도 L의 실행 취소를 제공합니다.
- 닫기·복구·비동기 응답은 제거 세대와 복구 요청에 연결합니다. 오래된 버튼 동작이나 결과가 다른 P/L을 지우지 않도록 합니다.

## 표시와 접근성

1. 복구 UI는 이름 있는 영역 하나이며, P는 `복구 대기`, L은 `최근 제거`로 구분합니다. 각 기록의 회사·공고 제목·원래 지원 상태·저장일을 표시해 동일 ID의 서로 다른 기록도 구분할 수 있게 합니다. 동작은 `실행 취소` 또는 `복구 다시 시도`, 닫기는 해당 기록의 `복구 안내 닫기`입니다. 저장 대기 중에는 같은 추가를 중복 요청하지 못하게 하며, 실패 시 기존 저장 재시도를 제공합니다.
2. 열린 네이티브 모달이 있으면 패널은 **가장 위 모달의 헤더 다음, 정상 문서 흐름 안에 한 번만** 표시합니다. 모달 밖의 높은 `z-index`로 대신하지 않습니다. 공고 상세·다른 공고·프로필·필터·데이터·저장 기록 관리 창을 모두 포함합니다. 모달 닫기는 처음 조작부로 남습니다.
3. 모달이 없으면 현재 저장 목록이나 회사 공고 목록 가까이에 표시합니다. 저장 목록에서는 위쪽 페이지 이동 다음, 카드 목록 직전에 두고 빈 결과에서도 사용할 수 있게 합니다. 다른 화면에는 본문 내 대체 위치를 둡니다. 긴 목록 아래에서 제거한 뒤에도 현재 초점과 가까운 조작 또는 명확한 키보드 경로로 복구에 접근할 수 있어야 합니다.
4. 패널 위치만 바뀌며 App의 P/L은 유지합니다. 모달 인스턴스나 작성 중인 입력을 다시 만들지 않습니다. 등록 해제된 이전 모달이 새 모달의 패널을 가져가거나 두 곳에 동시에 표시하지 않아야 합니다.
5. 제거 안내는 이 패널에서 알리며 같은 제거를 일시적인 Toast로 중복 알리지 않습니다. 일반 Toast의 기존 수명은 유지하고 알림 큐는 추가하지 않습니다. 일반 메시지가 P/L을 소거하지 않습니다. 저장 오류를 기존 안내와 패널이 중복 낭독하지 않도록 조정합니다.
6. 안내 등장·백그라운드 저장 갱신·다른 탭의 변화만으로 초점을 빼앗지 않습니다. 현재 입력으로 이동한 사용자의 초점을 늦은 저장 결과가 가져오지 않아야 합니다.
7. 사용자가 패널의 복구·닫기를 눌러 초점이 있던 버튼이 없어지거나 비활성화되면, 모달 안에서는 중립적인 `닫기` 조작부로 이동합니다. 페이지에서는 현재 페이지에 있는 복원된 카드 제목, 살아 있는 원래 저장 버튼, 현재 페이지의 첫 제목, 검색·빈 상태·본문 순으로 적절한 대상을 사용합니다. 비활성 배경·제거된 노드·`body`에 남기지 않습니다.
8. 저장 카드의 제거 버튼에 초점이 있다가 카드가 사라지면 현재 페이지의 첫 살아 있는 제목, 검색·빈 상태·본문으로 복귀합니다. 페이지 수가 줄지 않는 제거도 포함합니다. 첫 카드 제목에서 복구 패널의 마지막 사용 가능한 조작부까지 최대 두 번의 Shift+Tab으로 갈 수 있어야 합니다. 복구가 필터나 페이지 밖의 기록을 추가했다고 조건을 바꾸어 그 기록으로 이동하지 않습니다.
9. 회사 공고의 저장 버튼과 상세의 다시 저장은 복구 기록이 있을 때 `제거 취소`임을 표시하고 같은 경로를 사용합니다. 상세에서 저장된 기록을 제거하는 버튼은 `저장 목록에서 제거`로 명확히 표시합니다. 저장 중 여부는 별도 상태로 알립니다.
10. 1440px·320px에서 실제 키보드와 포인터로 확인합니다. 긴 회사/공고명·메시지·동작이 줄바꿈되고 정상 스크롤로 접근 가능하며, 하단 메뉴·고정 조작부·안전 영역에 가려지지 않아야 합니다. 일반 Toast와 함께 표시돼도 초점이 가려지지 않아야 합니다.
11. Escape·배경 클릭은 기존 모달 닫기 가드를 따르고 P/L을 유지합니다. 검색·필터·페이지·작성 중인 모달 입력을 복구 패널 때문에 초기화하지 않습니다. 복원 위치는 기존처럼 목록 맨 앞이며 최초 저장 시각은 보존합니다.

## 구현 범위

주 담당은 App의 복구 상태·명령 처리, 필요한 컨트롤러 결과 추적, 공통 모달/페이지 표시, 관련 저장 버튼·초점·스타일을 맡습니다. 기존 컨트롤러·저장소의 가드와 충돌 규칙을 재사용합니다. 데이터 수급·공고 기한·검색 계산·일반 알림 큐·영속 휴지통은 범위에 넣지 않습니다.

Fable은 테스트 파일과 로컬 검증 자료만 수정하고 정식 검사를 실행합니다. Astra는 독립 설계·소스·근거 검토를 맡습니다. 구현 담당은 자체 검사 결과로 독립 E2E를 대신하지 않습니다.

## 검증 계약

먼저 Fable이 수정 전 코드에서 최소한의 회귀 검사를 작성·실행합니다. 열린 상세 안에서 실행 취소할 수 없는 경우와 시간이 지난 뒤 원래 메모·지원 상태를 복구하지 못하는 경우를 명시적인 기대값으로 재현합니다. 의도한 실패와 다른 환경·전역 오류를 분리하며, 완결된 일반 보고서도 보존합니다. 실패한 baseline을 최종 통과로 기록하지 않습니다.

최종 검사는 다음 결과를 확인해야 합니다. 세부 파일·명령·가상 자료와 기대값은 실행 전에 확정합니다.

- 상세를 열고 제거한 뒤 창을 닫지 않고 복구: 원래 공고·회사·메모·지원 상태·저장 시각 복원. 키보드와 포인터로 실제 동작.
- 7초를 충분히 지난 시점, 숨김/복귀, 다른 모달과 페이지 왕복에서도 같은 후보 유지. 그 사이 일반 알림이 발생해도 유지.
- 같은 공고의 다시 저장은 후보가 있으면 복원임이 명확하고, 명시적 안내 닫기 후에는 새 저장으로 구분.
- 실패한 제거는 P/L을 바꾸지 않음. 일반적인 후속 제거는 L만 교체하고, 복구를 요청한 P는 보존. P가 있을 때 L의 두 번째 복구 시작은 거절하고 이유와 L을 유지.
- 한도·읽기 불가·배타적 작업 경계: 거절 이유와 원본 보존. 한도 거절 A → B 제거 → A 복구 뒤에도 B의 L 보존. 저장소 쓰기 실패 뒤 원래 메모 유지와 정상 재시도.
- 이미 존재하거나 쓰기 시점에 새로 생긴 같은 ID를 덮어쓰지 않음. 서로 다른 메모 `ORIGINAL`/`NEWER`의 충돌 → 현재 기록 제거 → 원본 복구. 내용이 같은 원본의 재제거는 새 세대에 보존.
- 삭제가 아직 저장 중인 복구, 삭제 실패 뒤 복구, 복구 안내를 닫은 뒤의 실패·재시도, 세대 교체 뒤 늦은 응답과 중복 누름.
- 결과 추적의 거절/noop/정상 완료/충돌/대체/실패 재시도, 중지·재시작과 오래된 응답, 객체 키 순서가 다른 동등한 기록, 예상할 수 없는 저장소 결과를 단위 검사로 보강.
- 복구·닫기로 조작부가 사라진 뒤 올바른 초점, 실제 가독성과 가림 없음. 검색·필터·페이지·열린 모달의 작성 내용 보존.
- 기존 저장·가져오기·모달 포커스·알림 주변 스크롤 동작의 회귀와 새 네트워크 요청이 생기지 않음.

가상 자료를 사용하며 저장 컨트롤러의 내부 함수로 기대 기록을 계산하지 않습니다. 예시 메모·지원 상태·저장 시각·회사/공고 ID를 명시하고 실제 저장소와 화면을 확인합니다. 검증 후 제품 소스가 바뀌면 영향을 받는 검사를 다시 실행합니다.

필요한 타입·단위 검사·빌드·개발/배포 E2E를 완료하고, 세 담당자의 같은 최종 소스·근거에 대한 승인을 확인한 뒤 커밋합니다. 서버는 검증 소유 프로세스만 실행·종료합니다. 가치 있는 근거를 Git에 보존하고 이 단계의 임시 자료를 정리한 뒤 실제 결과를 별도로 기록합니다. 기존 보호 파일 42개는 유지합니다.

## 근거와 한계

- [MDN dialog](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog): 모달은 나머지 페이지를 비활성화합니다.
- [WAI-ARIA Alert Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/alert/): 안내 자체가 초점을 가져가지 않도록 하고, 너무 빨리 사라지는 안내를 피하도록 설명합니다.
- [WCAG 2.2 Timing Adjustable](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html): 콘텐츠의 시간 제한에는 사용자 제어 또는 해당하는 예외가 필요합니다.

이 설계는 특정 기준의 인증이나 모든 브라우저·보조 기술에서의 검증 완료를 뜻하지 않습니다. 실제 실행 환경·관측한 화면·실패·남은 한계는 검증 기록에 적습니다.
