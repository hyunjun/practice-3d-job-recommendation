# 시간 경과에 따른 Worker 공고 본문 중복 전달 줄이기

79단계 설계안 03 · 2026-10-01. 기준 소스는 `e6921f00012e5e28370101e45d1aed24ee68fd1d`입니다. 이 문서 해시에 대한 주 담당·Astra·Fable의 승인을 별도로 기록합니다. 문서를 작성했다는 이유로 설계·구현·검증 합의를 완료한 것으로 취급하지 않습니다.

## 문제와 근거

현재 Worker는 시간 경계가 바뀔 때 수신한 원본에서 `ageCatalog`를 다시 계산합니다. 오래된 공고에는 `{ ...job, stale: true }`를 만들어 주므로, 다른 회사만 새로 오래되거나 만료되어도 이미 오래된 공고 객체가 다시 만들어집니다. 전송 여부를 이전 객체와의 참조 비교로 결정하는 `sentJobs`는 이 공고의 전체 본문을 다시 보냅니다. 같은 현상은 오래됨 경계를 지난 수집 중간 응답에서도 발생할 수 있습니다.

이 경로는 세 참여자가 각각 소스를 읽어 확인했습니다. 원본 시각에서 다시 계산하는 방식은 시계가 뒤로 움직였을 때도 결과를 복원하기 위해 유지해야 합니다. 이전에 파생한 공고를 계속 덮어쓰는 방식으로 문제를 해결하지 않습니다.

보존된 과거 캐시 v5에는 공고 6,755개가 있었고, 공고별 compact JSON 합계는 59,727,431바이트, 최상위 description의 UTF-8 합계는 41,368,269바이트였습니다. 이는 한 과거 자료의 형태를 확인한 값입니다. 현재 공고 수·유효성·마이그레이션 결과·실제 structured clone 크기·압축 HTTP 전송량·메모리 사용량·실행 시간 측정은 아닙니다.

## 결과 계약

1. 수신 측이 이미 가진 공고에서 **본문 필드는 그대로이고 오래됨 상태만 바뀌면**, 전체 Job을 보내지 않습니다. 최초 fresh→stale, 이후 다른 회사의 경계, 역방향 시각 변경에도 적용합니다.
2. 본문 필드와 오래됨 상태가 모두 같으면 전체 Job과 오래됨 변경분을 모두 생략합니다.
3. 새 ID, 실제 본문 변경, 수신 캐시에서 제거된 뒤 복원되는 ID에는 전체 Job을 보냅니다. 별도로 파싱된 중첩 객체·배열의 참조가 다르면 같은 내용처럼 보여도 전체 Job을 보수적으로 보낼 수 있습니다.
4. 목록·검색·미리보기·조건 완화·도시·원격·기타 근무지·지도·비교 집계·점수·게시판 이력·열린 상세·저장 기록은 기존 시간 규칙에 맞게 유지합니다. 본문 전송을 줄이는 것이 결과를 생략하거나 원래 시각을 바꿀 근거가 되지 않습니다.

## 공고 변경 분류

비교 영역은 기존 JSON 수신·마이그레이션 경로의 **불변인 plain Job 데이터**입니다.

- 이전 전달 기록이 없으면 전체 공고입니다. 이전 객체와 현재 객체가 같으면 기존 불변성 전제 아래 변경 없음입니다.
- 객체가 다르면 `stale`을 제외한 **모든 enumerable own string key의 집합과 각 값**을 비교합니다. 키의 존재는 `Object.hasOwn`과 같은 own-key 검사로, 값은 `Object.is`로 확인합니다.
- 추가·삭제·이름 변경된 키, 바뀐 원시 값, 다른 중첩 참조는 전체 공고입니다. 알려진 Job 필드만 나열하거나 ID·fetchedAt·source만으로 본문 버전을 추정하지 않습니다. 확장 필드와 명시적인 `undefined` 키 존재도 직접 비교 경계에서 구분합니다.
- non-stale 필드가 같으면 `stale`의 own-property 존재와 값을 비교합니다. 생략·own false·own true는 각각 다른 상태입니다. 모두 같으면 변경분도 생략합니다.
- 객체가 바뀌었고 `stale`이 compact 표현 밖의 상태라면 전체 공고로 처리합니다. 예를 들어 own `stale: undefined`를 생략과 같다고 간주하거나 null로 바꾸지 않습니다. 공용 JSON 검증이 허용하지 않는 값을 새로 허용하는 것은 아닙니다.
- 본문 전체의 JSON 직렬화·해시·깊은 비교를 시간 경계마다 추가하지 않습니다. 키 순서·프로토타입·descriptor·symbol·accessor의 일반 객체 동등성을 보장하는 비교도 아닙니다.

동일 참조의 내부 데이터를 나중에 바꾸는 것은 기존 불변 입력 계약을 위반합니다. 이번 작업이 깊은 불변성을 강제하는 것은 아닙니다. 원시 문자열 비교의 상수 시간도 보장하지 않습니다.

## 사설 projection 프로토콜

`project` 요청과 projected reply의 patch에 `protocol` 필드를 필수로 두고, 같은 `CATALOG_PROJECTION_PROTOCOL` 상수를 사용합니다. 첫 버전은 `1`입니다. 새 Worker는 없거나 타입이 잘못됐거나 지원하지 않는 요청 버전을 **snapshot aging·검색·projection 계산과 전달 기록·pin·pruning 변경 전에** `CATALOG_WORKER_FAILED`로 거부합니다. 새 client는 없거나 지원하지 않는 응답 버전을 연결 실패로 처리합니다. 서로 다른 형식의 무음 혼용을 막는 장치이며 형식 협상·대체 프로토콜·공용 API나 저장 형식 이전은 추가하지 않습니다.

상수는 `src/lib/catalog-worker-types.ts`에 둡니다. decode·preview·acknowledge 형식은 바꾸지 않습니다. Vite의 해시가 붙은 자산에서 실제로 서로 다른 빌드가 섞이는 현상을 관찰했다는 주장은 하지 않습니다. 새 버전의 검사가 담당하는 요청·응답에서 지원하지 않는 형식을 명시적으로 실패시키는 범위입니다.

기존 `jobs`는 전체 공고 삽입·교체, `removed`는 삭제입니다. 새 필수 배열 `staleUpdates`는 다음 세 상태만 표현합니다. 변경이 없어도 배열 자체는 존재하며, 실제 변경 항목은 현재 카탈로그 `jobIds`의 순서로 보냅니다.

| 항목 | 수신 측 결과 |
| --- | --- |
| `{ id, stale: true }` | own `stale: true` |
| `{ id, stale: false }` | own `stale: false` |
| `{ id, stale: null }` | `stale` own property 삭제 |

생략과 false 사이의 변경도 정확하게 전달합니다. null을 Job에 저장하거나 undefined를 대입해 삭제를 대신하지 않습니다. 기존 Job의 나머지 필드를 얕게 복사해 보존하고, 실제 상태가 바뀔 때만 새 표시 객체를 만듭니다. 이전에 발행한 projection·열린 상세·저장 스냅샷을 직접 수정하지 않습니다.

수신 측은 변경을 적용하기 전에 다음을 확인합니다.

1. 버전과 `staleUpdates` 배열이 존재하고 지원하는 형태입니다. 각 항목은 문자열 ID와 명시적인 boolean 또는 null stale 값을 가집니다. 누락·undefined·잘못된 타입은 삭제 명령이 아닙니다.
2. stale ID는 중복되지 않습니다. 전체 공고·삭제·오래됨 변경의 ID 집합이 서로 겹치지 않습니다.
3. 오래됨 변경 대상은 적용 전 수신 캐시에 존재하며, 새 `jobIds`에도 존재합니다. 없는 본문을 만들어 내거나 이전 상태를 유지한 채 성공으로 처리하지 않습니다.
4. ID 집합으로 존재 여부를 확인하여 변경분마다 전체 `jobIds`를 선형 검색하지 않습니다.

이 새 변경분의 정합성 검사와 projection 생성이 실패하면 **그 client 연결을 종료**하고, 대기 작업을 실패시키고, 기존 `CATALOG_WORKER_FAILED` 경로로 한 번 알립니다. 잘못된 projected-result 종류나 버전도 같은 경계에서 처리합니다. 이미 다른 UI 요청에 밀린 응답이라도 client 내부에서 종료해야 합니다. 현재 hook은 오래된 요청의 오류를 먼저 건너뛸 수 있으므로 hydrate에서 예외를 던지는 것만으로 끝내지 않습니다.

project 호출의 원격 오류가 `CATALOG_WORKER_FAILED`인 경우에도 client 내부에서 연결을 종료합니다. 정상적인 원격 `CATALOG_SUPERSEDED`처럼 이미 정리된 revision에 대한 조회 실패는 기존의 요청 단위 결과로 유지합니다. 모든 원격 오류를 무조건 Worker 충돌로 바꾸지 않습니다. 종료된 client에서 먼저 resolve된 뒤 아직 처리되지 않은 결과도 새로 hydrate하거나 발행하지 않습니다.

다른 hydrate 정합성 오류를 적용 도중 발견하면 그 연결을 버리고 마지막으로 정상 발행한 불변 결과를 보존합니다. 계속 사용할 연결로 되돌리기 위해 전체 캐시 Map을 복사하는 별도 transaction은 추가하지 않습니다. 자동 본문 재동기화·수집 재시도 루프 없이 기존 명시적 복구가 새 Worker와 전체 초기 공고를 받도록 합니다.

## 전달 순서와 수명

- 비교 기준은 **마지막으로 전달한 projection**의 공고 Map입니다. acknowledge된 revision이나 한 번이라도 보낸 적 있는 ID 전체가 기준이 아닙니다. 결과가 같아 전송을 생략했어도 Map은 현재 파생 공고를 가리키게 합니다.
- client는 전달된 정상 projection을 순서대로 hydrate한 뒤 기존 최신 요청 검사가 UI 반영 여부를 정합니다. 오래된 요청이라는 이유로 중간 변경분을 건너뛰지 않습니다.
- `preview`는 경계를 계산할 수 있지만 본문·flag·facts 전달 기록을 소비하지 않습니다. acknowledge도 전달 기준을 바꾸지 않습니다.
- 최신 decode·마지막 acknowledge·마지막 project의 최대 세 revision 보존과 정리를 유지합니다. 오래된 revision으로 돌아갈 때는 그 시점의 수신 상태와 비교해 전체 공고·역방향 flag·변경 없음 중 필요한 결과를 보냅니다.
- 만료로 제거한 ID는 양쪽의 현재 캐시에서 제거합니다. 역방향 시각으로 다시 살아나면 본문과 필요한 facts를 다시 보냅니다. 과거 본문을 무한히 붙잡는 별도 strong cache는 두지 않습니다.
- 새 Worker/client는 비어 있는 전달 상태로 시작합니다. 이전 세대의 같은 revision 번호나 ID만으로 본문을 재사용하지 않습니다.
- 필터 때문에 보이지 않는 공고도 카탈로그의 공고로 관리합니다. 이후 조건을 풀었을 때 실제 교체된 본문이 나타나야 합니다.

## 시간·검색·수집 경계

`ageCatalog`와 수집·검증·마이그레이션의 정책은 바꾸지 않습니다. 일반 출처 30분, 일 단위 출처 24시간, 정확히 24시간 보존과 +1ms 제외, 실패한 게시판의 이전 자료, 알 수 없는 시각, legacy lastSuccessAt 추정과 명시적 null, unmappedCount의 알려지지 않은 값·과거 개수 보존 규칙을 유지합니다.

시간 경과는 새 수집이 아닙니다. 기존 화면 복귀·명시적 조회·쿨다운·Retry-After·refreshAfter 정책, 진행 응답 검증, ArrayBuffer의 Worker 전달과 개인 정보 비전송을 유지합니다.

이번 구현의 범위는 Worker model/client/types와 필요하면 작은 private 공고 변경 분류 helper입니다. 공유 freshness·검색·점수·저장 정책은 변경하지 않습니다.

## 대안 논의와 남은 비용

주 담당은 처음부터 본문과 오래됨 변경을 구분하는 방향을 제안했습니다. Astra는 처음에는 원본 Job별 WeakMap으로 stale 객체를 재사용하는 좁은 방식을 권고했습니다. 이후 첫 stale 전환과 역방향 전환에서도 전체 본문을 생략하는 추가 효과를 검토하여, 정확한 필드 비교·연결 종료·버전 조건을 포함한 사설 변경분 방식으로 선호를 바꿨습니다. 최초 의견도 보존합니다.

Fable의 독립 제안은 원본에서 인덱스·점수를 계산하고 생존 ID로 걸러, 본문뿐 아니라 시간 경계의 재색인·재점수·facts 재전송도 줄이는 방식입니다. 이 재계산 경로는 소스에서 확인되며 별도의 개선 가치가 있습니다. 다만 생존 필터를 미리보기·조건 완화·기타 근무지 등 모든 계산에 일관되게 적용하는 추가 설계가 필요합니다.

Fable은 후속 논의에서 이 본문·flag 단계를 먼저 진행하는 순서에 반대하지 않는다고 밝혔습니다. 그 조건은 남은 비용을 정확히 명시하고, 고정된 자료에서 facts 재전송 등 한계를 관측하는 단위 검사를 두며, F3를 다음 독립 단계의 후보로 등록하는 것입니다. 전체 개선의 더 나은 도착점이라는 최초 F3 권고를 철회한 것으로 기록하지 않습니다.

F3를 **다음 독립 설계의 우선 후보**로 등록합니다. 출발 근거는 `CatalogWorkerModel.search()`의 aged catalog 참조에 따른 무효화, `createSearchIndex()`의 전체 자료 처리, `createSearchRanker()`의 SearchEntry별 WeakMap과 `sentMatches` 참조 비교입니다. 생존 여부를 미리보기·조건 완화·기타 근무지 등 모든 소비자에 적용하고, 수집 중간 revision·프로필·메타데이터 변경과 preview로 인한 캐시 교체에서도 정확한 무효화·수명·facts 전달 규칙을 설계해야 합니다.

고정 fixture의 특정 stale·부분 만료 경계에서 아직 재전송되는 facts의 명시적인 ID·개수, 독립 재파싱의 보수적인 본문 재전송, 계속 포함되는 deadlines를 **남은 비용을 기록하는 검사**로 둡니다. 이는 F3를 완료했다는 검사가 아니며, F3에서 비용을 줄이면 그 단계의 의도한 변경으로 함께 갱신합니다. E2E에서는 facts 개수도 관측 자료에 기록합니다. 원래 색인·점수의 결과 의미는 유지하고, 이 최종 문서 해시에 대한 전원 승인을 받은 뒤 구현합니다.

현재 범위에는 경계 변경에 따른 aging 스캔·stale wrapper 생성·필요한 얕은 필드 비교가 남습니다. 파생 catalog의 참조가 바뀌면 인덱스·ranker 재생성과 해당 matches의 facts 전달도 계속 발생합니다. 전체 자료에 비례하는 스캔뿐 아니라 점수 계산·정렬·그룹 생성과 메타데이터·ID 배열·deadlines 전달 비용도 남으므로 전체 경계 처리를 변경된 공고 수만의 비용이나 단순 O(N)으로 설명하지 않습니다.

모든 가능한 deadline이 반드시 새 catalog를 만들거나 모든 카드가 반드시 다시 그려진다고 주장하지 않습니다. React 렌더 횟수와 실제 비용은 여기서 측정하지 않았습니다. 새 revision에도 공유되는 공고가 있으므로 “decode마다 모든 본문을 다시 보낸다”고 일반화하지 않으며, 독립적으로 파싱한 중첩 값은 보수적인 전체 본문 경계로 구분합니다. 실제로 바뀐 중첩 참조·non-stale 필드·수신 캐시 부재·지원하지 않는 own stale 상태의 전체 본문 예외는 유지합니다.

총 처리 시간이 일정해지거나 메인 스레드 지연이 특정 수치만큼 개선됐다는 주장을 하지 않습니다. 추가 WeakMap 캐시는 비교·할당 비용이 유의미하다는 근거가 있을 때 별도로 검토합니다. 큰 가상 자료의 단계별 실행 시간을 기록하더라도 실행 환경과 시계 출처를 밝힌 참고 관측으로만 취급하며, 빠르다는 통과 기준이나 실제 기기의 성능 개선값으로 사용하지 않습니다.

## 독립 검증의 필수 결과

Fable이 테스트를 작성·실행하며 제품 구현은 수정하지 않습니다. 기대값은 가상 자료의 명시적인 ID·순서·개수·시각·문구·flag 값으로 정하고 제품 함수로 정답을 계산하지 않습니다.

1. 순차 stale 경계: 초기 전체 공고 이후 A→B→C 각각의 경계에서 전체 본문 0개, 해당 회사의 실제 flag 변경만 전달합니다. 같은 경계 반복과 경계 사이 시각 변경에서는 변경분도 없습니다.
2. 정확히 24시간, +1ms의 부분·전체 만료와 역방향 복원: 제거 ID·본문 복원·역방향 flag·순서·집계·게시판 이력·expired 상태가 정확합니다.
3. own true·false·생략의 모든 전환과 own undefined의 보수적 전체 본문 경계, 확장 필드 추가·제거·같은 개수의 이름 변경·값 변경·중첩 참조 변경을 직접 확인합니다. 객체·과거 projection은 불변입니다.
4. 오래됨 경계를 지난 수집 중간 응답에서 바뀌지 않은 회사 본문을 생략하고, 같은 ID의 실제 본문 교체는 전달합니다. 필터로 숨겼다가 다시 표시한 공고도 최신 본문입니다.
5. preview·acknowledge가 전달 기록을 소비하지 않고, 최신 decode·acknowledge·project의 세 revision과 이후 정리가 유지됩니다. 늦은 정상 응답도 hydrate하고 최신 조건만 발행합니다.
6. 일 단위 출처, 입력에 이미 표시된 stale, 실패 게시판, legacy 시각·null, 빈 목록·결과 0개·기타 근무지의 기존 검사를 유지합니다. 바뀐 프로필의 facts·회사·도시·게시판 메타데이터도 갱신됩니다.
7. 실제 structured-cloned 응답의 전체 Job과 flag 변경을 구분해 관측합니다. 큰 가상 description의 전달 횟수·문자 합계 같은 결정적인 지표를 검사하되 이를 물리적 clone 바이트·힙·HTTP 대역폭·실행 시간 개선으로 표현하지 않습니다.
8. 없는 base, 중복·충돌 ID, jobIds 밖 대상, 누락 배열·값·버전, 지원하지 않는 버전을 거부합니다. 이미 세 revision이 보존된 상태의 잘못된 요청 뒤에도 이전 projected revision 조회와 다음 본문·flag·facts 전달이 유지되어, 오류 코드만이 아니라 부수효과 없음도 확인합니다. 최신 UI 요청에 밀린 잘못된 응답도 client 종료·알림 1회·부분 결과 미발행을 확인합니다. 이후 응답은 무시되고 명시적으로 새 연결을 만든 경우 전체 초기 자료를 받습니다. 정상 `CATALOG_SUPERSEDED`는 연결을 종료하지 않습니다.
9. 실제 브라우저 Worker로 1440px·320px에서 순차 stale·부분/전체 만료·진행 응답·타이머를 건너뛴 화면 복귀를 검사합니다. 목록·요약·게시판·비교 값, 입력·선택·저장 메모·상태를 명시적으로 확인하고 시간 경과 때문에 추가 API 호출이 생기지 않음을 검사합니다. 요청을 보류한 뒤 검색 조건을 바꿔 앞선 응답을 밀어낸 상태의 오류 주입에서는 입력·저장 자료와 마지막 정상 기준을 보존합니다. 아직 계산하지 못한 새 조건에 예전 추천을 붙이지 않고 기존 보존 모드의 **새 조건 확인 불가·집계 `—`** 안내를 유지합니다. 같은 조건의 마지막 정상 추천을 계속 볼 수 있는 경우와 구분합니다.
10. 브라우저의 전달 관측은 테스트 helper에서만 수행하고 메시지를 수정하지 않습니다. 오류 주입·응답 보류는 별도 통제이며 실제 자연 발생 충돌이나 네이티브 수명 복원의 증거로 보고하지 않습니다.

제품 수정 전에 기존 소스에서 최소 회귀 검사를 실행합니다. 최초 stale 전환의 전체 본문과 다음 회사 경계에서 재전송되는 앞선 회사의 ID를 각각 관측해 두 문제를 재현합니다. 아직 없는 helper의 import, 새 필드 누락, 타입·설정 오류나 지원하지 않는 프로토콜 요청 때문에 실패한 것을 원래 문제의 재현으로 세지 않습니다. 기존에 관측 가능한 `jobs`를 사용하고, 프로토콜 도입 후 요청 envelope에 필요한 변경은 별도로 기록합니다. 같은 가상 자료 의미와 본문 생략 기대값을 최종 검사에서도 유지합니다.

이 최소 회귀 검사와 최종 검사의 명령·기대 결과는 실행 전에 따로 전원 검토합니다. 먼저 기존 프로토콜의 `jobs`만으로 두 원인을 확인할 수 있는 작은 단위 검사로 범위를 제한합니다. 아직 없는 새 프로토콜·helper에 의존하는 전체 최종 검사나 큰 부하 검사를 baseline 재현에 함께 실행하지 않습니다. 의도한 baseline 실패도 실패 원문으로 기록하며 최종 통과에 포함하지 않습니다. 관측 기록에서는 전체 생존 목록 `jobIds`와 실제 전달 본문의 ID인 `bodyIds`를 구분합니다. 큰 가상 본문의 합계는 순방향 시간 경과와 만료 후 복원을 나눠 기록하며, 복원 시 필요한 전체 본문을 누락한 합계로 개선을 주장하지 않습니다.

최종 소스에서 전체 타입·단위 검사·빌드를 완료합니다. 개발 모드는 최종 diff에 해당하는 E2E를, 배포 모드는 Fable의 제안에 따라 **전체 E2E**를 실행하여 같은 관련 파일도 포함합니다. 별도의 배포 부분 실행을 먼저 반복할 필요는 없습니다. retry 0, 건너뜀·flaky·예상 밖 실패 없음이 완료 조건입니다. 정확한 개발 모드 파일과 명령, 두 모드의 Worker 전달 기록과 화면 증거 항목은 Fable 제안 및 최종 diff를 기준으로 별도 실행 계획에 고정합니다. 직접 model을 호출하는 기존 테스트에는 요청 버전 필드를 기계적으로 추가하되 기존 결과 기대값을 낮추지 않습니다.

두 모드의 실제 데스크톱·320px 화면과 전송 기록을 세 참여자가 각각 읽고 확인합니다. 화면은 해당 샘플 시점의 표시 근거이며 연속적인 프레임 안정성이나 자연 발생 성능의 증거로 확대하지 않습니다. 소유한 임시 서버·브라우저와 잠자기 방지 프로세스의 시작·종료·전원 사건을 기록합니다.

## 레퍼런스

2026-10-01에 실제 응답과 관련 문구를 읽고 원문·응답 해시·조회 시각을 보존했습니다.

- [MDN Worker.postMessage](https://developer.mozilla.org/en-US/docs/Web/API/Worker/postMessage): Worker 메시지의 데이터는 structured clone 가능한 객체입니다.
- [MDN structured clone](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Structured_clone_algorithm): 지원하는 객체 그래프를 재귀적으로 복제하고 방문한 참조를 추적합니다.
- [HTML structured data](https://html.spec.whatwg.org/multipage/structured-data.html): 직렬화의 memory map은 해당 작업의 중복 참조·순환을 보존하는 장치입니다. 서로 다른 메시지에 대한 공고 캐시가 아닙니다.
- [web.dev: Off-main-thread](https://web.dev/articles/off-main-thread): Worker와 메인 스레드 간 통신 비용도 고려해야 합니다. 2019년 글의 수치 예시를 이 앱의 보편적인 성능 예산으로 채택하지 않습니다.

## 합의·보존·정리

독립 의견과 이견·수정 이유를 보존하고 같은 설계 해시로 전원 승인한 뒤 구현·테스트를 진행합니다. 구현·테스트 및 실행 계획의 같은 해시에도 전원 승인하고, 실제 최종 근거에는 별도의 전원 승인을 받습니다.

완료한 제품·테스트·문서·결과와 합의를 Git에 보존하고 main만 push합니다. 조사 원문 등 다시 얻을 수 없는 자료는 보호된 로컬 보관 위치·이유·해시를 기록합니다. 그 뒤 단계의 재현 가능한 빌드·브라우저·캐시·로그·화면·trace·임시 도구·자료 사본과 소유 프로세스를 정리합니다. 이전 수집·관측·보존 자료를 변경하지 않았는지 확인한 후 단계 완료를 보고합니다.
