# 게시 상태 확인 중에도 카탈로그의 대기 상태 먼저 표시

75단계 설계안. 기준 소스는 `bb27a9fd941b765f5c4ff9e07f9567f2720092a6`입니다. 주 담당·GPT-6 Astra Max·Claude Code Fable 5.1 Max의 독립 의견을 검토한 뒤, 이 문서의 같은 해시에 명시적으로 동의해야 구현을 시작합니다. 초기 의견의 차이와 결정은 별도 단계 기록에 남깁니다.

## 문제와 범위

저장 화면에서 게시 상태 확인을 시작하고 탐색으로 이동하면, 카탈로그의 첫 비동기 응답이 진행 중인 게시 목록 확인을 기다립니다. 정상 본문 캐시가 있어도 그동안 브라우저에 공고나 진행 ID가 도착하지 않습니다. 현재 첫 요청의 150초 제한을 넘기면 연결 실패로 표시될 수 있습니다.

실제 서비스 함수와 가상 회사 두 곳으로 목록 응답을 보류해, 본문 캐시가 없는 경우와 5분 된 정상 본문이 있는 경우 모두 첫 응답이 보류되는 것을 재현했습니다. 이는 의존 작업을 기다리는 순서의 재현이며 실제 서비스의 지연 시간 측정이 아닙니다.

캐시 초기화를 마친 뒤에는 다른 작업의 외부 응답을 기다리지 않고, 현재 공고와 대기 상태를 먼저 보냅니다. 목록·본문의 기존 직렬 수집, 회사별 재시도·유효기간, 한 프로세스의 수집 공유는 유지합니다. 외부 요청 동시성을 늘리거나 첫 응답의 밀리초 목표를 보장하는 변경이 아닙니다.

## 작업 수명과 실제 수집 대상

1. 진행 중인 본문 작업이 있으면 같은 작업에 합류합니다. 게시 목록 확인만 진행 중이면 하나의 카탈로그 작업을 먼저 예약합니다. 예약 시점의 목록 작업 Promise를 캡처하고, 해당 작업의 완료와 저장을 백그라운드에서 기다립니다.
2. 예약된 작업의 ID는 대기·수집·완료 동안 같습니다. 대기 중 들어온 본문 조회 요청은 모두 합류하며, 명시적인 `refresh=1` 의도는 OR로 합칩니다. 수집 대상이 확정된 뒤에는 추가 요청으로 대상을 늘리거나 두 번째 수집을 시작하지 않습니다.
3. 이미 진행 중인 목록 확인에 들어온 추가 목록 요청은 그 목록 작업에 합류합니다. 뒤에 예약된 본문 작업 때문에 기존 목록 요청까지 본문 완료를 기다리게 만들지 않습니다. 목록 작업이 없는 동안 예약/실행 중인 본문 작업을 새 목록 작업이 앞지르지는 않습니다.
4. 목록 확인이 끝난 시점의 시계와 수락한 기록으로 본문 수집 대상을 한 번 계산합니다. 일반 조회의 정상 본문 TTL, 명시적 갱신의 최소 간격, 일 단위 출처, 양방향 오류 최소 60초와 더 긴 Retry-After를 그대로 적용합니다.
5. 이때 실제로 예약한 본문 회사 수가 `total`입니다. 목록 확인 중 새로 재시도 대기가 생겨 제외한 회사를 본문 완료/실패 수에 넣지 않습니다. 대기하는 동안 갱신 가능해진 회사도 이 계산에 포함합니다. 대상 확정 후에는 목록과 분모를 고정합니다.
6. 각 본문 작업은 실제 시작 시각을 기존 방식대로 사용합니다. 예약 시각을 본문 시도·정상 확인 시각으로 기록하지 않습니다. 큐 예약·대기 메타데이터·본문 0회 완료만으로 본문 캐시를 쓰거나 `collection` 관측을 만들지 않습니다. 기존 초기 캐시 관측과 실제 목록 저장은 유지합니다.
7. 뒤의 요청이 전역 Promise를 잘못 기다려 자기 자신을 기다리지 않도록 의존 관계와 완료 Promise를 구분합니다. 종료 처리는 자신이 소유한 작업만 해제합니다.

## 대기와 진행 표현

기존 `id`, `revision`, `total`, `completed`, `done`에 작업 단계 `phase`를 추가합니다. 새 서버가 만드는 진행에는 단계가 명시됩니다. 새 클라이언트는 `phase`가 없는 이전 진행을 기존 수집 단계로 읽습니다.

| 상태 | `phase` | `total` | `completed` | `done` |
| --- | --- | --- | --- | --- |
| 목록 확인 완료를 기다림 | `waiting-for-presence` | `null` — 아직 미정 | `0` | `false` |
| 대상 확정 후 본문 수집 | `collecting` | 확정된 양의 회사 수 | 종료한 실제 본문 회사 수 | `false` |
| 실제 본문 수집 완료 | `collecting` | 같은 확정 수 | 같은 확정 수 | `true` |
| 목록 확인 뒤 본문 대상 0개 | `collecting` | `0` | `0` | `true` |

대기 상태는 완료된 `0/0`이 아닙니다. 회사별 본문 `pending`도 아직 만들지 않습니다. 현재 정상·실패 상태와 각 회사의 본문 이력을 그대로 제공하고, 사용할 수 있는 공고를 먼저 탐색하게 합니다.

대기 중 개별 목록 결과를 수락하면 메타데이터 revision을 올립니다. 이 변경분은 `companyIds: []`, `jobs: []`이며 본문 교체·본문 완료 수 증가가 없습니다. 실제 실패 원인·시도·재시도, 원래 본문의 신선도·보존 기간을 갱신해 전달합니다. 본문의 정상 시각과 내용은 바꾸지 않습니다.

대기에서 대상 확정으로 넘어갈 때 revision을 올리고, 최종 종료 때도 올립니다. 본문 대상이 0개여도 종료를 관찰할 수 있어야 합니다. 모니터 요청이나 시간 경과 자체로 revision을 올리거나 제공자 요청을 예약하지 않습니다.

클라이언트는 모든 중간 응답을 받는다고 가정하지 않습니다. 대기 → 일부 본문 완료, 대기 → 전체 완료, 대기 → 본문 0회 완료를 같은 ID의 유효한 전환으로 받습니다. 대상 확정 뒤에는 분모가 바뀔 수 없고 대기 상태로 돌아갈 수 없습니다.

현재 revision을 다시 조회하면 진행 중에는 기존 204, 새 revision이나 종료 결과가 있으면 기존 변경분 응답을 사용합니다. 같은 revision의 미완료 응답은 허용하지 않고, 기존의 완료 결과 재조회 규칙은 유지합니다.

## HTTP와 이전 클라이언트

브라우저는 확장된 진행 표현을 다음 헤더로 명시적으로 요청합니다.

```http
Prefer: respond-async, orbit-progress=queued
```

`orbit-progress=queued`는 이 앱의 확장 capability입니다. 확장 요청에 대한 202에는 `Preference-Applied: respond-async, orbit-progress=queued`, 현재 ID·revision을 담은 `Location`, `Retry-After: 1`, `Cache-Control: no-store`를 제공합니다.

기존 `Prefer: respond-async` 요청에는 대기 상태나 미정 분모를 보내지 않습니다. 기존과 같이 앞선 목록 작업이 끝나 수집 대상이 확정되면 양의 고정 분모의 진행 응답을 받으며, 본문 작업이 필요 없으면 완료 카탈로그를 받습니다. 새 작업에 합류한 기존 클라이언트도 같은 규칙을 따릅니다.

`Prefer`가 없는 카탈로그/본문 요청은 기존처럼 필요한 작업의 완료를 기다립니다. 대기나 수집이 없고 정상 캐시를 바로 사용할 수 있으면 기존 200/304를 유지합니다. 목록 작업이 진행 중인 확장 요청은 정상 캐시가 있어도 대기 상태와 해당 캐시를 먼저 보내고, 이후 목록 결과의 메타데이터와 본문 0회 완료를 받을 수 있습니다.

옵트인이 없거나 알 수 없는 값이면 기존 동작을 사용합니다. Preference 이름은 대소문자를 구분하지 않으며 값은 `queued`와 일치해야 합니다. 동일한 내용의 quoted string도 같은 값으로 읽습니다. 헤더의 quoted comma가 다른 preference를 만들어내지 않도록 해석하고, 같은 preference 이름이 반복되면 첫 항목을 적용합니다. `respond-async; orbit-progress=queued`는 하나의 preference에 붙은 parameter이므로 확장 옵트인이 아닙니다. 확장 요청만 있고 `respond-async`가 없으면 기존 동기 계약입니다. 새 클라이언트는 확장을 모르는 이전 서버의 기존 진행과 완료 응답도 읽습니다.

모든 카탈로그 응답의 `Vary: Accept-Encoding, Prefer`, 완료 카탈로그의 정책 확인 후 ETag·재검증, 진행 리소스의 `no-store`, 고정된 동일 출처 URL은 유지합니다. 새로 수락한 실패·상태를 이전의 완료 ETag로 숨기지 않습니다.

## 완료·실패·보존

목록 확인 뒤 본문 대상이 0개이면 새 외부 요청 없이 해당 작업을 종료합니다. 사용할 수 있는 정상 본문 스냅샷이 있으면 원래 시각과 상태로 완료합니다. 정상 빈 본문 스냅샷도 정상 기록이며 이전 공고를 되살리지 않습니다.

사용할 정상 본문 스냅샷이 하나도 없으면 기존 `CATALOG_UNAVAILABLE` / `CATALOG_EXPIRED`, HTTP 503와 재시도 시각을 유지합니다. 목록 확인만으로 정상 빈 카탈로그를 만들지 않습니다. 정확히 24시간 보존, 1ms 뒤 제외하는 경계도 유지합니다.

예상 밖의 의존 작업·저장·스케줄러 거부도 무한 대기나 잘못된 성공으로 바꾸지 않습니다. 작업을 종료하고 진행 조회·대기 중인 기존 요청에 실패가 관찰되도록 합니다. 백그라운드 Promise와 오류 보고 콜백의 거부를 방치하지 않습니다. 실제 가상 저장 실패와 오류 보고 콜백의 throw로 현재 목록 Promise가 거부될 수 있음을 별도로 재현했습니다.

이 예외 실패의 응답은 handoff 전후에 동일합니다. 진행 조회와 해당 작업에 합류한 기존 비동기/동기 카탈로그 요청에는 HTTP `503`, `Cache-Control: no-store`, JSON `{"error":"공고 조회를 완료하지 못했어요. 다시 조회해 주세요."}`를 반환합니다. 이 응답에는 `code`, `retryAt`, `Retry-After`를 만들지 않습니다. 종료한 실패 작업은 교체되거나 프로세스가 재시작될 때까지 같은 ID로 남으며, 반복 조회에도 같은 503을 반환하고 204나 성공으로 바뀌지 않습니다. 게시 상태 요청의 기존 고정 503 계약은 유지합니다.

일반적인 캐시 저장 오류는 오류 보고 콜백이 정상 반환하면 기존처럼 메모리 결과로 진행합니다. 그 콜백 자체의 throw나 예상 밖의 스케줄러/저장 거부는 위의 예외 실패로 처리합니다. handoff 이후에 발생해도 이미 수락한 본문·시각을 메모리에서 삭제하거나 이전 자료로 되돌리지 않습니다. 해당 작업의 진행은 실패로 알리고, 이후 새 카탈로그 요청은 현재 메모리 자료와 기존 적격성 정책으로 다시 판단할 수 있습니다. 예외가 있어도 소유한 제공자 작업이 모두 종료되기 전에 수집 소유권을 해제하거나 다음 작업과 겹치게 하지 않습니다. 실패를 보고하는 콜백의 추가 throw도 처리되지 않은 Promise 거부로 남기지 않습니다.

작업은 디스크에 보존하지 않습니다. 프로세스 재시작 또는 다음 작업으로 교체된 ID에는 기존 410을 유지합니다. 완료한 하나의 작업과 회사별 완료 revision만 보유하고 전체 카탈로그 이력을 반복 저장하지 않습니다.

## 사용자 화면과 상태 유지

대기 상태에는 `공고 조회 대기 중`과, 먼저 시작한 게시 상태 확인 뒤 필요한 회사의 공고를 이어서 조회한다는 설명을 표시합니다. 아직 미정인 회사 수나 determinate progressbar를 표시하지 않습니다. 기존 공고와 원래 시각, 현재 확인한 회사별 실패를 함께 볼 수 있습니다.

실제 본문 수집이 시작되면 기존 `이번 회사 조회`와 실제 대상·종료 수를 표시합니다. 전체 회사의 현재 실패 수와 이번 본문 종료 수를 섞지 않습니다.

상태 안내는 기존 `role="status"`, `aria-live="polite"`를 사용하며 초점을 이동하지 않습니다. 1440px·320px에서 글자가 잘리거나 가로로 넘치지 않아야 합니다. 제품 화면에는 프로토콜·큐·내부 구현 세부사항을 안내하지 않습니다.

검색·필터·선택 도시, 저장한 원문·메모·지원 상태는 대기·수집·실패·재접속 뒤에도 유지합니다. 화면을 떠나면 해당 브라우저의 모니터링을 취소하지만 서버의 공유 작업을 취소하지 않습니다. 돌아오면 같은 진행 중 작업에 다시 연결합니다.

검색 결과가 없을 때의 조건 완화 제안은 기존처럼 작업 진행 중에는 숨기고 종료 후 다시 판단합니다. 대기 단계만 별도로 이 제안을 활성화하는 변경은 하지 않습니다.

기존 Worker 처리와 화면 반영, 최소 1초 폴링, 개별 요청 제한과 전체 10분 모니터링 제한을 유지합니다. 이제 큐 대기도 전체 모니터링 시간에 포함됩니다. 이 제한을 넘으면 현재 결과를 보존하고 기존 진행 연결 실패·재조회 안내를 사용합니다. 이 단계에서 장시간 작업의 제한을 늘리거나 자동 재시도 정책을 추가하지 않습니다.

## 독립 검증 요구

테스트 담당이 가상 자료와 명시적인 기대값을 사용합니다. Main의 로컬 진단은 원인 재현이며 회귀 검사 통과로 집계하지 않습니다.

- 목록 응답을 명시적으로 보류한 냉/정상/이전 캐시에서 확장 초기 응답이 **해제 전** 도착함을 확인합니다. 본문 호출 0회, 미정 분모와 현재 본문·시각을 검사합니다. 실제 시간이 빠르다는 추측이나 짧은 sleep만으로 순서를 증명하지 않습니다.
- 대기 중 일부 목록 성공/실패의 메타데이터 변경, 원래 본문 시각·내용·보존 만료, 증가하지 않은 본문 완료 수와 정확한 호출 기록을 검사합니다.
- 두 회사 중 하나가 대기 중 실패하여 제외되면 실제 본문 분모·호출은 1개여야 합니다. 재시도 기한을 대기 중 넘긴 회사는 handoff의 실제 적격성에 따라 포함합니다. 단계 시작 전후 강제 요청의 OR·고정 시점도 구분합니다.
- 정상·이전·정상 빈 본문이 있는 0회 완료와, 사용 가능한 본문이 없는 unavailable/expired 503를 검사합니다. 큐만으로 본문 저장이나 새 collection 관측을 만들지 않아야 합니다.
- 다수의 카탈로그·본문 호출의 같은 ID, 추가 목록 호출의 기존 목록 합류, 목록 저장 종료 뒤 본문 시작, 자기 대기·중복 수집 없음, 오류 거부의 종료를 검사합니다.
- HTTP의 옵트인/이전 클라이언트·동기 요청·Vary·ETag·헤더, quoted/중복/잘못된 preference, 읽기 전용 진행·재시작/교체 410를 검사합니다.
- decoder는 잘못된 단계·미정/0 분모·대기 중 본문 교체·거꾸로 된 전환·변경된 확정 분모·ID/회사/출처/공고 불일치를 거부해야 합니다. 중간 revision을 건너뛴 정상 전환은 받아야 합니다. 기존 무결성 검사를 없애지 않습니다.
- 실제 앱 서버와 브라우저에서 저장 화면 → 목록 확인 보류 → 탐색 대기 → 수집/0회 종료/실패와 재접속을 검사합니다. 실제 요청의 해제 순서·호출 수, 검색·저장 상태와 접근성을 확인합니다. 라우팅으로 만든 화면 검사만으로 서버의 의존 순서를 입증하지 않습니다.
- 최종 타입·전체 단위 검사·빌드와 영향받는 E2E의 개발·배포 실행을 완료합니다. 실패·환경 문제·수정·재검증을 구분하고, 기대값 완화나 건너뜀으로 합의를 만들지 않습니다.

## 조사 근거와 한계

2026-09-30 UTC에 RFC 7240과 WCAG 문서 응답·조회 기록을 보존하고 크기·SHA-256·ZIP 원본 일치를 확인했습니다.

- [RFC 7240 §4.1](https://www.rfc-editor.org/rfc/rfc7240.html#section-4.1): 클라이언트의 비동기 응답 선호와 202 사용. 실제 모니터·종료 프로토콜은 앱이 정의합니다.
- [WCAG 2.2 · 4.1.3 Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html): 초점을 옮기지 않는 대기·진행·결과 안내의 프로그램적 전달.

미정 분모·명시적 capability·단계별 수집 정책은 이 앱의 설계 결정입니다. 제공자 증설, 여러 서버 간 공유 수집, 수집 자체의 속도 개선, 캐시 형식 변경, Worker 성능·지구 렌더링 변경은 포함하지 않습니다.
