# 공식 채용 출처 확장 설계

상태: 설계 문서 원본 SHA-256 `f1234e860709cb1eb93fc552d10f17e9e5e45a342d864925e535cf071630aa37`에 대한 검토 후 구현했고, source07의 로컬 검증은 Main·Astra 합의를 마쳤다. 이 문단만 현재 상태로 정정했으며 설계 본문은 유지한다. 실제 신규 공고의 운영 반영과 자동 발행 확인은 아직 미완료다. [로컬 검증 기록](../validation/reference-official-jobs-2026-10-26.md)을 참고한다.

## 목표와 기존 상태

두 레퍼런스의 신규 출처 조사·원문 수집·중복 식별·실패 처리 방식을 적용해 실제 공고를 추가한다.

- [ai-job-search](https://github.com/ai-job-search-dev/ai-job-search/tree/e16acee3abdaae57f8026789338a3c6eebf4608b): 실제 목록과 상세 응답을 조사한 뒤 공통 계약을 따르는 출처 어댑터를 등록한다. 공고의 정규 URL과 안정적인 식별자로 이전 집합과 새 집합을 비교한다.
- [ai-job-search-kr](https://github.com/wing0828/ai-job-search-kr/tree/ae76108fc5e2ae75dc057e4147a3c56982042ec5): 회사 공식 원문을 우선하고 목록·본문의 신원을 확인한다. robots, 호스트별 간격, 요청 한도와 오류·빈 결과 구분을 적용한다.

개인 이력서 작성이나 모든 채용 포털의 이식은 이번 변경의 대상이 아니다. JSON-LD와 기존의 회사별 전체 게시판 계약을 연결하는 부분은 이 프로젝트에서 설계한다.

기존 서비스는 Cloudflare Worker와 SQLite Durable Object에서 공개 자료를 제공하고, GitHub Actions의 Node 수집기가 예약 발행한다. 검증된 구현 커밋은 `176ea96f8da55755419696bff01ba9bcdebee941`이며 현재 회사는 130곳이다. 기존 운영 성공이나 과거 공고 확대를 이번 레퍼런스 적용의 증거로 대신하지 않는다.

## 조사한 출처

2026-10-25에 확인한 `https://careers.daangn.com/jobs/`의 전체 공고 표기는 50개이고, `[data-job-list] [data-job-card]`도 고유한 공고 50개다. 연결된 클라이언트 스크립트는 이 목록을 숨기거나 보여 주며 추가 페이지를 수집하지 않는다. 페이지 전체에는 배너의 중복 링크와 항상 존재하는 숨긴 빈 결과 문구도 있으므로 이를 공고 수나 빈 게시판의 근거로 사용하지 않는다.

| 회사 ID | 회사 | careers 게시판 ID | 원문의 회사 구분 | 조사 당시 공고 |
| --- | --- | --- | --- | --- |
| `daangn` | 당근 | `daangn` | `karrot-market` | 45 |
| `daangn-pay` | 당근페이 | `daangn-pay` | `karrot-pay` | 5 |

각 회사의 필터 선택지가 원문에 명시되어 있다. 당근서비스 등 다른 선택지를 두 회사의 공고로 합치지 않는다.

상세 표본 `5004587003`과 `8000332003`에서 목록·상세 제목, 정규 URL, `JobPosting.hiringOrganization`의 당근·당근페이를 확인했다. `JobPosting`은 `Organization`과 함께 JSON-LD 배열 안에 들어 있다. 두 표본의 근무지는 국가 `KR`만 명시되어 있다. 바닥글의 서울 주소는 회사 연락처이며 공고 근무지로 사용하지 않는다.

이 수는 원문 전체 목록 수다. 기술 직군 정규화 후 신규 공고 수와 실제 서비스 반영은 별도 검증한다.

## 목록과 본문 계약

서버에서 `parse5@8.0.0`으로 HTML 트리를 읽는다. 웹페이지의 JavaScript나 본문 링크를 실행하지 않는다. `parse5`는 수집기에만 사용하며 Worker의 공개 조회 경로에 포함하지 않는다.

목록은 쿼리가 없는 `/jobs/`에서 읽는다.

1. 페이지 신원, 단 하나의 전체 목록과 공고 수, 회사 필터 선택지를 검증한다.
2. 목록 내부의 공고 카드만 읽고 고유한 숫자 ID, 같은 출처의 정규 상세 URL, 제목, 회사 구분을 확인한다.
3. 전체 카드 수와 명시된 공고 수가 같아야 한다. 50을 상수로 사용하지 않는다. 중복 ID, 모순된 항목, 누락된 표시, 새 페이지 나누기, 잘림, 한도 초과는 불완전한 조회로 실패한다.
4. 전체 목록을 검증한 후 해당 회사의 항목을 선택한다. 회사 선택지와 전체 목록이 정상인 경우에만 해당 회사의 공고가 0개임을 인정한다.
5. presence에는 해당 회사의 모든 공고 ID를 제공한다. 본문 수집과 기술 직군 선별은 기존 규칙을 따른다.

상세 페이지는 `/jobs/role/<숫자 ID>/`만 읽는다.

- 배열·객체·`@graph` 안의 JSON-LD를 데이터로 파싱한다. 일치하는 `JobPosting`은 하나여야 하며, 다른 공고나 모순된 중복 공고를 섞지 않는다.
- 목록과 상세의 ID, 정규 URL, 제목, 회사가 일치해야 한다. 바깥 제목의 추천 배지나 사이트 바닥글을 본문 사실로 사용하지 않는다.
- 비어 있지 않은 실제 설명과 올바른 고용 형태·위치 필드를 검증한다. 로그인·차단·다른 공고·누락된 본문은 빈 공고로 처리하지 않는다.
- `data-keywords`는 검색용 값이다. 기술, 자격, 비자, 근무 형태의 근거는 제목·구조화된 직군·공고 본문이다.
- `datePosted`를 수정 시각이나 수집 시각으로 바꾸지 않는다. 이번에는 원본 검증 자료에 보존하고, 공개 `updatedAt`은 확인되지 않으면 `null`이다. 오래됐지만 열려 있는 공고를 임의의 14일 필터로 제외하지 않는다.
- 국가만 확인된 공고는 도시 미확인 상태를 유지한다. 기존 다른 근무지 목록·검색·상세에서 찾을 수 있어야 한다.

## 네트워크와 실패 처리

허용 출처는 `https://careers.daangn.com`으로 고정한다. 수집기의 요청 경로는 `/robots.txt`, `/jobs/`, 숫자 ID의 상세 페이지뿐이다. `/preview`, `/jobs/completed`, 지원서 경로와 외부 출처는 요청하지 않는다.

- User-Agent는 `OrbitCareerAtlas/1.0`으로 밝힌다.
- 두 회사와 목록·본문·robots·리다이렉트가 같은 호스트 대기열을 사용한다. 동시 요청은 하나이며 시작 간격은 최소 3초다. 3초는 레퍼런스에서 채택한 보수적 정책이며 사이트가 선언한 값으로 보고하지 않는다.
- robots의 해당 User-Agent 및 `*` 그룹, 동일 그룹 병합, 가장 긴 경로 규칙과 같은 길이의 Allow 우선, 와일드카드·끝 표시를 처리한다. 더 긴 `Crawl-delay`를 따르되 60초를 넘으면 수집을 실패시킨다.
- robots는 각 회사의 수집 호출에서 새로 읽고 그 호출 안에서만 재사용한다. 네트워크 오류, 잘못된 응답, 404·410을 포함한 비정상 상태는 확인 실패로 처리한다. 보존된 정상 공고를 빈 목록으로 바꾸지 않는다.
- 리다이렉트는 자동으로 따라가지 않는다. 최대 3회이며 대상의 출처·경로와 robots를 확인한 뒤 같은 대기열에서 요청한다.
- HTML 응답은 압축 해제 후 4 MiB, robots는 512 KiB까지 읽는다. 전체 목록 300개, 회사별 상세 300회, 회사별 총 요청 310회, 호출 전체 15분을 한도로 둔다. 초과 시 성공한 일부 목록으로 마감 상태를 계산하지 않는다.
- HTTP 오류와 `Retry-After`, 취소, 대기 중인 요청의 정리를 기존 게시판 실패·backoff 계약에 연결한다.
- `careers`의 24시간 갱신 규칙과 기존 자료 유효기간을 유지한다. 기존 130개 회사의 스냅샷을 다시 수집한 것처럼 시각을 바꾸지 않는다.

각 회사 호출은 전체 목록을 독립적으로 검증한다. 두 회사의 목록 요청 두 번은 같은 대기열에서 수행한다. 기존 호출 인터페이스에는 수집 회차 식별자가 없으므로, 새 전역 캐시로 서로 다른 회차의 목록을 섞지 않는다. 이 선택과 요청 한도는 Astra의 설계 검토에서 명시적으로 합의한다.

## 통합

`shared/companies.ts`에 두 회사를 등록하고 `shared/career-sources.ts`에 서로 다른 게시판 ID를 추가한다. `server/providers/careers.ts`에서 명시적으로 새 어댑터에 연결한다. 현재의 마지막 Zalando 분기로 새 출처가 흘러가지 않게 한다.

목록·본문 파서는 새 `server/providers/daangn.ts`에 둔다. robots·전용 수송 처리는 분리하고, 다른 제공자의 기존 수송 동작을 불필요하게 바꾸지 않는다. 공통 정규화·presence·캐시·체크포인트·관측·발행 경로를 재사용한다. 로컬 자료 파일이나 `ORBIT_BOARDS_FILE`만 추가한 상태를 운영 통합으로 간주하지 않는다.

신규 기본 회사 수는 132곳이다. 기존 130곳과 새 두 곳의 건강 상태를 구분해 검사한다. 기존 가용성·용량 기준을 낮추지 않는다.

## 검증과 완료 조건

Main은 제품·통합·문서를, Astra는 독립 설계·소스·결과 검토를, 별도 테스트 담당은 가상 자료와 E2E·실제 수집 검증을 맡는다. 설계, 최종 소스·테스트·실행 계획, 실제 결과마다 같은 해시에 대한 Main·Astra의 명시적 합의가 필요하다.

테스트는 다음 결과를 직접 확인한다.

- 중복 배너, 숨긴 빈 결과 문구, 여러 회사가 포함된 전체 목록에서 정확한 회사별 ID와 공고 수를 얻는다.
- 정상적인 0개와 구조 변경·잘린 목록·중복 ID·모순된 수·한도 초과를 구분한다.
- 본문의 잘못된 회사·제목·ID·URL, 중복 `JobPosting`, 누락된 설명을 거부한다.
- 국가 `KR`만 있는 공고를 서울로 바꾸지 않으며, 정규직·계약직·인턴과 미확인 값을 보존한다.
- 차단·리다이렉트·시간 초과·429·본문 일부 실패에서 기존 공고를 보존하고, 읽지 못한 공고를 마감으로 바꾸지 않는다.
- 성공한 전체 목록에서 사라진 공고만 마감 상태로 전환한다. 같은 목록을 다시 읽어 새 공고가 중복 추가되지 않는다.
- 체크포인트의 새 회사 구성이 기존 130개 회사와 관측 자료를 보존한다.
- 최종 소스에서 필요한 타입·단위·빌드·Cloudflare·전체 production E2E와 영향받는 development 검사를 실행한다. 기존 미완료 Stage81 변경은 격리한다.

실제 수집에서는 이전 catalog의 ID·정규 URL 집합을 동결한 뒤 전체 목록과 필요한 본문을 읽는다. 원문 총수, 회사별 총수, 정규화된 기술 직군, 위치 미확인 항목, 실패, 새로 추가된 ID를 구분한다. 적어도 하나의 실제 신규 공고가 최종 catalog에 들어가야 하며, 반복 조회를 추가 공고로 세지 않는다.

새 공고를 데스크톱·모바일의 검색·다른 근무지 목록·상세·원문 링크에서 확인한다. 승인된 커밋을 발행한 뒤 운영 catalog와 예약 수집이 같은 새 출처 및 공고 ID를 제공하는지 검사한다. 측정한 Cloudflare 발행 크기와 저장 한도를 확인한다. 구현·승인·검증·실제 배포 및 수집 버전을 Git에 보존하고, 재현할 수 없는 원본은 위치와 보존 이유를 남긴 로컬 자료로 유지한다. 그 뒤 해당 단계의 임시 자원을 정리한다.
