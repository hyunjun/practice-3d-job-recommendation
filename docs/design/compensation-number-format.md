# 공고 보상 금액의 숫자 표기 해석

설계 후보 3 · 2026-10-01 · 76단계. 단계 승인은 이 문서의 SHA-256과 각 참여자의 독립 검토 기록에 연결한다.

## 문제와 근거

보존된 2026-09-27 수집 자료에서 8개 본문 기반 EUR 보상 구간이 현재 코드에서도 잘못 해석된다. Affirm 3개는 공백으로 구분한 천 단위의 앞부분만 금액으로 읽고, Proton 5개는 점으로 구분한 금액을 작은 소수로 읽는다. 이는 당시 자료의 표시 오류이며 현재 공고의 모집 여부를 새로 확인했다는 뜻이 아니다. 현재 결과는 모두 `salary:null`이다. Affirm의 기존 결과는 숫자 일부를 잘못 읽어 불완전하고, Proton은 기본급 여부가 확인되지 않았다. 잘못된 작은 금액이 실제 연봉 필터·순위에 쓰였다고 주장하지 않는다. 교정 후에는 기존 통화·기간·기본급·지역 조건을 충족하는 정상 범위가 연봉 비교 대상이 될 수 있다.

Unicode CLDR는 숫자의 소수점·그룹 구분 기호를 로케일별 기호로 정의한다. 통화나 회사 소재지가 숫자 표기의 로케일을 확정하지는 않는다. Greenhouse의 구조화된 `pay_input_ranges`는 숫자형 `min_cents`·`max_cents`와 통화를 별도로 제공하므로 본문 문자열 해석의 변경을 그 숫자에 적용하지 않는다.

- [Unicode TR35, Number Symbols](https://unicode.org/reports/tr35/tr35-numbers.html#Number_Symbols)
- [Unicode TR35, Parsing Numbers](https://unicode.org/reports/tr35/tr35-numbers.html#Parsing_Numbers)
- [Greenhouse Job Board API](https://docs.greenhouse.io/job-board.html)

실제 응답·공고 본문·분석 사본은 무시되는 로컬 자료로 보관한다. 공개 회귀 검사에는 가상의 회사·공고·문구를 쓴다.

## 숫자를 읽는 계약

금액 전체를 먼저 구분한 뒤 해석한다. 지원하지 않는 표기 안의 숫자 일부를 떼어 읽거나, 범위의 다른 끝점을 별도 확정 금액으로 살리지 않는다.

기존의 구분자 없는 정수, 쉼표 세 자리 그룹, 명확한 소수점, `k`·`m` 배수, 통화 표기, 범위 구분자와 단일 확정 금액을 유지한다. 다음 지원 범위를 명시적으로 추가한다.

| 가상의 본문 금액 | 숫자 결과 |
| --- | --- |
| `EUR 84 000–126 000` | 84000–126000 |
| `EUR 84 000–126 000` — U+00A0 | 84000–126000 |
| `EUR 84 000–126 000` — U+202F | 84000–126000 |
| `EUR 84 000,50–126 000,75` | 84000.5–126000.75 |
| `EUR 84.000,50–126.000,75` | 84000.5–126000.75 |
| `EUR 84,000.50–126,000.75` | 84000.5–126000.75 |
| `EUR 84 000–126 000` — U+2009 | 84000–126000 |
| `EUR 1 234 567` — 서로 다른 지원 공백 | 1234567 |
| `EUR 1,234.567–2,345.678` | 1234.567–2345.678 |
| `EUR 1234.567–2345.678` | 1234.567–2345.678 |
| `EUR 1.200.000–1.500.000` | 1200000–1500000 |
| `EUR 62.000–118.000` | 숫자를 확정하지 않고 원문 보존 |
| `EUR 1.500k` | 숫자를 확정하지 않고 원문 보존 |
| `EUR 24,50–38,75` | 이번 문법에서는 지원하지 않으며 원문 보존 |

`62.000`처럼 다른 구분자 없이 점 앞이 1~3자리이고 뒤가 정확히 3자리인 숫자 핵심 부분은 소수와 엄격한 천 단위 그룹 문법에 모두 해당한다. 이를 62로 읽거나 통화·근무지·금액 크기로 62000이라고 추정하지 않는다. `k`·`m` 배수도 이 모호성을 해소하지 않는다. 반면 `1234.567`은 앞이 네 자리라 지원하는 점 그룹 문법이 아니며, `1,234.567`은 쉼표 그룹이 점의 소수 역할을 구분한다. 이런 기존의 명확한 소수 표기는 소수 자릿수를 임의로 줄이지 않는다.

기존 쉼표 세 자리 그룹은 호환성을 위한 명시적인 지원 문법이다. 쉼표를 소수점으로 쓰는 로케일에서 `60,000`이 가지는 반대 방향의 모호성까지 해결했다고 설명하지 않는다. 이번 조사에는 `$204,00`과 `$264,000`이 한 범위에 나타나는 등 잘못된 것으로 보이는 쉼표 표기가 있었다. 구분자 없는 정수 뒤의 소수 쉼표는 이번에 추가하지 않는다. 새 소수 쉼표는 올바른 점·공백 그룹 정수 뒤에서만 한두 자리까지 지원한다. 누락된 숫자를 추정해 고치지 않는다.

지원 문법은 다음과 같다. `SPACE`는 한 가족으로 취급하여 같은 숫자 안에서 네 공백을 섞을 수 있지만, 쉼표·점·공백을 정수의 그룹 구분자로 섞을 수는 없다.

```text
SPACE       := U+0020 | U+00A0 | U+202F | U+2009
DIGITS      := [0-9]+
GROUP(s)    := [0-9]{1,3} (s [0-9]{3})+     s ∈ {"," , "." , SPACE}
DOT_FRAC    := "." [0-9]+
COMMA_FRAC  := "," [0-9]{1,2}

NUMBER      := DIGITS [DOT_FRAC]
             | GROUP(",") [DOT_FRAC]
             | GROUP(".") [COMMA_FRAC]
             | GROUP(SPACE) [DOT_FRAC | COMMA_FRAC]
AMBIGUOUS   := [0-9]{1,3} "." [0-9]{3}
MULT        := [kKmM]
```

다른 숫자 구분자를 포함하지 않는 핵심 부분에 `AMBIGUOUS` 판정을 먼저 적용한다. 배수는 기존 `DIGITS[DOT_FRAC]`·`GROUP(",")[DOT_FRAC]` 뒤에서만 허용하며 앞의 지원 공백이나 탭은 허용한다. 새 점·공백 그룹이나 그룹 뒤 소수 쉼표에 배수를 붙인 표기는 지원하지 않는다. 범위 한쪽만 배수가 있으면 다른 쪽의 완전하게 해석된 배수 적용 전 값이 1000 미만일 때만 기존처럼 배수를 상속한다. 이 기존 약식 표기의 크기 기준을 로케일 추정과 구분해 명시한다.

| 배수 표기 | 숫자 결과 |
| --- | --- |
| `EUR 84–126k` | 84000–126000 |
| `EUR 84 000–126k` | 84000–126000, 이미 그룹인 끝점에 배수 재적용 안 함 |
| `EUR 1.25m` | 1250000 |
| `EUR 84 000k` | 지원하지 않으며 원문 보존 |
| `EUR 1.500m` | 모호한 핵심 부분이므로 원문 보존 |

숫자 연속 부분은 숫자와, 다음에 숫자가 이어지는 구분자(쉼표·점·아포스트로피·오른쪽 작은따옴표·공백)를 끝까지 포함한다. 시작 방향에서도 숫자나 숫자 뒤의 구분자가 바로 앞에 있는 숫자 조각에서 새로 시작하지 않는다. 지원하지 않는 구분자·단위·부호를 본 뒤 앞부분만 유효하다고 회수하지 않는다. 숫자에 직접 붙은 단어·퍼센트·다른 숫자에서도 짧은 조각을 회수하지 않는다. 통화 표기와 지원 배수는 기존처럼 명시적으로 구분한다. 숫자나 유효한 범위를 줄바꿈 너머로 합치지 않는다. 일반 문장 마침표·구두점은 숫자 자체의 구분자와 구별한다. `USD 120,000 3 days`처럼 같은 줄의 숫자가 공백으로 이어지는 경우도 하나의 잘못된 숫자 연속 부분으로 보아 금액을 확정하지 않는다.

모호하거나 잘못된 숫자도 정상 금액과 같은 인접 통화 표기·급여 문맥 조건을 만족할 때만 불완전한 보상 근거로 남긴다. 예를 들어 `Annual base salary: USD 120,000 for a team of 1 0.`이나 `62.000 units shipped. Annual base salary: USD 120,000.`은 각각 정상 USD 120000 단일 연봉만 남기며 무관한 숫자로 보상 경고를 만들지 않는다.

범위의 첫 끝점 뒤에도 배수·통화 표기와 기존 지급 기간 어휘의 슬래시 주석(`/year`, `/yr`, `/month`, `/mo`, `/week`, `/wk`, `/day`, `/hour`, `/hr`, `/h`)이 올 수 있다. 이런 주석이 범위 연결을 끊지는 않는다. 양 끝점이 정상이고 다른 비교 조건도 충족하면 하나의 정상 범위로 읽는다. 한 끝점이라도 모호하거나 잘못된 범위는 전체를 하나의 불완전한 범위로 취급하며, 어느 끝점도 별도 단일 급여로 회수하지 않는다. 별도 문장의 정상 급여까지 함께 삼키지 않는다. 역전된 범위는 기존처럼 비교하지 않는다.

| 기간·통화 표기가 있는 가상의 범위 | 결과 |
| --- | --- |
| `Annual base salary: USD 84,00/year to USD 126,000/year.` | 숫자 구간 없음, 원문·비교 불가 안내, `salary:null`. 확정 126000 단일 급여를 만들지 않음 |
| `Annual base salary ranges from USD 174,000/year to USD 299,000/year.` | USD 174000–299000, 연간 기본급, 비교 가능 |
| `Annual base salary: 120,000 USD – 150,000 USD.` | USD 120000–150000, 연간 기본급, 비교 가능 |

줄바꿈은 숫자나 유효 범위를 연결하지 않는다. 다만 금액이 있는 줄이 범위 구분자로 끝나고 다음 줄이 금액으로 시작하거나, 두 금액 사이 줄에 구분자만 있으면 하나의 지원하지 않는 불완전한 범위로 묶어 양 끝의 부분 회수를 막는다. 다음 줄이 대시와 숫자로 시작하면 대시를 목록 표시로 취급하여 앞줄 급여와 연결하지 않는다. 따라서 `Annual base salary: USD 150,000` 다음의 `- 4 weeks of vacation`, `- 401(k) match`는 정상 단일 연봉에 경고를 추가하지 않는다. 반면 `USD 120,000 –` 다음 줄의 `USD 150,000` 및 두 금액 사이 별도 줄의 `–`는 숫자 구간 없이 원문 근거만 남긴다.

배수를 적용한 십진수의 실제 값이 양수이고 `Number.MAX_SAFE_INTEGER` 이하여야 한다. 이 한도는 이진 `Number` 변환의 반올림으로 초과분이 사라지기 전에 확인한다. `9007199254740991`은 한도 내이고, `9007199254740991.01` 및 `9007199254.74099101m`은 초과하므로 근거만 남긴다. 허용한 값을 기존 `Number` 표현으로 바꾼 결과도 유한한 양수여야 한다. 새 공용 금액 자료형이나 일반 임의 정밀도 연산 체계를 도입하지 않는다.

지원하지 않는 표기는 아포스트로피·오른쪽 작은따옴표 그룹, 세 자리 이외의 그룹(라크·네 자리 등), 지수·부호·퍼센트 표기, 모호한 점 세 자리, 새 그룹 표기에 붙인 배수, 세 자리 이상의 새 소수 쉼표, 정수 내부의 그룹 가족 혼합, 네 종류 이외의 공백, ASCII 이외의 숫자, 줄바꿈을 건너는 범위다. 이를 부분 숫자로 추정하지 않는 한계를 기록한다.

통화·기간·기본급/총보상·지역 조건의 해석은 기존 계약을 유지한다. 숫자를 읽을 수 있어도 다른 조건이 미확인인 경우 연봉으로 비교하지 않는다. 월급·시급을 연봉으로 환산하지 않는다.

## 불확실한 금액의 표시

모호하거나 잘못된 숫자 표기를 발견하면 원문 근거와 기존의 비교 불가 안내를 남긴다. 정확하지 않은 금액 구간을 만들지 않는다. 같은 공고에 다른 정상 구간이 있으면 그 구간은 표시하되 전체가 완전하게 확인된 연봉이라고 주장하지 않는다. 불완전한 결과는 연봉 비교와 알려진 연봉만 포함하는 필터에 쓰지 않는다.

숫자 구간이 하나도 남지 않으면 `보상 설명은 있지만 비교할 수 있는 급여 범위를 확인하지 못했어요. 원문 근거를 확인해 주세요.`, 정상 구간과 불완전한 근거가 함께 있으면 `일부 보상 구간의 금액을 확인할 수 없어요. 확인된 구간과 원문을 표시하며 연봉 비교에는 사용하지 않습니다.`라는 기존 안내를 쓴다. 실제 근거가 있는 모호한 금액을 조용히 버려 `연봉 미공개`로 바꾸지 않는다.

`MAX_TEXT`와 금액 수 제한을 유지하며, 제한을 넘겼다는 근거 없이 본문 전체를 읽었다고 주장하지 않는다. 개인정보나 실제 회사의 본문을 공개 테스트 자료로 옮기지 않는다.

## 이미 저장된 자료

보상 해석 버전을 3으로 올린다. 입력 스키마는 기존 버전 1·2도 받아들인다. 기존 `upgradeJobCompensation`과 공고 업그레이드 경로를 통해 서버 캐시, 브라우저 카탈로그, 저장 공고·백업의 본문 기반 금액을 다시 해석한다.

- 공고 ID, 회사, 원문, 수집 시각과 갱신 시각을 바꾸지 않는다. 새 수집으로 기록하지 않는다.
- 저장 상태·지원 메모·저장 시각을 보존한다. 본문에서 확인할 수 없는 옛 저장 급여를 보존하던 정책도 유지한다.
- 본문 길이 제한 밖에서 보존한 보상 인용문도 기존 방식대로 독립적으로 재해석한다. 다른 인용문끼리 통화·기간을 빌려 주지 않는다.
- 모호한 보상 인용문을 복구했다면 예전의 잘못된 숫자를 보존하지 않는다. 원문 근거가 아예 없는 경우의 ‘이전 기록’ 보존 정책과 구분한다.
- 구조화된 게시판 숫자에 근거한 기존 버전 1·2 결과는 보존한다. 본문 숫자 정책이 구조화된 숫자를 다시 문자열로 변환하거나 대체하지 않는다.
- 이미 버전 3인 자료는 중복 계산하지 않는다. 알 수 없는 미래 버전은 계속 거절한다.

캐시 파일 형식, 게시 여부 확인 주기, 외부 호출 정책, 환율, 지원 통화·도시 범위는 이 단계의 변경 대상이 아니다. 공급자가 잘못 기재한 구조화된 숫자나 모든 언어의 보상 문법을 자동 교정하는 기능도 아니다.

## 독립 검증

Fable이 기존 검사를 확인하고 테스트를 보강·실행한다. 제품 파서로 기대값을 계산하지 않으며 금액·상태·문구의 기대값을 명시한다. 주 구현 담당과 Astra는 최종 소스·테스트·실행 계획의 동일 해시를 검토한다.

필수 검증은 지원 표기와 모호·잘못된 표기의 경계, 단일 금액과 양 끝 범위, 정상/불완전 구간의 혼합, 배수 표기, 통화·지급 기간·기본급 구분의 회귀, 구조화된 숫자 보존, 버전 2 자료의 업그레이드와 저장 상태 유지다. 브라우저에서는 공고 목록·상세의 숫자·원문·미확인 안내, 연봉 필터, 저장 후 재시작·복원처럼 이어지는 사용자 흐름을 검사한다.

실제 6,819개 과거 공고는 최종 소스에서 읽기 전용으로 전후 대조한다. 분류를 미리 `변화 없음`, `공백 그룹 교정`, `점 세 자리 → 근거`, `잘못된 표기 → 근거`, `새로 비교 가능`, `비교 불가로 변경`, `구조화된 자료 보존`, `기타`로 정하며 한 공고에 여러 분류가 적용될 수 있다. 처음 발견한 8개를 전체 변경 수라고 가정하지 않는다. 모든 변경을 분류하고, 비교 가능 여부가 바뀐 공고와 기타 변경은 개별 근거로 검토한다. 구조화된 자료는 버전을 제외한 전체 공고가 동일한지 각 공고별로 검증한다. 문법별 숫자 표기 수와 Himalayas의 본문/구조화 자료 우선순위 변화 여부도 확인한다. 자료·도구는 공개 테스트와 구분하여 로컬 보존한다.

서버 디스크 캐시 업그레이드는 단위 검사로 검증하고 현재 합성 E2E 서버가 디스크 캐시를 직접 읽지 않는 한계를 기록한다. 브라우저에서는 목록·상세·자료 요약·도시 통계, 연봉 필터, 버전 2 저장 공고의 정상/모호/복구 불가/구조화된 보상, 저장 상태 유지와 CSV 내보내기를 검증한다. 기존 회귀 자료의 버전 상수만 갱신하는 변경과 버전 2 업그레이드를 검증하는 자료를 분리한다.

관련 타입·전체 단위 검사·빌드와 같은 범위의 개발/빌드 모드 E2E를 각각 실행한다. 실패·중단·건너뜀·재시도를 성공으로 간주하지 않는다. 검증용 서버는 종료하고 확인용 8787 서버는 켜지 않는다. 검증 결과에 세 참여자가 동의한 뒤 커밋·push, 재사용 자료의 로컬 Git 보존, 임시 파일 정리와 보호 원본의 무결성 확인을 완료한다.
