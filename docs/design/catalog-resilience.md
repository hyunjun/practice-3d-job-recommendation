# Worker 연결 실패 후 추천 유효기간 유지

73단계 설계 1 · 2026-09-30. 이 문서의 SHA-256을 기준으로 세 참여자의 설계 승인을 별도 단계 기록에 남깁니다. 설계 승인과 최종 구현·검증 승인은 별개입니다.

## 문제와 근거

`useCatalog`는 Worker 실패 시 마지막으로 화면에 반영한 결과를 보존합니다. 그러나 이후 `project()`는 실패한 Worker를 사용할 수 없고, 추천 목록의 시간 경과 처리는 Worker 안에서 수행합니다. 열린 화면의 타이머는 계속 동작해도 회사별 24시간 보존 기간을 넘긴 공고가 목록·지도·집계에 남을 수 있습니다. 상세 화면의 별도 유효기간 안내와도 일치하지 않습니다.

현재 E2E는 정상 Worker의 시간 경과와 Worker 실패 후 명시적 재시도를 각각 검사합니다. 실패한 채로 유효기간을 지나는 조합은 확인하지 않습니다. 이 문제는 현재 코드에서 확인한 경로이며, 실행 재현과 수정 후 결과는 독립 검증에서 별도로 기록합니다.

실패 이후 바꾼 프로필·검색 조건에도 이전 추천을 계속 보여주면 비교 화면의 “현재 프로필과 필터 기준” 안내가 사실과 달라집니다. 마지막으로 계산한 조건과 사용자가 새로 요청한 조건을 구분해야 합니다.

## 목표

Worker가 실패하거나 복구 중이어도, 화면에 이미 반영된 추천의 회사별·공고별 유효기간을 지킵니다. 저장한 공고·메모·지원 상태, 입력한 조건과 선택한 도시를 보존하고, 계산하지 못한 조건의 결과 수를 만들어 표시하지 않습니다.

## 결과 보존과 시간 경과

1. 기준은 마지막으로 Worker 세대·요청 검사를 통과해 **화면에 반영된** projection과 당시 프로필·필터·Worker 세대로 고정합니다. 응답 수신, decode·hydrate 완료, 제스처 때문에 보류된 응답은 화면 반영으로 취급하지 않습니다. 보존 중 파생한 결과는 기준을 대체하거나 Worker revision을 acknowledge하지 않습니다. 시간 재평가는 고정된 기준과 현재 wall-clock 시각에서 수행합니다.
2. 기존 `ageCatalog`의 회사별·공고별 규칙을 재사용합니다. 일반 출처의 30분, 일 단위 출처의 24시간 상태 변화를 유지하고, 정확히 24시간은 보존하며 1ms 이후 제외합니다. 알 수 없는 시각과 이전 형식도 같은 규칙으로 해석합니다.
3. 일부 회사만 만료되면 나머지 회사는 계속 표시합니다. 정상 빈 목록과 조건에 맞는 결과 없음은 전체 만료가 아닙니다. 이미 만료된 projection의 `fetchedAt`이 비어 있어도 `expired` 상태를 잃지 않습니다.
4. 메인 스레드는 전역 matches와 기존 도시·원격·기타 근무지 그룹을 유효한 공고 ID와 교차해 갱신하고, 남은 공고의 stale 참조를 사용합니다. 기존 지역·도시 소속을 유지하고 새 요청 필터로 그룹을 다시 만들지 않습니다. 회사 수는 고유 회사 ID 수, 도시 평균은 남은 공고 점수의 산술평균이며 빈 도시는 제거합니다. 도시 정렬은 companyCount 내림차순 → averageScore 내림차순 → city.en.localeCompare 순입니다. 지도 companyIds와 묶음 회사 수는 생존 회사 ID의 집합·합집합으로 계산합니다. 공고 점수·매칭 근거·개별 공고 순서는 그대로 보존합니다.
5. 이 보존 표시 경로에서는 원문 해석, 정규화, 검색 인덱스 생성, 새로운 조건 평가와 점수 계산을 메인 스레드에서 수행하지 않습니다. 마지막 적용 지역 밖 도시나 이전에 추천하지 않던 공고를 추가하지 않습니다. 기존 저장 상세의 별도 프로필 비교를 변경하는 작업은 아닙니다.
6. 같은 원본 projection과 시간 경계에서는 계산 결과를 재사용합니다. 새 검색 입력마다 전체 본문을 다시 처리하지 않습니다. 기존 wall-clock 유효기간 규칙을 따르며 별도의 단조 시계 정책을 도입하지 않습니다.
7. 원래 조회 시각·게시판 조회 성공/실패 이력·원본 projection·저장 기록을 수정하지 않습니다. 유효기간 경과를 새 수집이나 게시판 장애로 기록하지 않습니다.

## 실패와 복구의 수명

1. 보존 모드 진입은 Worker 실패·생성 실패로 계산 경로를 사용할 수 없는 경우에 한정합니다. 기존 Worker가 정상적으로 이전 자료를 계산할 수 있다면 HTTP·응답 검증 실패만으로 검색·미리보기·조건 완화 기능을 차단하지 않습니다. `failedRequestRef`, 오류 문구나 로딩 상태만으로 진입하지 않습니다. Worker가 실패하면 진행 중인 monitor와 보류된 화면 반영을 취소하고, 늦은 응답이 화면을 바꾸지 못하도록 처리합니다. 마지막으로 반영된 결과를 즉시 현재 시각에 맞춰 표시합니다. 만료 처리는 지도 제스처 종료를 기다리지 않습니다.
2. 보존 중임을 명시적으로 관리합니다. `client.failed`, 오류 문구나 로딩 상태 하나만으로 보존 종료를 판단하지 않습니다.
3. 재시도로 새 Worker가 생성되거나 새 응답이 decode됐다는 이유만으로 보존을 끝내지 않습니다. 현재 세대·최신 요청 조건·현재 시간 경계에 맞는 새 projection이 실제 반영되어야 합니다. 시간 정합성은 이전 기준의 deadlines가 아니라 새 projection 자체의 deadlines와 실제 반영 시각으로 확인합니다. 계산 후 반영 전에 경계가 지났다면 Worker 재계산 또는 허용된 시간 경과 파생으로 정합성을 확보한 뒤 보존을 종료합니다.
4. 이미 보존 중인 복구 요청의 생성 실패, 응답·projection 처리 실패, 재시도 중 또 다른 만료 경계에서도 보존 상태를 유지합니다. 복구 Worker의 revision 번호가 다시 1부터 시작해도 이전 Worker의 revision과 혼동하지 않습니다.
5. 현재 유효한 요청의 `CATALOG_EXPIRED`는 이전 기준과 파생 캐시를 무효화하고 명시적인 전체 만료 상태를 표시합니다. 이후 타이머나 취소된 응답이 이전 기준을 복원하지 못합니다. 정상 빈 응답의 의미도 유지합니다.
6. Worker 복구를 위한 무한 재생성이나 자동 수집 루프를 추가하지 않습니다. 시간 경과만으로 네트워크 요청을 시작하지 않습니다. 기존 명시적 재시도·화면 복귀·온라인 복귀·쿨다운 규칙을 유지합니다.

## 요청한 조건과 실제 계산한 조건

1. 프로필·필터가 마지막으로 계산한 값과 같으면 유효기간 안의 기존 추천을 계속 탐색할 수 있습니다. 시간 경과로 파생한 결과는 그 경계의 현재 결과입니다. 로딩 중이 아닌데 시간 key만 달라졌다는 이유로 searching·aria-busy나 “검색 결과를 다시 확인해 주세요”를 표시하지 않고, 실제 남은 공고 수를 표시합니다.
2. 보존 중 프로필 또는 필터가 달라지면 입력 자체는 유지하되, 새 조건에 대한 추천 목록·지도 마커·비교 집계는 **계산할 수 없음**으로 표시합니다. 수치를 0으로 표현하지 않고 `—`를 사용하며, 새 조건을 적용하지 못했다는 안내와 기존 재시도 경로를 제공합니다.
3. 도시·원격·기타 근무지 탭 선택과 도시 비교 선택은 유지합니다. 같은 프로필·필터의 기존 그룹 안에서 이동하는 동작은 허용합니다.
4. 보존 중의 조건 완화 제안은 표시하지 않습니다. 자세한 필터의 미리보기는 계산 불가로 처리하고, 임의의 0건 또는 다른 Worker 세대의 결과로 적용 버튼을 활성화하지 않습니다. 보존 기준을 만든 Worker와 다른 복구 Worker에 기준의 revision으로 preview를 요청하지 않습니다.
5. 로딩·시간 경과·보존 갱신만으로 현재 input key를 이전 결과에 붙여 새 조건이 적용됐다고 표시하지 않습니다.
6. 회사별 조회 기록·공개 데이터 안내와 저장 공고의 상세·검색·메모·지원 상태는 계속 사용할 수 있습니다.

계산 불가 안내의 제목은 **“새 조건의 추천을 확인하지 못했어요”**, 설명은 **“입력한 조건과 선택한 도시는 유지됩니다. 다시 조회한 뒤 추천을 확인해 주세요.”**로 합니다. 복구 요청이 진행 중이면 제목은 **“새 조건의 추천을 준비하고 있어요”**로 표시합니다. 기존 수집 상태 영역의 재조회 경로를 사용합니다. 추천 회사·도시 수와 각 탐색 탭의 수치는 `—`이며, 이전 회사 목록·마커·비교표를 새 조건의 결과로 표시하지 않습니다.

## 화면 복귀와 저장한 기록

화면이 숨겨져 타이머가 실행되지 않았더라도 복귀 시 실제 시각으로 다시 판단합니다. 재조회가 쿨다운에 막히거나 응답을 기다리거나 실패해도 먼저 유효기간을 적용합니다. 이미 열어 둔 공고의 원문·메모·지원 상태는 유지하고 상세의 유효기간 안내를 갱신합니다. 저장 화면만 여는 경우의 수집 지연 시작 정책과 개인정보 비전송 원칙을 유지합니다.

## 구현 범위

작은 projection 보존·시간 경과 유틸리티, `useCatalog`, 필요한 `App`·`CityPanel` 결과 안내에 한정합니다. 집계의 중복 구현을 피하기 위한 기존 집계 함수의 작은 타입·공통 처리 조정은 검토할 수 있습니다. Worker 프로토콜, 제공자 수집·재시도 정책, 저장 형식과 분류 규칙은 변경 대상이 아닙니다.

독립 조사에서 네 후보를 확인했습니다. Fable의 최초 권고는 서버 Gap1의 실패·재시도 정보 누락을 먼저 수정하는 것이었습니다. 주 담당과 Astra는 표시된 추천의 유효기간·적용 조건 정확성을 우선했습니다. Fable은 별도 Worker 독립 검토와 논의 후, 이 설계의 범위를 유지하고 서버 Gap1을 광범위한 재조사 없이 다음 단계로 진행하는 조건으로 Worker 우선 순서에 동의했습니다. 최종 문서 해시에 대한 승인은 별도로 받습니다.

서버 Gap1은 게시 목록 확인의 실패 대기 때문에 본문 수집을 건너뛴 회사가 카탈로그에서 정상/데이터 미확인으로 표시되고, 실패 사유·재시도 시각이 빠지는 문제입니다. 해당 회사의 `lastSuccessAt: null`을 화면이 다른 회사의 카탈로그 시각으로 대신할 수 있다는 추가 경계도 포함합니다. 서버 Gap2는 본문·게시 목록 수집이 서로 기다리면서 첫 진행 응답도 지연되는 경로입니다. 현재 기본 회사 수는 130개이며 최초 조사 메모의 106개는 정정합니다. 실제 대기 시간·시간 초과 발생률은 측정하지 않았습니다. 의도된 외부 수집 직렬화는 후속 설계에서도 보존해야 합니다.

“연속된 stale 경계에서 이미 전송한 본문을 다시 보내는 현상”도 별도 확장성 후보입니다. 이 세 후속 후보의 근거·원래 권고와 수정 의견을 보존하며, 이번 Worker 유효기간 보장의 성공 조건을 대신하지 않습니다.

## 논의 후 반영한 세부 조건

Fable은 처음에는 가장 이른 만료 시각 이후 전체 추천을 미확인으로 숨기는 안을 제안했습니다. 논의 후 현재 선별·점수·정렬 규칙에서 생존 부분집합의 결과가 정확히 유지됨을 독립 확인하고 이 안을 철회했습니다. 이 의견 변경과 다음 조건을 원래 제안과 함께 보존합니다. Worker 실패의 실제 발생 빈도나 후보 간 상대 발생률은 측정하지 않았습니다.

파생 결과의 정확성은 현재 검색·매칭이 공고별 조건과 프로필로 결정되고, 전체 카탈로그의 상대 통계나 시각·stale 값에 따라 점수·선별 기준이 달라지지 않는다는 전제에 근거합니다. 카탈로그 백분위나 IDF 같은 상대 지표를 나중에 추가한다면 이 전제를 다시 설계해야 합니다. 명시적인 기대값과 별도로 정상 Worker의 동일 시각 결과를 대조하는 회귀 검사를 두어 이 전제가 깨지는 변경을 확인합니다.

생존한 Match의 facts를 재계산하지 않고 job 참조만 ID로 교체합니다. 공고 참조가 같으면 기존 MatchedJob도 재사용합니다.

Worker 실패 시 연결이 끊긴 progress는 지웁니다. 현재 오류가 로컬 Worker 실패인 경우 수동 재조회 버튼을 보존 기준의 catalog.refreshAfter만으로 막지 않습니다. 요청을 받은 서버는 기존 회사별 수집 주기를 계속 적용합니다. 현재 reload의 비정상 HTTP 응답에서 받은 CatalogRequestError.retryAt는 기존대로 지키고, 이전 reload의 오류 시각을 새 요청에 상속하지 않습니다. 오류 없는 오래된 자료 안내와 명시적인 오류 retryAt가 없는 HTTP 오류에서는 기존 refreshAfter fallback을 유지합니다. 진행 조회의 Retry-After 간격 처리도 유지하며, 새로운 헤더 전용 오류 파서를 추가하는 작업은 아닙니다. 알려진 현재 reload의 HTTP 오류 재시도 시각은 그 뒤 발생한 로컬 Worker 오류만으로 지우지 않습니다. 예를 들어 정상 자료 표시 → HTTP 재조회 실패와 미래 retryAt 수신 → Worker 실패 순서에서도 해당 시각까지 수동 재조회가 잠깁니다. 새 reload가 실제 시작할 때는 기존대로 이전 오류 상태를 초기화합니다. 요청이 진행 중이면 중복 재조회 동작을 허용하지 않습니다.

자동 화면 복귀 재조회는 기존 기준을 유지합니다. 따라서 일 단위 출처만 설정한 경우 catalog.refreshAfter 때문에 자동 복구가 늦을 수 있으며, 이때 수동 재조회로 Worker를 복구할 수 있다는 한계를 기록합니다.

## 독립 검증의 필수 기대값

- 단위 검사: 회사·공고 시각이 다른 자료의 정상→stale→일부 만료→전체 만료, 정확히 24시간과 +1ms, 정상 빈 목록·결과 0건·이미 만료된 상태, 원격·기타 근무지·여러 도시에 걸친 회사의 실제 개수, 남은 순서·매칭 근거·원본 불변. 만료 후 도시 순위 변경과 동점 정렬, 한 공고의 다른 도시가 적용 지역 밖인 경우, 같은 기준의 반복 파생과 wall-clock 역방향 재평가도 확인합니다.
- 1440px·320px E2E: 실제 앱의 Worker 실패 후 경계 통과, 여러 회사의 순차 제외와 전체 만료, 열린 저장 상세의 메모·지원 상태와 개인 조건 보존.
- 실제 지도 제스처 동안 더 최신 응답이 보류된 상태의 실패: 마지막 표시 결과만 기준으로 삼고, 만료는 즉시 반영하며 보류한 응답이 뒤늦게 나타나지 않음.
- 검색·프로필·빠른 필터 변경: 입력·선택을 보존하고 새 조건의 결과는 미확인으로 표시. 미리보기·조건 완화 제안·비교 화면에 이전 값을 새 결과처럼 표시하지 않음.
- 복귀 시 타이머를 건너뛴 시각 확인, 실패하거나 오래 걸리는 재시도, Worker 생성 실패와 복구 중 만료, 마지막 정상 복구의 최신 조건·세대·시각 일치. 이전 기준에 다음 deadline이 없어도 새 응답이 자기 만료 경계를 지나는 경우와, 복구 중 명시적인 `CATALOG_EXPIRED`가 이전 기준을 무효화하는 경우를 포함합니다.
- 정상 Worker에서 HTTP·응답 검증 실패 후에도 기존 검색·미리보기·조건 완화가 동작하는 대조 검사를 유지합니다.
- 각 stale·만료 경계에서 파생 결과와 정상 Worker 결과의 ID·순서·집계·마커 회사 집합·게시판 상태·stale 값을 대조합니다. 공고 한 개를 단독·전체 카탈로그·stale 변경 상태에서 비교해 선별과 점수가 같은지도 확인합니다. 이 대조는 명시적인 기대값 검사를 보완하며 대체하지 않습니다.
- 두 검색 요청 중 먼저 받은 응답이 hydrate됐지만 최신 요청 검사에서 탈락한 뒤 실패해도, 기준은 실제 표시된 projection입니다.
- 조건이 같은 부분 만료 이후 실제 남은 수·비교표를 표시하고 aria-busy는 false입니다. 다른 Worker가 복구 중일 때 preview에 이전 기준의 revision을 보내지 않습니다.
- 먼 미래의 refreshAfter가 있는 정상 기준에서 Worker만 실패하면 수동 재조회가 즉시 가능하고 progress는 사라집니다. 그 재조회가 서버의 명시적 retryAt를 포함한 HTTP 오류로 끝나면 해당 시각까지 버튼이 잠깁니다.
- 같은 경계의 파생 결과 객체를 재사용하고, 경계 사이의 검색 입력이 보존 자료 전체를 재계산하지 않음을 확인합니다.
- 먼저 HTTP 오류의 미래 retryAt를 받은 뒤 Worker가 실패해도 대기를 유지하며, 시각이 지나면 버튼만 활성화되고 자동 요청은 발생하지 않습니다. 실패 전 pending 게시판은 진행 정보가 끊긴 상태로 유지하고, 새로 성공·실패한 것으로 만들어 표시하지 않습니다.
- 시간 경과·조건 수정이 추가 수집 요청을 만들지 않으며, 저장 화면과 공개 조회에 개인 메모·프로필·저장 ID를 전송하지 않음.
- 최종 소스 기준 타입·전체 단위 검사·빌드와 영향받는 개발/배포 E2E. 정확한 파일·명령·예상 범위는 테스트 담당이 제안하고 세 참여자가 실행 전에 승인합니다.

기대값은 가상 자료에 명시한 ID·개수·시각·표시 문구로 작성합니다. 제품 함수로 정답을 재계산하지 않습니다. 실제 브라우저 Worker 이벤트를 통제한 검사와 운영체제 자체의 Worker 충돌 재현은 구분해 보고합니다.
