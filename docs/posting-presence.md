# 공개 게시 목록과 본문 확인

저장 화면의 게시 확인은 회사별 공개 ID 목록을 확인합니다. 공고 본문을 비교하려면 **공고 내용 확인**을 실행합니다. 두 작업 모두 서버에 등록된 전체 게시판을 대상으로 하며 저장한 ID·메모·지원 기록·프로필을 받지 않습니다.

## 요청과 시각

| 요청 | 수집 | 저장한 기록 |
|---|---|---|
| `GET /api/posting-status?refresh=1` | 회사별 전체 공개 목록 | 브라우저에서 게시 여부 판정 |
| `GET /api/posting-status?refresh=1&content=1` | 전체 목록과 탐색 대상 본문 | 브라우저에서 표시 내용 비교 |
| 공개 카탈로그 갱신 | 전체 목록과 탐색 대상 본문 | 저장 원문은 유지 |

새 서버의 게시 상태 응답은 `version: 2`입니다. 이전 `version: 1` 응답도 브라우저에서 읽습니다. 기존 수집기만 제공하는 `createCatalogService` 호출은 v1 계약을 유지하며, 앱의 실제 서버는 네 제공자 모두 목록 전용 수집기를 등록합니다.

- `boards[].lastSuccessAt` / `listing.validUntil`: 전체 게시 목록의 마지막 정상 확인 시각과 유효 기간.
- `listing.content.checkedAt` / `validUntil`: 본문을 정상 수집한 시각과 별도 유효 기간. 본문 갱신에 실패하면 `content.status: "error"`로 남깁니다.
- `refreshAfter` / `contentRefreshAfter`: 목록과 본문을 각각 다시 요청할 수 있는 가장 이른 시각. 현재 시각보다 이전일 수 있습니다.
- `listing.jobs`: 아직 유효한 본문 요약만 포함합니다. 현재 공개 ID 목록에 없거나 게시 상태가 충돌하는 ID는 제외합니다.
- `listing.content.jobIds`: 마지막 본문 스냅샷에 실제로 남아 있는 공고 ID. 이 목록에도 본문 요약에도 없는 공고에는 게시판의 조회 시각을 개별 본문 확인 시각으로 표시하지 않습니다.

정상 목록과 본문의 유효 기간은 각각 30분입니다. 목록만 새로 확인해도 본문의 시각·유효 기간은 연장하지 않습니다. 저장한 공고의 조회 시각보다 오래된 본문, 만료되거나 실패한 본문으로는 내용이 같거나 달라졌다고 판정하지 않습니다. 화면의 본문 유효 기간이 지나면 추가 네트워크 요청 없이 비교 표시를 해제합니다. CSV의 기존 열 뒤에 **공고 내용 확인 시각**을 추가하고, JSON 백업의 저장 원문과 개인 기록은 유지합니다.

## 수집 비용

| 제공자 | 게시 목록 확인 |
|---|---|
| Greenhouse | `content=false` 목록 한 번. 보상 상세 요청 제외 |
| Ashby | 공개 피드 한 번, `isListed` 적용. 본문 정규화·보상 조회 제외 |
| Lever | 모든 50개 단위 페이지. 본문 정규화 제외 |
| SmartRecruiters | 모든 100개 단위 PUBLIC 목록 페이지. 공고별 상세 요청 없음 |

Ashby·Lever의 목록 응답에는 제공자 특성상 본문이 포함될 수 있습니다. 모든 제공자의 전송량이 ID만큼 작아진다는 의미는 아닙니다. SmartRecruiters는 본문 수집과 목록 확인이 동일한 요청 큐를 사용합니다. 기존 동시 4개·요청 시작 간격 200ms·429 및 Retry-After 대기를 공유합니다.

목록과 본문은 별도 30분 캐시와 수동 조회 최소 1분 간격을 사용합니다. 같은 종류의 진행 중인 수집은 공유하고, 두 종류의 전체 수집은 겹쳐 실행하지 않습니다. 어느 경로의 회사 조회가 실패하더라도 다른 버튼으로 해당 회사의 재시도 대기를 우회할 수 없습니다. 전체 본문을 정상 수집하면 그 시각의 목록 캐시도 함께 갱신합니다.

설정 범위가 넓으면 요청 수는 회사 수와 페이지 수에 비례합니다. 사용자마다 공고 URL에 접근하거나 매 화면 이동마다 외부 API를 호출하지 않습니다. 분산된 여러 서버 사이의 잠금·공유 큐는 제공하지 않으므로 여러 프로세스로 운영하려면 별도 조정이 필요합니다.

저장 화면을 바로 열거나 그 화면에서 창 초점·네트워크가 돌아와도 공개 카탈로그의 자동 수집을 시작하지 않습니다. 탐색·도시 비교로 돌아가면 기존 유효 기간과 재시도 규칙에 따라 조회합니다. 직접 시작한 수집과 데이터 모드 변경은 계속 사용할 수 있습니다.

## 판단과 실패

전체 목록의 페이지 수·총수·ID 중복·회사·공개 상태를 검증한 다음 결과를 반영합니다. 중간 페이지 실패나 429는 정상 빈 목록으로 처리하지 않습니다. 실패 전 정상 목록은 보관하되 게시 상태는 확인 필요로 안내합니다.

공개 목록에 ID가 없다는 사실은 채용 종료 확정과 다릅니다. 현재 목록의 게시 여부도 지원 가능성·채용 완료 여부를 보장하지 않습니다. 원문 링크와 확인 시각을 함께 제공합니다.

SmartRecruiters 상세 응답이 명시적으로 비활성·내부 게시라고 알려준 ID는 별도로 보관합니다. 이후 목록 전용 확인에서 같은 ID가 다시 보여도 활성화로 단정하지 않고 **확인 필요**로 안내합니다. 정상 본문 확인에서 게시 상태를 다시 확인해야 비교를 재개합니다.

본문 요청 전체의 연결 실패는 아직 유효한 목록 확인 결과를 없애지 않습니다. 회사별 본문 실패도 목록과 별도로 표시하며, 비교할 수 있는 새 본문이 없으면 **내용 미확인**입니다. 탐색 범위 밖이거나 이번 목록에서 처음 발견한 공고에도 본문 미확인을 안내합니다.

본문 갱신 중이라도 **목록 자체의 검증이 실패했다면** 게시 상태 역시 확인 필요로 표시합니다. 목록 확인 실패와 상세·본문 실패를 구분해 보존하므로, 전체 갱신 후 목록이 불완전해졌는데도 이전의 게시 확인을 성공으로 유지하지 않습니다. 실패 단계가 없는 이전 캐시도 보수적으로 확인 필요로 처리합니다.

## 로컬 저장

본문 캐시 경로가 `.local/public-board-cache-v5.json`이면 목록 캐시는 `.local/public-board-cache-v5.presence-v1.json`입니다. 사용자 설정별 캐시도 해당 경로에서 파생하므로 회사·제공자·게시판·Lever 지역을 다시 확인합니다.

처음에는 기존 본문 캐시의 완전한 공개 ID 목록을 **원래 확인 시각 그대로** 재사용합니다. 목록만 확인하면 본문 캐시를 쓰지 않습니다. 목록 캐시는 임시 파일과 원자적 이름 변경으로 저장하고 실패·재시도·상태 충돌도 서버 재시작 후 유지합니다. 실제 수집 자료와 실행 로그는 Git에서 제외되는 `.local/`에 보관합니다.
