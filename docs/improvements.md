# ORBIT 개선 기록

개선별로 확인한 문제, 참고 자료, 반영한 동작과 검증을 기록합니다. 원본 이력서와 공개 공고 전체 응답은 이 문서나 저장소에 포함하지 않습니다.

## 01 · 채용 조건과 원문 근거 — 2026-09-19

### 확인한 문제

- Datadog의 `Time Type: Full time`과 Anthropic의 `Location Type: On-Site`가 기존 필드 목록에서 누락되어 있었습니다.
- 직무·지원자에 따라 제한되는 비자 지원 정책이 모두 미확인으로 분류되어, 지원 문구가 있는 공고를 따로 찾기 어려웠습니다.
- Cloudflare의 수출 통제 안내에 있는 `without sponsorship for an export license`가 취업 비자 미지원으로 오분류되었습니다.
- `Full time`을 정규직으로 표시해 근무 시간과 계약 형태를 혼동할 수 있었습니다.
- 화면의 판별 결과에서 실제 근거 문장으로 연결되는 경로가 없었습니다.

### 반영한 동작

- 알려진 공고별 메타데이터를 우선하고, 필요한 경우 해당 직무를 직접 설명하는 문장만 사용합니다. 일반적인 회사 복지, 유연근무 소개, `2-Flexible`처럼 뜻이 명확하지 않은 내부 값은 추정에 사용하지 않습니다.
- 비자 조건을 지원 명시·조건부·지원 없음·미확인으로 분리했습니다. 기존의 조건부 제외 필터를 유지하면서 조건부 포함 선택지를 추가했습니다. 서로 상충하는 문구는 지원 가능으로 단정하지 않습니다.
- 수출 허가 스폰서십을 취업 비자 정책에서 제외했습니다.
- 비자·근무·고용 형태의 근거 문구와 출처 종류를 공고 상세에서 펼쳐 볼 수 있습니다. 저장한 공고에도 근거가 함께 보존되며, 예전에 저장한 공고도 계속 읽을 수 있습니다.
- 풀타임·파트타임·계약직·인턴·임시직을 구분합니다. 풀타임을 정규직 계약으로 단정하지 않습니다.
- 데이터 화면에 조건별 확인 건수를 추가했습니다.
- 모바일의 조건 입력란을 한 열로 배치해 비자 지원 필터의 조건부 포함·제외 문구가 잘리지 않도록 했습니다.
- 조건 추출을 `server/job-facts.ts`로 분리해 다른 채용 게시판 수집기에서도 재사용할 수 있게 했습니다.
- Greenhouse 급여 범위의 공식 필드명인 `currency_type`을 읽도록 보완했습니다.

### 실제 데이터 확인

2026-09-19 03:56 UTC에 조회한 10개 게시판의 동일한 응답으로 이전 동작과 개선 동작을 대조했습니다. 이후 04:08 UTC에 앱의 실제 API에서도 10개 게시판이 모두 정상 조회되는 것을 확인했습니다.

| 항목 | 이전 | 개선 후 |
| --- | ---: | ---: |
| 지도·원격 탐색에 포함된 개발 공고 | 707 | 708 |
| 조건부 비자 지원으로 분류 | 0 | 182 |
| 비자 미지원으로 분류 | 115 | 0 |
| 근무 형태 미확인 | 427 | 290 |
| 고용 형태 미확인 | 633 | 560 |

추가된 1개 공고는 공고별 원격 메타데이터를 읽게 되면서 도시 좌표가 없어도 원격 탐색에 포함된 경우입니다. 비자 미지원 115개는 수출 허가 문구에 의한 오분류였으며, 개선 후에는 비자 미확인으로 남깁니다. 수치는 이 시점의 수집 범위와 분류 결과이며 채용 시장 전체 규모나 분류 정확도를 뜻하지 않습니다.

### 참고 자료

- [Greenhouse Job Board API](https://developers.greenhouse.io/job-board.html): 공개 조회, `content=true`, 공고별 `metadata`·`offices`, 급여 범위의 `currency_type`을 확인했습니다.
- [Ashby Public Job Posting API](https://developers.ashbyhq.com/docs/public-job-posting-api): `workplaceType`, `employmentType`, `secondaryLocations`, 보상 항목별 통화·기간 구조를 확인했습니다.
- [Lever Postings API](https://github.com/lever/postings-api): `categories.commitment`, `workplaceType`, `salaryRange.interval`을 확인했습니다.

이번 개선에서 실제 수집에 연결한 소스는 기존 Greenhouse 게시판입니다. Ashby와 Lever는 수집 범위를 확장할 때 사용할 구조화된 정보와 공통 데이터 계약을 검토한 자료입니다.

### 검증

- 단위 검사: 조건부·부정·상충 문구, 수출 허가와 취업 비자의 구분, 게시판 메타데이터의 우선순위, 일반 회사 소개의 오인 방지, 계약 형태, 급여 필드, 비자 필터.
- 브라우저 검사: 조건부 포함·제외 선택, 원문 근거 펼치기, 공고 저장 후 새로고침, 저장된 근거 복원, 접근성.
- 단위 검사 38개, 기존 브라우저 시나리오 11개와 새 시나리오 1개가 통과했습니다. 실제 공개 공고를 사용한 배포 빌드에서도 데스크톱·모바일의 근거 표시, 가로 넘침과 브라우저 오류를 확인했습니다.

### 이어서 확인할 항목

- 공개 데이터 모드, 검색 조건과 선택 도시의 재방문 복원 → 개선 02에 반영.
- 회사별 조회 실패 시 이전 데이터를 보존하는 수집 구조 → 개선 03에 반영. 공고 변경·마감 이력은 별도 확인 항목입니다.
- Ashby·Lever 수집기와 도시·회사 범위의 다양성 → 개선 04에서 7개 회사 추가. 제공 도시 확장은 별도 확인 항목입니다.
- 원격 근무지의 `CAN` 같은 국가 코드와 구조화된 지역 정보 정규화 → 개선 04에 반영. 국가별 지원 가능 여부가 불명확한 지역은 계속 미확인으로 남깁니다.
- 경력 차이, 필수·우대 기술, 시민권·취업 허가 조건을 반영한 추천 집계와 평가용 공고 집합.

## 02 · 마지막 탐색 복원과 조회 상태 구분 — 2026-09-19

### 확인한 문제

브라우저에서 공개 공고 → 런던 검색 → 도시 선택 → 2D 지도로 전환한 뒤 새로고침했습니다. 공개 모드는 샘플로 돌아왔고 검색어·선택 도시·지도 보기까지 초기화되었습니다. 저장한 프로필의 기본 희망 조건 외에는 탐색을 이어갈 수 없었습니다.

프로필의 기억하기를 꺼도 편집 화면을 다시 열면 체크가 켜지는 문제도 있었습니다. 탐색 상태 저장을 추가하면서 이 선택을 무시하면 저장하지 않기로 한 희망 조건이 별도 저장 항목에 남을 수 있습니다.

### 반영한 동작

- 데이터 모드, 검색어와 모든 필터, 선택 도시와 도시·원격 탭, 지도 유형·주야간 보기, 도시 정렬을 복원합니다. 기존 프로필만 있는 경우에는 이전의 희망 조건을 사용하며, 사용자가 필터를 명시적으로 초기화한 뒤에는 그 초기화 결과를 우선합니다.
- 공개 모드로 다시 방문하면 실제 공고를 재조회합니다. 첫 응답 전에는 회사·도시 수를 `—`로 표시하고, 지도와 목록에 샘플 공고를 끼워 넣지 않습니다. 성공적으로 조회한 결과가 0개인 경우와 조회하지 못한 상태를 구분합니다.
- 연결 실패 시 공개 모드와 탐색 조건을 보존하고 재시도를 제공합니다. 조회 중에도 샘플로 전환할 수 있고, 취소한 요청의 늦은 응답이 화면을 되돌리지 않도록 합니다. 화면에 이미 있는 결과를 갱신할 때는 이전 결과를 보고 있음을 알립니다.
- 연결·저장 실패 알림은 성공 체크 대신 별도의 아이콘과 색으로 표시합니다.
- 자동 복원과 첫 조회의 재시도는 화면 안의 상태 안내를 사용합니다. 중복 알림이 모바일의 재시도 버튼을 덮지 않으며, 조회 상태 변화도 스크린리더에 전달합니다.
- 프로필 기억하기를 끄면 현재 화면의 개인 탐색 조건은 유지하지만 저장하지 않습니다. 이전에 저장한 조건은 지우며, 프로필을 다시 열었을 때도 꺼 둔 선택을 유지합니다. 프로필 삭제도 같은 조건 정리를 수행합니다.
- 데이터 모드와 표시 설정은 프로필과 별도로 유지하고, 저장한 공고·메모·도시 비교는 그대로 보존합니다. 이력서 원문이나 조회한 공고 전체를 탐색 상태에 저장하지 않고, 검색 조건을 URL이나 서버 요청에 넣지 않습니다.
- 저장 데이터의 필드를 검증하고 잘못된 옵션·사라진 도시·선택 지역 밖 도시를 복구합니다. 브라우저의 저장소 접근이 차단되어도 탐색은 계속 동작합니다.
- 공개 공고 조회와 취소 처리를 `src/hooks/useCatalog.ts`로 분리했습니다.

### 참고 자료와 판단

- [MDN localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage): 브라우저 재방문 시 유지되며 같은 출처에 한정됩니다. 브라우저 정책에 따른 `SecurityError` 가능성을 고려해 읽기와 쓰기 실패를 처리합니다.
- [MDN sessionStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage): 탭 세션에 한정되어도 새로고침 시에는 유지됩니다. “이번 화면에만 적용”한 프로필과 조건을 별도 세션 저장으로 우회 보관하지 않습니다.
- [React useEffect](https://react.dev/reference/react/useEffect): 조회 요청의 정리 함수와 개발 모드의 추가 실행을 고려해 오래된 응답과 취소를 처리합니다.

새로 방문한 화면에서 상태를 읽는 방식입니다. 여러 탭에서의 실시간 동기화나 다른 브라우저·기기와의 공유는 포함하지 않습니다.

### 검증

- 기존 프로필과 새 탐색 상태의 우선순위, 필드별 오류 복구, 프로필 저장 해제·삭제, 저장소 차단을 단위 검사로 확인했습니다. 전체 단위 검사 45개가 통과했습니다.
- 기존 브라우저 시나리오 12개와 신규 시나리오 5개가 통과했습니다. 신규 5개는 배포 빌드에서도 확인했습니다. 실제 UI 조작 후 새로고침·새 탭 재방문, 공개 모드의 조회 실패·재시도·빈 결과·요청 취소, 기억하기 선택과 저장 내용, 접근성을 검증했습니다.
- 실제 API의 공개 공고 708개로 데스크톱·모바일의 런던 선택·검색어·2D 보기 복원을 확인했습니다. 원격 탭 복원도 브라우저에서 확인했습니다. 모바일의 390px·320px 너비에서 연결 실패 화면의 가로 넘침과 실행 오류가 없으며, 재시도 버튼을 바로 누를 수 있음을 확인했습니다.

## 03 · 회사별 공고 보존과 조회 상태 — 2026-09-19

### 확인한 문제

기존 수집기는 일부 회사의 조회가 실패해도 성공한 회사의 결과만으로 전체 캐시를 덮어썼습니다. 04:08 UTC의 실제 캐시를 복사해 Stripe만 HTTP 503으로 실패하고 나머지는 정상적인 빈 목록을 반환하도록 재현했습니다. Stripe의 기존 공고 92개가 사라졌고 전체 결과는 최신으로 표시되었습니다.

전체 조회가 실패하고 캐시도 없으면 반복 요청을 막지 못했습니다. 서버를 다시 시작하면 재시도 간격도 초기화되었습니다. 이전 결과의 유효기간 상한과 회사별 마지막 정상 확인 시각을 화면에서 구분할 수 없었습니다.

### 반영한 동작

- 회사별 마지막 정상 결과와 마지막 조회 시도를 분리했습니다. 일부 조회가 실패하면 해당 회사의 기존 공고만 보존하며 공고의 원래 확인 시각을 바꾸지 않습니다. 정상적인 빈 목록은 기존 공고를 제거하고, 이후 실패가 발생해도 제거된 공고를 되살리지 않습니다.
- 정상 결과는 30분 사용하며 수동 재조회는 게시판별 최소 1분 간격을 둡니다. 실패 시 기본 1분부터 지수적으로 간격을 늘리고 임의 지연을 더하되 30분 이내로 제한합니다. 공급자의 `Retry-After`가 더 늦으면 그 시각을 지킵니다.
- 캐시가 전혀 없는 실패도 기록하며 재시도 대기 시간을 디스크에 보존합니다. 동시 요청은 한 수집 작업을 공유하고 게시판 조회는 최대 4개씩 실행합니다. 완료된 작업의 자리를 다음 게시판이 바로 사용합니다.
- 마지막 정상 확인 후 24시간을 넘긴 결과는 다음 조회에서 추천 대상에서 제외합니다. 모든 결과가 만료된 경우에는 API가 이를 구분해 알리고, 브라우저에 남아 있던 이전 추천도 지웁니다. 저장한 공고는 사용자가 보관한 기록으로 유지합니다.
- 데이터 화면에 최근 조회·이전 조회 공고 수와 미확인 게시판 수를 표시했습니다. 회사별 정상 확인·실패·재시도 시각을 펼쳐 볼 수 있고, 문제가 있으면 조회 기록이 먼저 열립니다. 대기 중인 재조회 버튼은 비활성화되며 시간이 지나면 새로고침 없이 다시 사용할 수 있습니다.
- 일부 게시판의 실패 안내를 탐색·비교 화면에도 유지했습니다. 이전 공고는 목록·상세·저장 화면에서 구분하고, 도시 비교에는 이전 공고가 몇 개 포함되었는지 표시합니다.
- 게시판 조회, 수집 정책, 디스크 저장을 분리했습니다. 저장 파일과 정규화한 공고를 검증하고 임시 파일을 원자적으로 교체합니다. 이전 버전 캐시는 정상 결과를 회사별로 이전하되, 복구할 수 없는 회사별 지도 제외 건수는 미확인으로 남깁니다. 새 캐시가 손상되어도 더 오래된 캐시로 되돌아가 제거된 공고를 복원하지 않습니다.

### 참고 자료와 판단

- [MDN Retry-After](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Retry-After): 대기 시간(초)과 HTTP 날짜 형식을 모두 처리합니다.
- [RFC 5861, stale-if-error](https://www.rfc-editor.org/rfc/rfc5861.html#section-4): 실패 시 이전 결과를 제한된 기간 동안 사용하되, 오래된 결과임을 숨기지 않고 유효기간을 계속 연장하지 않는 원칙을 참고했습니다.

30분·최소 1분·최대 24시간은 이 로컬 앱에 정한 정책이며 외부 API의 보장이나 RFC의 지정값이 아닙니다. HTTP 캐시 확장을 구현한 것은 아니며 앱 API는 계속 `Cache-Control: no-store`를 사용합니다. 조회와 재시도는 사용자의 요청에 따라 실행하며 상시 백그라운드 수집은 하지 않습니다.

## 04 · Ashby·Lever 수집과 출처별 조건 보존 — 2026-09-19

### 확인한 문제

- Ashby에는 목록에서 제외해야 하는 `isListed: false`, 기본·추가 근무지, 구조화된 근무·고용 형태, 여러 보상 구간이 있습니다. Lever는 페이지를 나눠 반환합니다. 게시판 응답을 그대로 하나의 목록이나 급여 범위로 취급하면 일부 공고가 누락되거나 조건이 합쳐질 수 있습니다.

## 07 · 저장한 공고의 현재 게시 여부와 내용 비교 — 2026-09-19

### 확인한 문제

- 저장 목록은 저장 당시 공고·메모·지원 상태만 보여주어, 나중에 다시 볼 때 현재 공개 게시 여부와 내용 차이를 확인하기 어려웠습니다.
- 기존 카탈로그는 직무·도시 필터를 통과한 공고만 보관했습니다. 이 목록에서 빠졌다는 사실만으로 공개 게시가 종료됐다고 판단하면, 직무나 근무지 해석이 달라진 공고까지 종료로 오인할 수 있습니다.
- 게시판 조회 실패, 오래된 캐시, 정상 조회의 빈 목록도 의미가 다릅니다. 전체 공개 목록의 근거 없이 같은 상태로 표시하면 저장한 지원 기록을 잘못 정리하게 할 수 있습니다.

### 반영한 동작

- Greenhouse·Ashby·Lever에서 직무·근무지 필터 전 전체 공개 ID를 확보합니다. Ashby의 목록 비공개 공고는 제외하고, Greenhouse의 제공된 전체 건수를 검증하며, Lever는 모든 페이지 조회가 성공했을 때만 반영합니다.
- 저장 목록에 **게시 상태 확인**, 확인 시각, 게시 여부·내용 차이의 집계와 필터를 추가했습니다. 포지션·근무지·근무/고용/비자·보상·기술/경력·본문·지원 링크 중 저장 내용과 다른 항목을 표시하며 현재 원문으로 연결합니다.
- **게시 확인**, **공개 목록에서 미확인**, **현재 상태 확인 필요**, **미조회**를 구분합니다. 조회 실패, 30분을 지난 확인, 전체 공개 ID가 없는 이전 캐시, 다른 게시판·출처·Lever 지역, 저장 공고보다 이전에 조회한 목록으로는 게시 종료나 현재 게시 여부를 단정하지 않습니다.
- 정상 응답이 빈 목록이면 목록에서 미확인으로 표시하지만, 이후 조회가 실패하면 확인 필요로 바뀝니다. 이전 공고를 되살리거나 저장한 기록을 삭제하지 않습니다.
- 서버의 고정된 공개 게시판 목록을 받아 브라우저에서 비교합니다. 저장 ID·메모·프로필을 전송하지 않고, 저장 공고·저장일·메모·지원 상태·탐색 모드·필터를 그대로 유지합니다.

- 게시 상태는 현재 화면에서만 유지합니다. 열어 둔 화면에서도 확인 근거가 30분을 지나면 확인 필요로 바뀌며, 재방문 시 다시 확인합니다. CSV의 지원 상태와 공개 게시 상태를 분리하고 확인 시각·내용 일치/차이/미확인·달라진 항목을 함께 남깁니다.

## 08 · 비자 지원 범위와 추가 취업 자격 구분 — 2026-09-19

### 확인한 문제

- n8n의 개발 공고 6개에는 “독일에는 비자를 지원할 수 있지만 다른 국가에서는 기존 취업 권한이 필요하다”는 문구가 있었습니다. 기존 해석은 이를 일반적인 **비자 지원 명시**로 분류해 국가별 제한이 있는 공고까지 조건부 제외 필터에 포함했습니다.
- 원격근무 국가와 프로필의 거주 국가가 일치하면 “원격 지원이 가능하다”고 표시했습니다. 그러나 실제 공고에는 시민권, 취업 허가, 주별 거주 제한이나 보안 인가 등의 별도 조건이 있어 지리적 일치만으로 지원 자격을 확인할 수 없습니다.
- Anthropic의 `Staff+ Software Engineer, Public Sector` 공고는 시민권 확인을 필수로 명시하면서 보안 인가는 우대 항목에 적었습니다. 시민권의 증명 방법으로 정부 보안 인가를 예시한 문장도 있어, 관련 단어가 등장했다는 이유만으로 모든 보안 인가를 필수로 취급하면 안 됩니다.
- Cloudflare의 수출 허가 스폰서십과 취업 비자, 수출 통제의 `U.S. person`과 미국 시민권도 서로 구분해야 합니다.

### 반영한 동작

- 특정 국가·직무·지원자 범위에 한정된 비자 지원을 **조건부 지원**으로 표시합니다. “조건부 제외” 필터에서는 제외하며 조건부 포함 탐색에서는 원문과 함께 확인할 수 있습니다. 지도에 등록되지 않은 국가나 도시의 범위도 버리지 않습니다.
- 취업 자격을 비자 지원 적용 범위·기존 취업 허가·국적과 시민권·거주 요건·보안 인가·수출 통제로 구분했습니다. 각 문구에 **필수로 명시·적용 조건 확인·우대 사항·원문 확인**과 원문 근거를 남깁니다.
- 공고 상세에 **취업 자격과 추가 조건**을 추가했습니다. 같은 문구에서 확인한 조건은 묶어 펼쳐 볼 수 있고, 목록·저장 카드와 추천 설명에서도 별도 조건을 확인하도록 안내합니다.
- 우대 보안 인가, 보유하거나 취득할 수 있다는 선택 경로, 시민권의 증명 수단을 구분합니다. 차별 금지 문구, 개인정보 수집 목록, 소프트웨어 비유와 질문 문장은 취업 자격으로 사용하지 않습니다. 취업 비자와 수출 허가가 같은 문단에 있어도 문장별로 구분합니다.
- 원격근무 관련 설명과 필터를 **명시된 근무 지역과 거주 국가의 비교**로 바꾸었습니다. 거주 국가를 국적·취업 허가로 간주하지 않고 추가 개인정보를 입력받지 않습니다. 이러한 조건으로 추천 점수를 조정하거나 지원자를 자동 제외하지 않습니다.
- 세 수집기가 같은 해석을 사용합니다. 이전 캐시와 저장 기록은 보관한 본문·비자 근거로 다시 확인하고 공고 ID·원래 조회 시각·저장일·메모·지원 상태를 유지합니다. 취업 자격 정보도 저장 내용 비교에 포함하며 CSV 끝에 비자 지원·자격 조건·원문 근거를 추가합니다.
- 데이터 화면에 취업 자격 원문을 찾은 공고 수를 표시합니다. 원문을 찾지 못한 경우가 제한 없는 조건을 뜻하지 않음을 함께 안내합니다.

## 09 · 빈 검색 결과의 조건별 미리보기와 탐색 복구 — 2026-09-19

### 확인한 문제

- 빈 결과에서는 “조건 조정”이나 “검색 조건 초기화”만 제공했습니다. 사용자는 어떤 조건을 바꾸면 후보가 생기는지 알기 어렵고, 전체 초기화로 필요한 비자·연봉 조건까지 지울 수 있었습니다.
- 현재 도시에는 결과가 없어도 다른 도시나 원격 탭에는 같은 조건의 공고가 있을 수 있습니다. 이 경로를 빈 결과에서 직접 안내하지 않았습니다.
- “모든 개발 직무”에서는 입력 기술과 자격 기술이 전혀 겹치지 않는 공고를 제외합니다. 따라서 직무 필터를 지우는 것이 항상 결과를 늘리는 것은 아니며, 이 규칙을 무시한 미리보기는 잘못된 수치를 만들 수 있습니다.
- 원격근무 국가 제한을 해제한 뒤에도 거주 국가만 표시하면, 다른 국가나 지역 미확인 공고까지 해당 국가에서 근무 가능한 것으로 오인할 수 있었습니다.

### 반영한 동작

- 빈 결과에서 **같은 조건의 다른 도시·원격 기회**를 먼저 안내합니다. 이 경로를 선택할 때 검색 조건과 프로필을 바꾸지 않습니다.
- 현재 공고에서 실제 후보가 생기는 **최대 3개의 조건 변경안**을 계산합니다. 각 변경 전·후 값과 적용 후 회사·공고 수를 표시하고, 여러 조건을 함께 바꿔야 하는 경우도 변경 항목을 모두 공개합니다.
- 같은 결과를 찾는 데 불필요한 추가 변경은 제안하지 않습니다. 예를 들어 조건부 비자 지원을 포함해 후보가 생기면 미확인이나 지원 없음까지 넓히는 동일한 변경안은 생략합니다. 자동으로 조건을 완화하지 않습니다.
- 비자 미확인·지원 없음, 거주 국가 범위 밖·지역 미확인, 연봉 미공개·별도 보상을 포함하는 변경의 의미를 설명합니다. 거주 국가를 바꾸거나 취업 권한을 추정하지 않으며, 원격 범위를 넓힌 상태는 결과 화면·필터 수·재방문에도 남깁니다.
- 선택한 도시나 원격 탭을 유지한 채 표시한 필드만 변경합니다. 실행 취소를 제공하고, 이후 사용자가 직접 수정한 값은 덮어쓰지 않습니다. 키보드로 적용하면 결과 영역에 포커스를 두고 상태 알림을 제공합니다.
- 기술 불일치로 제외된 공고는 프로필 확인을 안내합니다. 조회 대기·조회 실패에는 조건 변경안을 표시하지 않으며, 수집 범위에 공고가 없으면 수치를 만들어내지 않습니다.
- 검색 결과와 미리보기가 같은 필터 판정을 사용합니다. 검색어 대상·기술 일치·근무지·보상 비교 정보를 카탈로그와 프로필이 바뀔 때 준비하고, 공고별로 실패한 조건에서 변경안을 도출합니다. 모든 필터 조합을 전수 탐색하거나 미리보기마다 추천 설명을 다시 계산하지 않습니다.

## 13 · 공개 응답 압축과 변경 없는 데이터의 재검증 — 2026-09-19

### 확인한 문제

- 실제 공개 공고 960개를 담은 카탈로그 JSON이 **8,801,050바이트**였고, 압축 없이 전송됐습니다. 공고 본문·자격·분류 근거가 늘면서 데이터 전송량도 커졌습니다.
- 공개 카탈로그와 게시 상태는 `no-store`여서 같은 응답도 브라우저가 다시 받아야 했습니다. 서버의 게시판별 수집 캐시는 외부 조회를 줄여도 브라우저로 보내는 본문까지 줄이지는 못했습니다.
- 단순히 오래 캐시하면 변경된 공고, 정상 빈 목록, 조회 실패와 24시간 보존 한도가 반영되지 않을 수 있었습니다. 저장한 공고의 게시 상태도 원래 목록의 유효 기간을 유지해야 했습니다.

### 반영한 동작

- Express의 `compression` 미들웨어로 API와 배포용 정적 응답을 압축합니다. 브라우저의 `Accept-Encoding`을 따르고 1KB 임계값, Brotli 품질 4, gzip 수준 6을 사용합니다. 개발 서버에서는 API에 적용하고 Vite의 모듈 갱신은 유지합니다.
- 공개 카탈로그와 게시 상태의 정상 응답에 **`private, no-cache, must-revalidate`**를 적용합니다. 브라우저가 저장할 수 있지만 다시 사용할 때 서버 검증이 필요합니다. 샘플·실패·잘못된 API 요청은 `no-store`입니다.
- 조건부 요청도 **수집 서비스를 먼저 호출**합니다. 기존 수집 주기·수동 갱신 제한·실패·재시도·만료 정책을 적용한 결과를 ETag로 비교하고, 같으면 본문 없는 `304`를 반환합니다.
- 정상 조회로 확인 시각이 바뀌거나 공고·게시 상태가 바뀌면 새 본문을 보냅니다. 빈 목록과 오류를 이전 성공 응답으로 대신하지 않으며, `304` 때문에 공고 조회 시각이나 게시 상태의 유효 기간을 연장하지 않습니다.
- 압축 형식에 따라 캐시를 구분하도록 `Vary: Accept-Encoding`을 비압축·압축·`HEAD`·`304`에 유지합니다. 브라우저의 기본 `fetch`는 재검증에 성공하면 저장된 본문을 애플리케이션에 제공합니다.
- 서버가 보내는 공개 데이터의 범위는 유지했습니다. 프로필·검색 조건·선택하거나 저장한 공고 ID를 보내는 요청은 추가하지 않았습니다.
- HTTP 라우터를 `server/http.ts`로 분리해 실제 소켓을 사용하는 검사를 추가했습니다. 브라우저 캐시 검사에는 요청 가로채기를 사용하지 않습니다. Playwright의 라우팅은 HTTP 캐시를 비활성화하기 때문입니다.

- HTTP 재검증은 요청이 발생했을 때의 동작입니다. 페이지의 뒤로 가기 복원이나 장시간 열린 화면의 자동 갱신을 추가한 것은 아니며, 기존의 명시적인 공개 조회와 게시 상태 확인 흐름을 유지합니다.

## 14 · 열린 화면의 조회 기간과 실제 게시 상태 재검증 — 2026-09-19

### 확인한 문제

- 서버는 오래된 공고를 구분했지만, 탐색 화면은 응답을 받은 뒤 시간이 지나도 상태를 바꾸지 않았습니다. 브라우저 내부에서 **24시간 31분이 지난 시각**을 모사하고 복원 이벤트를 발생시켜도 공고가 추천에 남았고 데이터 화면은 **최근 조회 1개**로 표시했습니다.
- 열려 있는 상세와 저장 기록도 저장 당시의 `stale` 값만 확인했습니다. 시간이 흐른 사실과 실제 게시판 조회 실패를 구분할 필요가 있었습니다.
- 13차의 HTTP 응답 정책과 달리, 실제 게시 상태 버튼에는 요청의 `cache: 'no-store'` 옵션이 남아 있었습니다. 같은 내용을 다시 확인하는 실제 UI 검사에서 응답이 **200 → 200**으로 전송돼 서버의 조건부 재검증을 활용하지 못했습니다.

### 반영한 동작

- 서버와 브라우저가 **30분의 최근 조회 기간·24시간의 보존 한도**를 공유합니다. 원래 수집한 데이터는 유지하고 화면에 사용할 상태와 공고 목록을 별도로 계산합니다.
- 정상 확인 후 30분이 지나면 목록·상세·저장·도시 비교에 이전 조회임을 표시합니다. 시간 경과만으로 게시판 조회 실패를 만들지 않습니다.
- 회사별 마지막 정상 기록이 24시간을 넘기면 해당 공고를 회사 수·지도·검색·도시 비교에서 제외합니다. 더 최근인 다른 회사와 정상 빈 목록은 계속 사용합니다. 모두 만료되면 필터 때문에 결과가 없는 것처럼 보이지 않도록 재조회를 안내합니다.
- 다음 상태 변경 시각에 타이머를 예약합니다. 숨겨진 화면에서는 타이머를 멈추고, 다시 표시되거나 포커스·뒤로 가기 복원 이벤트가 발생하면 현재 시각으로 재평가합니다. 복원 이벤트만으로 외부 공고를 조회하지 않습니다.
- 같은 확인 기간 안에서 화면에 돌아온 경우 검색 인덱스를 다시 만들지 않습니다. 저장 공고마다 개별 타이머를 만들지 않고 공통 시계를 사용합니다.
- 열려 있는 상세와 저장 목록도 원래 조회 시각으로 안내를 바꿉니다. 저장한 공고·메모·지원 상태를 삭제하거나 새 공고로 덮어쓰지 않으며, 확인 기간 경과를 모집 종료로 표현하지 않습니다.
- CSV에 **저장 내용의 조회 시각·내보낼 당시 조회 기록의 상태·내보낸 시각**을 추가했습니다. 지원 상태와 공개 게시 여부는 계속 별도 열에 유지합니다.
- 회사별 원래 정상 확인·실패·재시도 기록을 보존합니다. 이전 캐시에 내용 없이 개수만 있는 지도 미연결 공고는, 일부 회사가 만료되어 소속을 구분할 수 없으면 수치를 추정하지 않고 미확인으로 표시합니다.
- 게시 상태 요청의 `no-store` 옵션을 제거했습니다. 실제 버튼도 서버 검증을 거쳐 HTTP 캐시를 사용하며, `304`가 와도 원래 게시 목록의 유효 기간을 늘리지 않습니다. 오류 응답은 계속 저장하지 않습니다.

### 참고 자료와 판단

- [Chrome Page Lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api?hl=en)의 정지·복원 상태와 [MDN pageshow](https://developer.mozilla.org/en-US/docs/Web/API/Window/pageshow_event)·[visibilitychange](https://developer.mozilla.org/en-US/docs/Web/API/Document/visibilitychange_event)를 확인했습니다. 복원된 화면은 초기 조회 효과를 다시 실행한다고 가정할 수 없습니다.
- [MDN setTimeout](https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout)의 백그라운드 지연을 참고해 실제 시각을 다시 비교합니다. 타이머가 정확한 시점에 항상 실행된다는 가정에 의존하지 않습니다.
- [MDN Request.cache](https://developer.mozilla.org/en-US/docs/Web/API/Request/cache)를 확인하고, 서버 헤더 검사와 실제 버튼의 요청 동작을 함께 검증하도록 보완했습니다.

### 검증

- 타입 검사와 전체 단위 검사 **253개 통과**, 배포용 빌드 성공. 정확히 30분·24시간인 경계, 회사별 부분 만료, 정상 빈 목록, 실제 오류의 재시도 시각, 기존 기록의 날짜·개수·원본 보존을 확인했습니다.
- 최종 배포용 서버의 브라우저 시나리오 **67개 통과**. 열려 있는 상세의 시간 경과, 저장·메모·지원 상태·CSV 보존, 지도·회사 수·비교 반영, 재조회 복구, 타이머 없이 시각을 이동한 뒤의 복원 처리, 320px 접근성을 확인했습니다.
- 실제 UI의 게시 상태 검사는 수정 전 **200 → 200**, 수정 후 **200 → 304**를 확인했습니다. 재방문 자체는 게시 상태를 자동 조회하지 않으며, 유효 기간이 지나면 확인 필요로 바뀌고 실패 시 이전 성공 상태를 재사용하지 않았습니다.
- 별도 Chrome 검증에서 실제 뒤로 가기로 페이지가 메모리 캐시에서 복원됐습니다(`pageshow.persisted: true`). 브라우저 내부에서 25시간이 지난 시각을 모사한 상태에서 추가 카탈로그 요청 없이 이전 추천을 제거했습니다.
- 실제 17개 게시판·960개 공고의 보관 응답으로 **1440px·320px** 목록·상세·게시판 기록을 확인했습니다. 시간 이동 후 화면에서 추천 제외와 저장 기록 보존을 확인했고, 가로 넘침·실행 오류·자동 WCAG A/AA 검사 위반이 없었습니다. 이 과정의 카탈로그 요청은 화면별 최초 1회였으며 실제 공고·화면 캡처는 로컬에만 보관합니다.

### 이어서 확인할 항목

- 화면의 기간 계산은 기기 시각을 사용하며 모집 종료 여부를 판정하지 않습니다. 현재 채용 상태는 명시적으로 다시 조회하거나 원문에서 확인해야 합니다.

## 15 · 아시아·호주 공고 수급과 SmartRecruiters — 2026-09-19

## 20 · 저장 기록 백업·복원과 원본 정리 — 2026-09-20

### 확인한 문제

브라우저 저장소를 바꾸거나 사이트 데이터를 지웠을 때 공고·메모를 되돌릴 방법이 없었습니다. CSV는 열람할 수 있지만 전체 공고 스냅샷을 복원하는 형식이 아니었고, 오류가 있는 이전 목록의 복구 원본도 다운로드만 가능했습니다. 원본 전체에 이미 삭제한 공고의 메모가 남아 있어 보관 범위를 확인하고 정리할 필요도 있었습니다.

MDN의 File API·파일 선택 안내와 WHATWG의 Web storage 동시 접근 규칙을 확인했습니다. 파일의 확장자만 믿지 않고 내용을 검증하며, 다른 탭의 최신 기록을 덮어쓰지 않도록 검토와 반영을 나누었습니다.

### 반영한 내용

- 저장 화면에 **기록 백업·복원**을 추가했습니다. JSON 백업은 현재 목록의 공고·메모·지원 상태·저장일과 저장하지 못한 최신 입력을 포함합니다. 프로필·이력서·탐색 조건과 별도의 복구 원본은 포함하지 않습니다.
- 버전 1 백업, 이전 버전의 복구 JSON, 이전 저장 배열을 읽습니다. 파일 크기 50MiB·검토 항목 5,000개를 제한하고 각 공고와 회사 ID를 검증합니다. 잘못된 항목과 서로 다른 중복은 숨기지 않고 검토 결과에 표시합니다.
- 기존 기록은 기본적으로 유지합니다. 메모·지원 상태·공고 내용의 차이를 확인한 뒤 대체할 공고와 중복 후보를 선택할 수 있습니다. 미리보기는 20개씩 표시하고 분류·페이지 이동을 제공합니다.
- 반영 직전에 선택한 각 공고가 검토 당시와 같은지, 새 ID가 여전히 비어 있는지, 읽을 수 없는 항목을 포함해 500개 한도 안인지 확인합니다. 한 IndexedDB 트랜잭션으로 반영하며 도중 실패하면 전체 선택을 취소합니다. 다른 탭이 기록을 바꾸면 다시 비교하게 합니다.
- 새 공고의 파일 순서와 기존 공고의 목록 위치를 유지합니다. 원래 조회·저장 시각을 보존하고 파일이나 저장 내용을 서버에 보내지 않습니다. 커밋 후 재조회만 실패한 경우에는 저장 성공과 재연결 필요를 구분해 안내합니다.
- 복구 원본을 보관 위치별로 내려받고 삭제 범위를 확인한 뒤 정리할 수 있습니다. 현재 정상 공고·다른 보관본·이전 완료 표시는 유지합니다. 삭제 전에 원본이 바뀌었거나 정상 기록으로 복구되었다면 삭제하지 않습니다.
- localStorage에 남은 이전 사본은 이미 이전한 내용과 같아도 표시합니다. 이전 버전 탭과의 잠금은 보장할 수 없으므로 사본을 정리하기 전에 해당 탭을 닫도록 안내합니다.

## 26 · 모바일 터치 영역과 가려지지 않는 목록 탐색 — 2026-09-20

### 확인한 문제

실제 보관 공고를 320px·390px 화면에서 열었을 때 도시 비교 버튼 22개가 20×20px이었고, 도시를 여는 버튼 위에 겹쳐 있었습니다. 기존 검사에 WCAG 2.2의 대상 크기 기준을 추가하자 두 화면에서 각각 22개의 위반이 확인됐습니다.

320px 화면에서는 키보드로 이동한 Wise 공고 제목이 하단 메뉴에 완전히 가려졌습니다. 좌표상 화면 안에 있으므로 기존의 뷰포트 포함 검사로는 찾을 수 없었습니다. 고정된 필터 안내도 목록 위를 덮었고, 공고 제목·조건과 작은 조작 버튼은 모바일에서 읽고 누르기 어려웠습니다.

### 반영한 내용

- 도시 비교 버튼은 기본 24px, 모바일에서는 **44×44px**로 확대했습니다. 회사 수와 버튼이 겹치지 않도록 도시 행의 여백도 조정했습니다.
- 모바일 공고 제목·저장·페이지 이동·목록 펼치기·상세 닫기 등 주요 조작 영역을 넓혔습니다. 공고 제목은 **16px**, 직무·근무·비자 등 목록 설명은 **12px**로 키웠습니다.
- 모바일의 필터 안내를 검색 도구 아래에 배치했습니다. 적용 범위가 길어도 문구 전체를 줄바꿈해 읽을 수 있고, 공고를 덮지 않습니다. 초기화한 뒤에는 사라진 버튼 대신 검색 입력에 포커스를 돌려줍니다.
- 문서의 스크롤 여백에 하단 메뉴 높이를 반영했습니다. 기기의 하단 안전 영역도 메뉴 높이·문서 여백·스크롤 여백에 함께 적용해 버튼을 누를 공간과 포커스의 표시 공간을 유지합니다.
- 키보드로 실제 Tab 이동을 하면서 포커스된 요소의 여러 지점이 다른 요소에 가려지지 않는지 확인하는 회귀 검사를 추가했습니다. 터치 버튼 가장자리를 눌러도 의도한 비교·저장이 실행되는지 함께 검증합니다.

### 실제 자료와 검증

- 320×568, 390×844, 667×375 화면과 390×844의 하단 안전 영역 34px 조건에서 새 브라우저 검사 **4개가 통과**했습니다. 도시 비교, 회사의 모든 페이지 이동, 저장, 메모·지원 상태 수정, 상세 닫기, 필터 초기화와 재방문을 연결해 확인했습니다.
- 각 시나리오에서 도시를 잘못 열지 않고 비교에 추가했으며, 마지막 페이지에서 누른 공고 ID가 실제 저장 기록과 일치했습니다. 메모·지원 상태·원래 공고 조회 시각이 보존됐고 검색어·프로필·개별 공고 ID·메모가 API 요청으로 전송되지 않았습니다.
- 보관 공고 **1,320개**로 모바일·가로 화면·데스크톱을 확인했습니다. Wise의 조건부 지원 공고 4개, Canva의 Sydney 공고 **40개·4페이지**, 긴 필터 적용 범위를 사용했습니다. 수정 전 확인한 비교 버튼 위반과 완전히 가려진 포커스가 사라졌고, 실제 자료의 16개 화면에서 자동 WCAG 2.2 A/AA 위반이 없었습니다.
- 모바일 3D 지구에서도 필터 안내가 나타난 뒤 런던 핀을 터치해 실제 Wise 공고를 열고, 초기화 후 22개 도시와 검색 포커스를 복원했습니다. 이 화면도 같은 접근성 검사를 통과했고 실행 오류가 없었습니다. 화면 이미지를 직접 확인해 버튼·글자·줄바꿈과 안전 영역의 배치를 점검했습니다.
- 타입 검사·배포용 빌드 성공, 단위 검사 **427개**, 전체 브라우저 검사 **110개 통과**. 모바일 회귀 검사에서는 문서와 회사 카드의 가로 넘침도 확인했습니다.

W3C의 대상 크기·포커스 가림 기준, MDN의 안전 영역, GOV.UK의 글자 크기 스케일을 [레퍼런스](references.md)에 정리했습니다. 브라우저 검증은 Chrome에서 수행했고 하단 안전 영역은 34px로 에뮬레이션했습니다. 실제 공고와 화면 자료는 로컬에 보관하고 공개 저장소에는 가상 공고를 사용하는 회귀 검사를 포함합니다.

## 27 · 지도 밖 국가의 원격근무 공고 탐색 — 2026-09-20

### 확인한 문제

원격근무의 국가 해석과 지역 검색이 지도에 등록한 국가·도시 목록에 의존했습니다. 보관된 실제 공고에는 `Poland`, `New Zealand`, `Brazil`, `Italy`, `Israel`이 명시돼 있었지만 국가가 누락됐고, 프로필에서도 해당 국가를 선택할 수 없었습니다.

같은 1,320개 공고를 국가 조건으로 검색하면 GitLab의 폴란드 10개, Canva의 뉴질랜드 4개, Airbnb의 브라질 3개, Datadog의 이탈리아 2개, GitLab의 이스라엘 6개를 찾지 못했습니다. 폴란드·뉴질랜드 공고는 국가를 알더라도 지도 도시에 해당 국가가 없어 지역 필터에서 빠질 수 있는 구조였습니다.

### 반영한 내용

- 국가 식별표를 지도 도시와 분리하고 프로필에서 **250개 국가·지역**을 선택하도록 확장했습니다. UN M49와 Unicode CLDR의 코드 대응을 참고하며 한국어 이름은 `Intl.DisplayNames`로 표시합니다.
- 공고의 국가명, 별칭과 구조화된 국가 코드가 같은 식별자를 사용합니다. 지역 검색도 국가 코드로 조회하므로 지도에 없는 폴란드·뉴질랜드 등의 원격 공고를 찾을 수 있습니다. 한국어 국가명 검색도 지원합니다.
- 국가명 안에 다른 이름이 포함된 경우를 구분합니다. `North Korea`를 대한민국으로, `New Jersey`를 저지섬으로, 호주의 `SA`를 사우디아라비아로 해석하지 않습니다. 실제 n8n 응답의 `Georgia`는 미국 주소여서 조지아 국가로 추가하지 않습니다.
- `Europe`·`EMEA`·`APAC`·`AMER` 자체로 국가별 근무 허용을 추정하지 않습니다. 공고에 표시된 국가 코드와 구조화된 국가 필드가 일치하는 경우는 활용하고, 사무실 주소나 광역 위치만 있는 경우의 불확실성은 유지합니다.
- 이전 캐시·검색·저장 기록도 보관된 위치와 국가 정보로 재해석합니다. 국가만 있는 구조화된 정보도 유지하며, 조회 시각·게시 ID·메모·지원 상태·다른 공고 조건을 보존합니다. 같은 위치 정보를 재해석할 수 있는 이전 공고와 새 공고는 게시 내용 비교에서도 같은 결과를 사용합니다.
- 상세와 CSV가 같은 한국어 국가 설명을 사용합니다. 상세의 국가 목록과 추가 확인 설명은 글자를 키우고 국가명을 읽기 쉽게 줄바꿈합니다. CSV에 원격 국가명·국가 코드·추가 확인 사항을 포함하고, JSON 백업·복원도 보완된 국가 정보를 유지합니다.

### 실제 자료와 검증

- 동일한 보관 자료에서 **29개 공고의 국가 정보가 보완**됐습니다. 원격 공고 238개 중 국가 미확인은 **36개에서 20개**로 줄었습니다. 나머지 공고의 국가 해석과 전체 공고 수는 유지됐습니다.
- 위 국가별 검색은 각각 **10·4·3·2·6개**를 모두 찾았습니다. 기술·경력 조건을 적용하기 전의 수이며 국가가 겹치는 공고가 있어 단순 합계를 전체 공고 수로 사용하지 않습니다.
- 이전 커밋의 코드와 비교해 기존 **16개 거주 국가의 기본 검색 결과**, 전체 1,320개 공고의 추천 점수와 국가 외 필드가 같음을 확인했습니다. 현재 기준으로 계산한 이전·보완 공고의 게시 내용 비교도 모두 일치했습니다.
- 22개 게시판의 캐시를 다시 읽어 전체 공개 ID·원래 조회·실패·재시도 기록·지도 미연결 수를 확인했습니다. 보관 카탈로그의 국가 해석은 약 103ms, 캐시 전체 검증·변환은 약 55ms였으며 한 번의 로컬 측정입니다.
- 새로 조회한 GitLab·Airbnb·Datadog·Canva의 공고 4개와 n8n 원격 공고 6개의 국가 해석이 보관 자료의 재해석 결과와 일치했습니다. 공개 GET 5회로 응답을 확인했고 원본 응답은 로컬에 보관합니다.
- 1440px·320px의 새 브라우저 시나리오가 국가 선택 → 공고 확인 → 기존 저장 기록·새 메모 → 게시 내용 비교 → CSV·JSON → 재방문을 통과했습니다. 국가·검색어·프로필·메모는 API 요청으로 보내지 않았습니다.
- 실제 공고를 사용하는 **1440px·320px의 2D와 390px의 3D**, 총 **18개 화면**에서 실행 오류·가로 넘침·자동 WCAG 2.2 A/AA 위반이 없었습니다. 이 확인에서는 기존 샘플의 기술을 가진 프로필을 사용해 GitLab 8개·n8n 4개·Airbnb 1개·Canva 2개가 조건에 맞았고, 국가를 바꾼 뒤에도 저장한 공고의 국가·조회 시각·메모·지원 상태가 유지됐습니다.
- 타입 검사·배포용 빌드 성공, 단위 검사 **440개**, 전체 브라우저 검사 **112개 통과**. 브라우저 검증은 Chrome에서 수행했습니다.

국가 표와 파싱·검색·보존 규칙의 회귀 검사를 추가했습니다. 국가 이름과 지리 구분의 출처, CLDR 고지 원문은 [레퍼런스](references.md)와 [출처 고지](attributions.md)에 기록했습니다. 실제 공고·API 응답·검증 화면은 로컬에 보관하고 공개 저장소의 검사는 가상 공고를 사용합니다.

## 28 · 미입력 경력과 소수 연수의 정확한 비교 — 2026-09-20

### 확인한 문제

경력 연수가 없는 이력서를 분석하면 경고와 함께 **3년을 자동 입력**했습니다. 사용자가 이 값을 수정하지 않고 진행하면 공고의 경력 조건과 실제로 비교했습니다. 또한 `3.5 years of experience`와 `0.5년 경력`의 소수점 뒤 숫자만 읽어 **5년**으로 처리했고, 입력란에서 소수를 직접 입력해도 정수로 반올림했습니다.

개인정보가 없는 가상 경력 텍스트와 보관된 실제 공고 1,320개로 재현했습니다. 기술·근무 조건에 맞는 결과 899개 중 100개에 근거 없는 `입력 경력 3년` 설명이 붙었습니다. 이는 동일한 보관 자료와 가상 프로필의 비교이며 전체 채용 시장에 대한 수치가 아닙니다.

### 반영한 내용

- 확인하지 못한 개인 경력은 **미입력**으로 유지합니다. 입력란을 지워도 0으로 바꾸지 않으며, 연수가 없어도 기술·직무·희망 조건으로 계속 탐색할 수 있습니다.
- 미입력 경력은 추천 점수와 경력 충족·부족 설명에 사용하지 않습니다. 상세에서 아직 비교하지 않은 조건임을 안내합니다. 사용자가 직접 입력한 0년은 경력 조건과 비교합니다.
- 소수, 한국어의 `경력 7년`, 명시된 연·월 기간을 읽습니다. 날짜·기간 범위·서로 다른 기술 경력을 임의로 합산하지 않으며, 명시적인 전체 경력을 우선합니다. 숫자의 일부만 읽지 않도록 소수점·범위·기호의 경계를 확인합니다.
- 0~50년 안의 소수를 직접 입력하고 수정할 수 있습니다. 잘못된 값은 작성한 상태로 남기고, 입력란에 연결한 오류와 포커스로 수정 위치를 안내합니다.
- 모바일에서는 이름과 경력 입력을 한 줄씩 배치하고 숫자·도움말·오류 글자를 키워, 소수 입력과 설명을 읽기 쉽게 정리했습니다.
- 경력의 미입력·0·소수 값은 프로필과 희망 조건을 함께 보존해 재방문 시 복원합니다. 경력을 바꿔도 저장한 공고의 메모·지원 상태·원래 조회 시각은 유지합니다.

## 29 · 개발·배포 환경의 공고 조회 검사 — 2026-09-20

### 확인한 문제

화면 복귀 시 공고 만료를 확인하는 검사에서 실패를 재현했습니다. 추적 기록의 두 요청은 **`net::ERR_ABORTED` 한 건과 HTTP 200 완료 한 건**이었습니다. 이전 배포용 서버의 검사 결과만으로는 기본 개발 검사 명령의 이 문제를 확인할 수 없었습니다.

추가 검증에서는 `.local`에 생성한 Playwright 추적 HTML을 개발 서버가 감지해 검사 도중 화면을 새로고침하는 문제도 확인했습니다. 서버의 `full-reload` 메시지와 브라우저의 탐색 원인을 함께 기록해 원인을 확인했습니다.

### 반영한 내용

- 실제 `/api/health`로 서버 모드를 확인하고 요청 시작·응답·완료·실패를 구분합니다. 초기 조회는 HTTP 200·202 완료 한 건이어야 하며, 개발 환경에서만 그 앞의 취소 한 건을 허용합니다. 중복 완료·다른 실패·대기 중인 추가 요청은 계속 검사 실패입니다.
- 공고 만료·화면 복귀·회사 페이지 이동·수집 재연결·거주 국가 변경 검사를 보완했습니다. 검증한 초기 요청 이후의 조회 횟수를 정확히 비교하고, 사용자가 다시 조회하면 한 건만 추가되는지 확인합니다.
- 취소된 요청도 URL·메서드·본문 검사에 포함합니다. 검색 조건·프로필·메모를 보내지 않는 기존 검사를 유지합니다.
- 취소된 초기 응답을 현재 결과가 도착한 뒤 전달하는 회귀 검사를 추가했습니다. 기존 샘플 전환·재방문 검사에는 대기 중인 초기 요청이 실제로 취소되는지 확인하는 조건을 추가했습니다.
- `.local`의 로컬 자료와 `playwright-report`의 HTML 보고서를 개발 서버 감시에서 제외했습니다. 기존의 `test-results` 기본 제외와 함께 생성 자료로 인한 예상치 못한 새로고침을 방지합니다.
- README에 개발 검사와 배포용 서버를 먼저 실행하는 검사 절차, 서버 모드 확인·종료 방법을 안내했습니다.

- 회귀 검사에는 회사 소개의 기술과 실제 자격 조건을 구분하는 이전 공고를 추가했습니다. 기존 검색 자료에는 현재 형식의 자격 근거를 명시하고, 이전 형식은 별도 자료로 확인합니다.

## 32 · 잘못된 공개 응답에서도 유지되는 탐색 화면 — 2026-09-20

## 33 · 공고가 늘어도 가볍게 조작하는 검색·필터 — 2026-09-20

### 확인한 문제

검색어를 바꿀 때마다 같은 공고의 추천 점수·설명을 다시 계산했습니다. ‘모든 필터’ 창은 예상 공고 수만 표시하면서 검색 인덱스 생성과 추천 정렬까지 반복했습니다. 실제 공고 1,320건과 이를 10배로 복제한 자료로 계산 단계와 브라우저 입력 지연을 측정해 병목을 확인했습니다.

### 반영한 내용

- 공고와 프로필이 같은 동안 검색 항목별 추천 결과를 재사용합니다. 처음 결과에 포함되는 공고만 계산하므로 좁은 검색으로 시작할 때 전체 공고의 점수를 미리 계산하지 않습니다.
- 매번 현재 검색어·필터로 대상 공고를 선택하고, 기존과 같은 기준으로 새 배열을 정렬합니다. 공고를 새로 받거나 프로필을 바꾸면 검색 인덱스와 추천 계산을 새로 시작합니다. 같은 ID의 공고라도 변경된 내용·회사 정보가 반영됩니다.
- 필터 초안의 예상 개수는 화면과 같은 검색 인덱스로 조건만 판정합니다. 적용·취소·초기화 동작과 검색어 유지 방식은 그대로입니다.
- 계산 재사용 범위는 현재 공고·프로필에 한정합니다. 검색어별 결과나 개인 프로필을 전역 캐시·서버·브라우저 저장소에 추가로 보관하지 않습니다.

### 브라우저 측정

배포 빌드에서 기본 샘플 프로필과 초기 필터로 공개 공고가 표시된 뒤 검색어 `engineer`를 세 번 입력하고, 연봉 슬라이더를 두 차례 조작했습니다. 조건별 검색 입력 24회·슬라이더 입력 20회의 중앙값입니다.

| 공고 수 | CPU 감속 | 검색 갱신 전 → 후 | 연봉 슬라이더 갱신 전 → 후 |
| --- | --- | --- | --- |
| 실제 1,320건 | 없음 | 33 → 28ms | 32 → 26ms |
| 실제 1,320건 | 6배 | 127 → 73ms | 151 → 30ms |
| 10배 복제 13,200건 | 없음 | 125 → 47ms | 208 → 25ms |
| 10배 복제 13,200건 | 6배 | 698 → 236ms | 1,262 → 45ms |

Chrome 153, 1440×960 화면에서 `input` 이벤트부터 두 번째 `requestAnimationFrame`까지 측정했습니다. 가장 큰 부하 조건의 95백분위는 검색 **811 → 320ms**, 슬라이더 **1,400 → 47ms**였습니다. 슬라이더 측정 구간에서 관찰된 50ms 초과 작업은 모든 변경 후 조건에서 0건이었습니다.

Node의 계산 단계에서도 실제 공고의 반복 검색·집계가 약 **12 → 1ms**, 10배 자료에서는 약 **110 → 10ms**로 줄었습니다. 처음 추천을 계산하는 비용은 계속 발생합니다. 13,200건은 브라우저 부하를 비교하기 위한 복제 자료이며 실제 수집 규모나 서버 용량이 아닙니다. 위 값은 로컬 실험 결과이고 현장 INP 수치가 아닙니다. 가장 큰 부하의 검색에는 여전히 계산·렌더링 비용이 남아 있습니다.

### 검증

- 보관된 실제 공고 1,320건으로 세 프로필·72가지 검색·필터 조합을 이전 커밋과 비교했습니다. 결과 순서·점수·기술 일치·추천 설명이 모두 같았고 원본 공고 내용도 유지됐습니다.
- 1,320건과 13,200건의 반복 검색 70회에서도 전체 추천 결과가 이전 코드와 같았습니다. 필터 예상 개수와 처음 좁은 검색으로 시작한 결과도 비교했습니다.
- 새 회귀 검사는 검색 범위 확대·축소, 결과 배열 순서 변경의 독립성, 프로필 변경, 같은 ID의 공고·회사 갱신을 다룹니다. 1440px·320px 브라우저에서는 필터 초안 취소·적용·초기화와 추천 순서·설명 갱신을 확인하고 저장한 메모·지원 상태·저장 당시 공고를 보존했습니다.
- 실제 공고로 1440px·320px의 2D와 390px의 3D에서 필터 미리보기·적용·검색 변경을 확인했습니다. 6개 화면을 점검했고 실행 오류·가로 넘침·자동 WCAG 2.2 A/AA 위반이 없었습니다. 이 화면 검증의 API 요청 3회는 공개 카탈로그 GET이며 검색어·프로필·메모를 포함하지 않았습니다.
- 타입 검사·배포용 빌드 성공, 단위 검사 **586개**, 개발 서버와 배포용 로컬 서버의 전체 브라우저 검사 **각 128개 통과**.

## 34 · 화면 크기에 맞는 2D 지도 조작과 갱신 속도 — 2026-09-20

### 확인한 문제

2D 지도의 도시 버튼은 SVG 안에서 크기를 유지했지만 화면 전체가 축소되는 비율을 반영하지 않았습니다. 320px 화면에서 버튼 폭은 약 **12px**, 숫자는 약 **4px**였고 지도를 확대해도 커지지 않았습니다. 드래그는 너비만으로 좌표를 환산해, 높이에 맞춰 지도가 표시되는 2560×720 화면에서는 포인터를 100px 움직여도 지도가 약 **42px**만 이동했습니다.

검색어를 바꾸거나 지도를 이동할 때마다 바다·경위도선·국가 경계의 투영도 다시 계산했습니다. 이전 검색 최적화 이후의 배포 빌드를 기준으로 CPU 프로파일과 입력 지연을 측정해 이 반복 작업을 확인했습니다.

### 반영한 내용

- 도시 버튼의 조작 영역을 **44×44 CSS px**, 숫자와 도시 이름을 **12px**로 유지합니다. 지도 컨테이너의 크기를 관찰해 창 크기 변경과 전체 화면 전환에도 반영합니다.

### 브라우저 측정

Chrome 153의 배포 빌드, 기본 샘플 프로필과 보관된 공개 공고 1,320건을 사용했습니다. 검색은 1440×960에서 `engineer`를 세 번 입력한 24회, 지도 이동은 각 화면에서 방향키를 20회 누른 결과입니다. 다음은 **CPU 6배 감속** 조건의 중앙값과 95백분위입니다.

| 실제 1,320건 검색 | 75 → 40ms | 85 → 52ms |
| 10배 복제 13,200건 검색 | 224 → 193ms | 254 → 228ms |

## 36 · 확대한 2D 지도에서도 보이는 키보드 초점 — 2026-09-20

- 브라우저의 `:focus-visible` 판정을 사용합니다. 마우스·터치로 일부만 보이는 도시를 누를 때는 초점 보정 때문에 버튼이 포인터 아래에서 움직이지 않습니다.

## 37 · 도시 묶음이 바뀌어도 이어지는 키보드 초점 — 2026-09-20

## 38 · 검색 조건을 바꿀 때 추천 순서 재사용 — 2026-09-20

### 확인한 문제

공고별 추천 점수와 설명은 재사용하고 있었지만, 검색어를 한 글자 입력할 때마다 결과 전체를 다시 정렬했습니다. 프로필과 공고가 같으면 상대적인 추천 순서도 같은데 회사 이름·공고 ID의 문자열 비교가 반복됐습니다. 배포 빌드의 CPU 프로파일에서 공고 수가 늘어날수록 이 비용이 커지는 것을 확인했습니다.

### 반영한 내용

- 현재 프로필·공고로 계산한 추천 순서를 보관하고, 검색·필터에 맞는 결과를 그 순서에서 골라 반환합니다. 기존 캐시에 없던 공고가 결과에 처음 포함될 때만 순서를 다시 계산합니다.
- 추천 점수와 설명은 해당 공고가 결과에 필요해질 때 계산합니다. 처음 좁은 검색으로 시작해도 전체 공고의 추천을 미리 계산하지 않습니다. 프로필이나 공고 자료가 갱신되면 새 캐시를 사용합니다.
- 기존 점수·회사 이름·공고 ID 비교 방식을 유지합니다. 문자열 비교까지 같은 것으로 판정되는 동점은 원본 공고 순서를 따릅니다. 나중에 검색 범위를 넓혀 앞쪽 공고를 발견해도 발견 순서가 추천 순서를 바꾸지 않습니다.
- 결과가 없으면 빈 배열을 반환하며, 매번 별도의 결과 배열을 제공합니다. 화면에서 반환된 배열의 순서를 바꿔도 이후 검색에 영향을 주지 않습니다.

### 브라우저 측정

Chrome 153의 배포 빌드, 1440×960의 2D 지도와 기본 샘플 프로필을 사용했습니다. 보관된 공개 공고 1,320건과 이를 열 번 복제한 13,200건을 각각 로드하고 검색을 준비한 뒤, `engineer`를 세 번 입력한 **24회**를 조건별로 비교했습니다. 다음은 `input` 이벤트부터 두 번째 `requestAnimationFrame`까지의 시간입니다.

| 공고 수 | CPU 감속 | 중앙값 전 → 후 | 95백분위 전 → 후 |
| --- | --- | --- | --- |
| 실제 1,320건 | 없음 | 25 → 26ms | 33 → 33ms |
| 실제 1,320건 | 6배 | 39 → 35ms | 48 → 46ms |
| 복제 13,200건 | 없음 | 39 → 34ms | 47 → 42ms |
| 복제 13,200건 | 6배 | 183 → 113ms | 253 → 129ms |

일반 조건의 실제 공고에서는 차이가 작았고 큰 부하에서 개선 폭이 컸습니다. 측정한 각 입력의 화면 결과 수가 현재 검색어와 일치하는지도 확인했습니다. 13,200건·6배 감속에서는 50ms를 넘는 작업이 전후 모두 **26건** 남았습니다. 처음 추천을 계산하거나 아직 계산하지 않은 공고가 포함될 때는 정렬 비용도 발생합니다.

13,200건은 브라우저 부하 실험용 자료이며 실제 수집 규모나 서버 처리 용량이 아닙니다. 해당 복제 응답은 서버의 64MiB 캐시 한도를 넘습니다. 위 값은 로컬 실험이며 현장 INP나 다른 기기의 성능을 보장하지 않습니다.

### 검증

- 실제 1,320건과 복제 13,200건에서 세 프로필·24가지 조건을 두 차례씩 바꾼 **288번의 비교**로 이전 구현과 전체 추천 결과·순서·도시 집계가 같은지 확인했습니다. 필터 예상 개수, 원본 자료, 결과 배열의 독립성도 확인했습니다.
- 새 회귀 검사는 유니코드 표현이 다른 회사 이름·공고 ID가 같은 것으로 비교될 때 원본 순서를 보존하는지 확인합니다. 첫 검색의 빈 결과, 범위 확대·축소, 프로필 변경과 같은 ID의 공고·회사 갱신 검사도 통과했습니다.
- 구현과 분리된 테스트 전담 subagent가 1440px·320px의 E2E **6개**를 보강하고 통과를 확인했습니다. 첫 빈 검색 뒤 더 잘 맞는 공고를 발견하는 흐름, 고용 형태에 따른 회사 순서 변경, 동점과 새로고침, 원격 거주 조건의 확대·복원을 검사합니다. 기대하는 공고·회사 순서를 직접 명시하며 제품 함수로 기대값을 계산하지 않습니다.
- 실제 공고로 1440px·320px의 2D와 390px의 3D에서 필터 예상 수·적용·빈 검색·도시 선택을 확인했습니다. 런던의 **1개 회사·18개 공고**, 시애틀의 **1개 회사·64개 공고**가 현재 조건과 일치했습니다. 2D의 키보드 도시 탐색도 확인했습니다.
- 실제 공고 검증에서 실행 오류·가로 넘침·자동 WCAG 2.2 A/AA 위반이 없었습니다. API 요청 **3회**는 공개 카탈로그 GET이며 검색어·프로필·메모를 포함하지 않았습니다.
- 타입 검사·배포용 빌드 성공, 단위 검사 **594개** 통과. 테스트 전담 subagent가 최종 소스·테스트를 고정하고 실행한 개발 서버와 배포용 로컬 서버의 전체 브라우저 검사도 **각 165개 통과**.

정렬 비용과 동점 순서의 근거는 [레퍼런스](references.md)에 정리했습니다. 실제 공고·이전 코드 사본·CPU 프로파일·측정 기록·화면은 로컬에 보관하고 공개 회귀 검사는 가상 자료를 사용합니다.

## 39 · 빈 결과 안내의 중복 검색 줄이기 — 2026-09-20

### 확인한 문제

검색 결과를 화면에 표시한 뒤, 조건 완화 안내가 필요한지 확인하려고 전체 공고를 다시 검색하고 집계했습니다. 현재 범위에 공고가 있으면 안내는 표시하지 않지만 계산 비용은 발생했습니다. 공개 공고와 복제 자료의 배포 빌드에서 이 반복 작업을 확인했습니다.

### 반영한 내용

- 도시 목록·선택한 도시·원격 기회·기타 근무지에 이미 표시하는 결과를 사용해 빈 범위인지 판단합니다. 현재 범위에 결과가 있으면 안내를 위한 재검색을 생략합니다.
- 다른 도시나 탭에 공고가 남아 있어도 현재 범위가 비면 기존 안내 계산을 수행합니다. 조건 완화안·예상 공고 수·대체 탐색 경로와 적용·되돌리기 규칙을 유지합니다.
- 별도의 상태나 캐시를 추가하지 않고 현재 화면의 결과에서 판단합니다. 프로필이나 같은 ID의 공고 내용이 바뀌어 결과가 사라지거나 돌아오는 경우도 반영합니다.

### 브라우저 측정

Chrome 153의 배포 빌드, 1440×960의 2D 지도와 기본 샘플 프로필을 사용했습니다. 보관된 공개 공고 1,320건과 이를 다섯 번 복제한 6,600건을 로드하고 검색을 준비한 뒤, `engineer`를 세 번 입력한 **24회**를 조건별로 비교했습니다. `input` 이벤트부터 두 번째 `requestAnimationFrame`까지 측정했으며, 중앙값은 가운데 두 측정값의 평균입니다.

| 공고 수 | CPU 감속 | 중앙값 전 → 후 | 95백분위 전 → 후 |
| --- | --- | --- | --- |
| 실제 1,320건 | 없음 | 25 → 27.5ms | 32 → 33ms |
| 실제 1,320건 | 6배 | 35.5 → 32ms | 46 → 44ms |
| 복제 6,600건 | 없음 | 26.5 → 26ms | 32 → 32ms |

일반 조건의 실제 공고에서는 차이가 작았습니다. 6,600건·6배 감속의 검색 구간에서 관찰된 50ms 초과 작업은 **22 → 3건**으로 줄었습니다. 각 입력에 표시된 결과 수가 현재 검색어와 일치하는지도 확인했습니다. 결과가 있는 검색 구간의 CPU 프로파일에서는 안내 계산과 그 하위 검색·집계의 표본이 더 이상 관찰되지 않았습니다. 빈 범위의 안내 계산과 나머지 검색·렌더링 비용은 남습니다.

6,600건은 브라우저 부하 실험용 복제 자료이며 실제 수집 범위나 서버 처리 용량을 뜻하지 않습니다. 위 값은 로컬 실험이며 현장 INP나 다른 기기의 성능을 보장하지 않습니다.

### 검증

## 40 · 프로필을 수정해도 이어지는 탐색 — 2026-09-20

### 확인한 문제

기존 개인 프로필의 이름이나 거주 국가를 수정해도 선택한 도시가 해제되고 결과 탭이 다시 지정됐습니다. 저장한 기회나 도시 비교에서 프로필을 수정하면 기회 탐색으로 이동했습니다. 프로필의 희망 직무를 바꾸지 않아도 현재 직무 필터를 덮어써, 별도로 넓혀 둔 검색 범위가 좁아질 수 있었습니다.

### 반영한 내용

- 기존 개인 프로필을 수정하면 보고 있던 탐색·저장·비교 화면과 선택 도시를 유지합니다. 검색어·지도 표시·정렬과 프로필에서 바꾸지 않은 검색 조건도 유지하면서 새 프로필로 결과를 갱신합니다.
- 희망 직무를 실제로 바꾼 경우에 직무 필터에 반영합니다. 이름·경력·기술·거주 국가만 수정하면 별도로 선택한 직무 필터를 보존합니다.
- 선호 근무 형태를 바꿨을 때는 기존 필터 조작과 같은 탭 이동 규칙을 사용합니다. 원격으로 바꾸면 원격 탭을 선택하고, 원격 탭에서 출근·하이브리드 등으로 바꾸면 도시로 이동합니다. 제한 없음으로 바꾸면 현재 탭을 유지합니다.
- 수정 버튼은 **변경 사항 적용**으로 표시합니다. 처음 개인 프로필을 만드는 흐름은 **내 기회 지도 만들기**와 기존 탐색 시작 동작을 유지합니다.
- 프로필 기억하기 해제·삭제에 따른 개인 조건 정리 규칙을 유지합니다. 입력한 경력과 검색 조건을 서버에 추가로 전송하거나 새로운 저장 항목을 만들지 않습니다.

수정 후 원래 작업으로 돌아가는 흐름과 대화상자 초점 복원의 근거는 [레퍼런스](references.md)에 정리했습니다.

### 검증

- 테스트 전담 subagent가 이전 배포 빌드에서 1440px·320px의 **12개 흐름**을 관찰해 도시 선택·원격/기타 탭·저장/비교 화면·별도 직무 필터의 유실을 재현했습니다. 이전에 유지되던 검색어·지도 설정·저장 메모·지원 상태·비교 목록도 함께 확인했습니다.
- 새 E2E **12개**가 통과했습니다. 편집 취소, 기술 변경으로 선택 도시가 비는 경우, 직무 필터 보존, 명시적인 희망 조건 변경, 저장 화면의 검색·지원 상태·메모, 비교 결과 갱신과 최초 프로필 생성을 검사합니다. 회사·공고 수와 문구는 가상 자료의 명시적인 기대값을 사용합니다.
- 기존 경력·추천 순서·원격 국가·기억하기 검사도 새 수정 흐름에 맞춰 보완했습니다. 거주 국가 버튼에서 편집한 뒤 같은 원격 탭의 안내로 돌아오고 키보드 초점도 호출 버튼에 복원되는지 확인합니다.
- 타입 검사와 배포용 빌드가 성공했고, 단위 검사 **594개**가 통과했습니다. 독립 담당이 최종 소스·테스트를 고정해 실행한 개발 서버와 배포용 로컬 서버의 전체 E2E도 **각 183개 통과**했으며, 실패·건너뜀·재시도 통과는 없었습니다.

초기 표적 검사에서 발견한 도시 정렬 선택자 오류는 실제 접근성 이름을 사용하도록 수정했습니다. 정렬 값과 결과 수의 기대값을 유지하고, 실패 기록과 수정 후 실행을 각각 보관했습니다. 320px의 수정 대화상자와 적용 후 도시 화면도 확인했습니다. 이 검증은 Chrome과 가상 공고를 사용했으며, 화면·상세 실행 기록은 로컬에 보관합니다.
