# 채용 트렌드와 공개 데이터 출처 조사 — 2026-09-26

이 문서는 2026-09-26에 수행한 조사를 2026-09-28 로컬 자료 정리 전에 Git에 보존한 기록입니다. 아래의 ‘현재’와 회사·공고 수는 **조사 당시**를 가리킵니다. 제안 전체가 구현됐다는 뜻은 아닙니다. 이후의 게시 확인·관측 이력·출처 확장은 [게시 확인](posting-presence.md), [관측 기록](catalog-observations.md), [출처 조사](source-survey.md), [지역 확장](regional-coverage.md)을 기준으로 합니다.

원문 응답과 조회 메타데이터는 [로컬 보존 기록](local-data-retention.md)의 비공개 압축본에 보관합니다. 사이트를 이번 정리 중 다시 조회하지 않았습니다.

사용자가 제공한 국내 자료와 해외 서비스 8곳의 공개 페이지·분석 방법·데이터 문서를 조사했다. 제품 코드, 설정, 수집 캐시를 변경하거나 새 기능을 구현하지 않았다. 이 문서는 논의를 위한 제안이다.

제 의견은 ORBIT에 지역·직무별 기술 수요와 시간에 따른 공고 변화를 보충하는 것이다. 기존 지구에서 지역을 선택하고, 그 지역의 채용 상황을 비교표와 작은 차트로 확인한 다음 실제 공고로 이어지는 구성이 잘 맞는다. 개인 조건에 맞는 해외 기회를 고르는 목적에 분석을 연결하는 것이 좋다.

현재 이미 구현된 도시 비교, 기술·경력 매칭, 비자·취업 자격, 원격근무 국가, 언어·협업 시간, 보상 근거, 저장 공고 상태 확인은 보완의 출발점이다. 이 기능들을 신규 기능으로 다시 제안하지 않는다.

사용자가 준 [개발자 직군별 채용 트렌드](https://heyman333.github.io/developer-trend/)는 직군별 공고 규모, 기술 스택, 기술의 교차 비교, AI 개발 관련 표현과 AI 코딩도구, 경력 조건을 한눈에 보여준다. 표본 크기와 분석 방법을 함께 설명하고 기술 차트의 눈금을 맞춘 점이 참고할 만하다.

다만 해당 페이지의 분석 방법에는 2026-09-23의 국내 공고를 대상으로 하고 해외 근무 공고를 제외했다고 명시돼 있다. 직군별 규모는 전체 대상 공고, 기술·AI·경력 지표는 직군마다 약 500개 본문 표본을 사용하며 모바일 두 직군은 전체를 사용한다. 한 공고가 여러 직군에 속할 수 있고, 기간별 추이는 없는 한 시점의 분석이다. 기술은 제목·요약·본문·태그의 정규식 언급으로 집계한다. 따라서 그 수치를 해외 수요에 적용하거나 모든 언급을 필수 자격으로 해석하면 안 된다. 제시된 표본 오차만으로 수집 플랫폼의 편중이나 분류·키워드 판정의 정확도를 설명할 수도 없다.

실제 데이터 보충을 검토할 때는 접근 방식도 구분할 필요가 있다. 이번 조사에서 확인한 후보는 다음과 같다.

- Indeed Hiring Lab의 공개 CSV는 CC BY 4.0이며 출처 표시를 요구한다. 장기 흐름을 추가할 때 유력한 후보지만, 개별 공고를 제공하는 API는 아니다.
- Himalayas는 인증 없는 공개 API의 채용 보드·내부 대시보드 사용을 안내한다. 출처 이름과 Himalayas 링크 표시, 제3자 채용 사이트로의 재배포 제한, 요청량 제한이 있다. 문서상 검색 API도 있어 전체 목록을 매번 수집할 필요는 없다.
- Arbeitnow는 키 없는 공개 API를 안내한다. 지역 보충 후보로 삼되 실제 도입 전 응답 범위·재사용 조건·중복을 구체적으로 확인해야 한다.
- IT Jobs Watch의 채용시장 집계 콘텐츠는 CC BY-NC-SA 4.0이며 공고 목록·제3자 자료는 그 라이선스에서 제외한다. 기능과 표현 방식의 참고 가치가 높고, 집계 데이터를 제품에 재사용할 때는 조건을 따로 검토해야 한다.
- Levels.fyi의 데이터 API는 별도 접근 요청 방식이다. 공개 보고서의 수치를 우리 공고 데이터에 합쳐 넣는 방식보다 출처가 분명한 참고 링크·허용된 임베드 등의 활용부터 검토하는 편이 적절하다.
- 공개 API가 있는 집계 사이트도 기존 공식 ATS 공고와 중복될 수 있다. 회사 식별자, 원래 게시 ID와 지원 URL, 출처를 연결하는 기준이 먼저 필요하다.

현재 ORBIT 자료를 읽기만 해서 확인한 사실도 제안에 반영했다. 2026-09-26에 보관된 캐시는 36개 회사, 전체 공개 공고 10,516건, 현재 탐색 후보 3,325건이다. 그중 SpaceX는 876건으로 26.3%이고, 상위 5개 회사는 55.1%를 차지한다. 이는 전체 해외 채용 시장을 대표한다는 근거가 아니다. 공고 수와 채용 중인 회사 수를 함께 표시하고, 지역·산업·회사 규모별 수집 범위를 넓힐 필요가 있다.

근무 형태를 명시적으로 확인하지 못한 공고도 2,043건, 61.4%다. 이것을 원격근무 불가로 처리해서 비율을 만들면 안 된다. 기존 앱의 미확인 구분을 통계에도 유지하고, 기술·경력·비자·연봉의 미확인 값과 통계에 사용한 분모를 보여주는 것이 좋다. 원격 공고나 국가만 알려진 공고에 도시 연결이 없는 것은 그 자체로 오류가 아니다.

이번 회사 12곳 추가와 직군 분류 보완도 중요한 사례다. 새로 수집하기 시작한 회사의 기존 공고를 모두 시장의 신규 공고로 세거나, 분류 규칙 때문에 제외된 137건을 채용 감소로 보여주면 잘못된 추이가 만들어진다. 해당 137건은 규칙 적용의 전후 차이이며 전수 수동 판정한 오류 건수도 아니다.

제가 제안하는 우선순위는 다음과 같다.

1. **수집 범위와 시간 비교 기준부터 정한다.** 관측 날짜, 당시 수집 대상과 정상 조회 여부, 처음·마지막으로 확인한 공고, 분류 기준을 구분한다. 같은 회사군에서의 변화와 새 회사 추가분을 따로 파악한다. 공개 목록에서 사라짐, 조회 실패, 실제 채용 종료도 구분한다. 처음부터 충분한 기간이 없으면 오늘의 분포를 보여주고, 관측 이력이 쌓인 뒤 추이를 제공한다. 외부 Hiring Lab 지수는 그 사이에도 별도 참고 자료로 활용할 수 있다.

2. **국가·도시·직무별 기술 수요를 만든다.** 선택 범위의 공고 수와 회사 수, 자주 요구하는 기술, 함께 요구하는 기술, 명시된 경력 조건을 비교한다. 현재 자격 조건 분석을 활용해 필수·우대·일반 언급을 구분한다. AI 개발 기술과 AI 코딩도구 사용 조건도 별도로 다룬다. 현재 표본의 통계임을 명시하고, 표본 수가 적은 조합을 큰 상승률이나 시장 순위로 강조하지 않는다.

3. **개인 조건과 지역 비교에 분석을 연결한다.** 예를 들어 ‘한국 거주 백엔드 개발자’라는 가정의 프로필에서 베를린·암스테르담·토론토의 관심 기술 공고, 비자 지원 근거, 언어·협업 시간, 공개 보상을 나란히 확인하게 한다. 어떤 통계 항목을 선택했을 때 해당 공고 목록과 원문으로 이어지면 실제 지원 판단에 도움이 된다. 명시 조건 일치·미확인·불일치를 유지하고 합격 가능성이나 취업 자격 확정으로 표현하지 않는다.

4. **보상과 이주 맥락은 별도 근거를 연결해 보충한다.** 현재 기본 급여 비교에 표본 수와 분위수, 지역·직급 조건을 더하는 방식이 우선이다. Levels.fyi의 제보 총보상은 별도로 표시하고, 세금·생활비는 출처와 기준 시점이 있는 참고 정보를 제공한다. 개인의 실수령액이나 이주 가능성을 단일 점수로 단정하는 기능은 이번 보완의 첫 목표로 삼지 않는 것이 좋다.

첫 논의에서 정하면 좋은 것은 두 가지다. 첫째, 주된 사용자를 ‘해외 공고를 고르고 지원하려는 개발자’로 유지할지, ‘국가별 기술 시장을 분석하려는 사용자’까지 같은 비중으로 다룰지다. 저는 기존 목적에 맞춰 해외 지원 의사결정을 우선하고 시장 분석을 그 판단 근거로 연결하는 쪽을 추천한다. 둘째, 데이터 범위를 넓힐 첫 지역을 정하는 것이다. 현재 회사 편중과 데이터 접근성을 고려하면 유럽·영국 및 국제 원격 채용을 먼저 검토할 근거가 있지만, 목표 지역이 북미·일본·싱가포르라면 그 지역의 공식 게시판 확보를 우선하는 것이 더 적절하다.

조사는 공개 페이지·README·API 문서와 제한된 브라우저 관찰에 기반한다. HN Hiring Trends는 데이터 로드 뒤 remote 입력, 검색 조건의 URL 반영, About 설명을 확인했다. Levels.fyi와 국내 자료의 페이지도 브라우저에서 열람했다. 각 사이트의 전체 검색 흐름이나 통계 정확도를 감사한 것은 아니다. TrueUp과 Hiring.cafe는 이번 HTTP 조회에서 403을 반환해 직접 확인한 기능 비교에서 제외했다. Indeed Data Portal도 403이었지만, 공식 Hiring Lab 사이트와 공개 GitHub의 방법론·데이터 안내는 정상적으로 확인했다.

조사 당시 출처 원문, 조회 메타데이터, 브라우저 화면과 캐시의 집계 근거는 무시되는 로컬 폴더에 보관했다. 2026-09-28 정리 후의 보존 위치는 위 로컬 보존 기록을 따른다. 실제 공고 원문을 공개 문서로 옮기지 않았으며 연구용 브라우저도 종료했다.

추가로 사용자가 질문한 ‘앱 동작 중 공고의 유효성을 확인하면 부하나 API 호출 문제가 생기는가’에 대해서는, **확인 범위와 재사용 방식에 따라 비용이 크게 달라지며 충분히 관리할 수 있다**고 판단한다. 모든 화면 열람을 외부 재조회와 연결하는 방식은 피하고, 서버가 확인한 게시판 목록을 여러 공고·사용자가 공유하는 방식이 적절하다.

현재 구현을 읽어서 확인한 보호 장치는 다음과 같다.

- 일반 조회는 정상 게시판의 30분 캐시를 재사용한다. 30분마다 무조건 도는 수집 작업이라는 뜻은 아니며, 요청이 들어왔을 때 갱신할 게시판을 고른다.
- 같은 서버 프로세스에서 진행 중인 수집을 공유한다. 여러 사용자가 동시에 조회해도 같은 수집을 중복 시작하지 않는다.
- 게시판 수집은 동시에 4곳으로 제한한다. SmartRecruiters는 여러 회사가 공유하는 별도 요청 큐를 사용하며 동시 요청 4개, 시작 간격 200ms로 제한한다. ‘게시판 4개’가 모든 제공자를 합친 HTTP 요청 4개와 같은 뜻은 아니다.
- 실패하면 이전 정상 결과를 보존하고 재시도 간격을 늘린다. 자체 지연은 최대 30분이며, 제공자의 Retry-After가 더 길면 그 시각을 따른다.
- 저장 목록 열기나 메모 수정은 게시 확인 요청을 만들지 않는다. 현재 게시 상태 확인은 명시적인 버튼 조작으로 실행한다.
- 진행 상태를 조회하는 API는 이미 진행 중인 수집 결과를 읽는다. 브라우저의 진행 상태 조회 횟수가 그대로 외부 제공자 호출 횟수가 되지는 않는다.

관련 근거는 [수집 서비스](../server/catalog-service.ts), [캐시 기간](../shared/catalog-freshness.ts), [게시 상태 조회](../src/hooks/usePostingStatus.ts), [SmartRecruiters 수집](../server/providers/smartrecruiters.ts), [요청 큐](../server/providers/request-queue.ts)다.

보완할 지점도 있다. 수동 새로고침은 최소 1분이 지나면 다시 수집할 수 있고, 게시 상태 확인 역시 현재 전체 공고 수집 경로를 사용한다. 저장 공고 한 건을 확인하는 요청에서도 갱신 가능한 다른 게시판까지 조회할 수 있다. 공개 서비스에서 자주 눌리면 본문 다운로드와 정규화를 반복할 수 있으므로 이 경로를 가볍게 만드는 가치가 크다.

앞선 실제 수집의 Grab 복구 실행 기록을 따로 확인했다. 이 실행은 전체 36곳의 신규 전수 조회가 아니라 Grab 한 게시판의 복구였다. 외부 요청은 **목록 5회와 상세 공고 139회, 총 144회**였고 모두 200 응답이었다. 첫 요청부터 마지막 응답까지 약 30초였다. 이 자료의 전체 게시 ID 존재만 확인하는 설계라면 목록 5회로 판단할 수 있지만, 본문·연봉·자격 내용이 변경됐는지까지 확인할 수는 없다. 검증 비용을 논할 때 ‘36개 게시판 = HTTP 요청 36번’으로 계산하면 안 되는 이유다.

해외 데이터 후보에도 같은 문제가 있다. [Himalayas API](https://himalayas.app/api)는 페이지당 최대 20건이다. 공고가 10만 건인 상황을 가정하면 전체 목록을 한 번 읽는 데 약 5,000회가 필요하고, 이를 30분마다 반복하면 하루 약 24만 회가 된다. 이는 비용을 설명하기 위한 가정이며 이번에 그 양을 호출한 것은 아니다. 해당 문서는 데이터의 일일 갱신과 필터 가능한 검색 API도 안내한다. 필요한 지역·직무 범위와 출처의 실제 갱신 주기에 맞춰 읽는 것이 적절하다.

향후 설계의 출발점은 다음처럼 나눌 수 있다. 아래 간격은 모든 제공자에게 허용된 호출량을 보장하는 값이 아니라 운영 정책을 논의하기 위한 예시다.

| 상황 | 제안하는 확인 방식 |
|---|---|
| 일반 탐색·검색·지도 이동 | 서버 캐시를 즉시 사용한다. 화면 조작마다 외부 요청을 만들지 않는다. |
| 게시 중인지 확인 | 출처별로 정한 주기, 예를 들어 30–60분 단위로 전체 게시 ID 목록을 갱신한다. 수동 확인도 서버의 대기 시간과 호출 예산을 따른다. |
| 본문·연봉·자격 변경 확인 | 처음 수집하거나 공식 변경 정보가 있거나 별도 본문 확인 기간이 지난 공고를 갱신한다. ID 목록의 확인 시각과 본문의 확인 시각을 구분한다. |
| 지원하려는 공고 | 최근 확인 결과와 원문 링크를 보여준다. 추가 검증이 필요할 때는 오래된 결과에 한정해 우선 처리하는 정책을 검토한다. |
| 트렌드 기록 | 이미 확인한 자료에서 일별 관측을 남긴다. 추이 차트를 그리기 위한 별도의 전수 외부 조회를 매번 수행하지 않는다. |
| 429·타임아웃·서비스 오류 | 제공자 지침과 재시도 대기 시간을 따르고, 상태를 미확인으로 표시한다. 오류를 채용 종료로 바꾸지 않는다. |

공식 API가 지원하면 ETag·수정 시각 등을 이용할 수 있지만, 지원 여부를 가정하면 안 된다. 304 응답은 다운로드 비용을 줄여도 제공자의 호출 쿼터에는 포함될 수 있다. 서버를 여러 대로 확장하면 현재 프로세스 안의 수집 공유만으로는 부족하므로 공통 저장소·작업 큐·중복 실행 방지와 출처별 요청 예산이 필요하다. 사용자 수가 늘 때는 외부 API와 별개로 우리 서버의 응답 생성·압축·전송 비용도 관찰해야 한다.

추가적인 단건 확인을 설계한다면 현재 ‘관심 공고 ID나 개인 저장 기록을 서버에 보내지 않고 전체 공개 목록을 비교한다’는 데이터 흐름도 함께 검토해야 한다. 이번 조사에서는 이 동작을 변경하지 않았다.

마지막으로 자동화가 확인할 수 있는 것은 주로 **공식 목록에 해당 ID가 최근 게시돼 있는지**다. HTTP 200만으로는 만료 안내나 일반 채용 페이지로의 이동을 구분할 수 없고, 공고가 게시돼 있어도 채용팀이 실제 선발을 계속하는지까지 보장할 수 없다. 화면에는 ‘게시 확인 · 확인 시각’, ‘공개 목록에서 미확인’, ‘현재 상태 확인 필요’를 구분하는 것이 적절하다. 현재 앱도 이 구분을 이미 사용한다.

운영 위험을 정량 부하 테스트로 검증한 결과는 아니다. 현재 소스와 이전 실제 수집 로그를 읽고 해외 API 문서의 제약을 대조한 판단이다. 따라서 다음 기능을 논의할 때는 **게시 여부 확인과 본문 갱신의 분리, 공유 캐시·요청 예산, 관측 이력**을 데이터 확장과 트렌드 화면의 선행 과제로 두는 것을 추천한다.
