# 당근 요청 간격 결함과 수정 검증

상태: 2026-10-26 KST, 실제 요청 간격 결함을 재현하고 수정했다. 테스트 보조 타입 오류를 수정한 뒤 12단계 로컬 검증이 실제 종료 코드 0으로 끝났다. Main·Astra가 같은 최종 소스·보고서·인덱스 해시에 명시적으로 동의했다. 새 실제 수집·운영 발행·진짜 예약 실행 확인은 아직 완료하지 않았다.

기계 판독용 소스·결과·합의 해시는 [검증 근거](daangn-pacing-remedy-evidence-2026-10-26.json)에 보존한다.

## 실제 실패

HTML 후행 모듈과 호출자 문맥 수정을 보존한 커밋 `357344d17064b981fa3fd1729ff6735176d5e63b`로 별도 실제 수집을 한 번 실행했다. 기존 공개 catalog 한 건과 당근·당근페이 응답 42건을 받았다. 이 중 robots 네 건, 목록 네 건, 상세 34건은 모두 HTTP 200과 EOF로 기록됐다. 앞서 실패한 첫 실제 수집의 요청과 결과도 그대로 보존한다.

연속한 41개 요청 간격 중 26→27번의 단조 시계 간격은 `2999.861374999993ms`였다. 밀리초 단위 벽시계 표시로는 3000ms였지만 실제 검사 기준인 최소 3000ms에 못 미쳤다. 허용 오차를 추가하거나 반올림해 통과시키지 않았다. 원본 실행과 수집 영수증은 `FAILED`, 종료 코드는 1이다.

기존 대기열은 `Date.now()`로 다음 시각을 계산하고 실제 요청 호출 전에 시작 시각을 저장했다. 벽시계의 정밀도와 호출 전 동기 작업 차이는 단조 시계에서 측정하는 최소 간격을 보장하지 못한다. 다만 내부 타이머 시각이 기록되지 않았으므로 이번 0.139ms 부족분의 정확한 원인을 특정한 운영체제 사건으로 단정하지 않는다.

## 확인한 부분과 확인하지 못한 부분

원래 공개 목록은 130개 회사와 7,045개 공고였다. 저장된 새 두 회사의 결과에는 당근 31개와 당근페이 3개의 공고가 있었고, 34개 ID와 URL이 모두 기존 공개 목록에 없었다. 42개 요청의 회사·수집 단계는 해당 작업 구간과 일치했고, 상세 34건의 원문 JSON-LD 회사명도 일치했다.

즉시 체크포인트 재실행의 외부 요청은 0건이었다. 저장된 ID·URL과 캐시·확인 시각은 유지됐다. 그러나 요청 간격 검사에서 중단돼 원문 전체의 완전성·제목·정규 URL·위치·게시 시각·기술 직군 제외 근거를 확인하는 마지막 검증기는 실행되지 않았다. 최종 출처 검증 및 재실행 비교 파일도 작성되지 않았다. 따라서 위 관측은 전체 수집 성공이나 운영 신규 공고 제공의 근거가 아니다.

예정된 마지막 의존성 보존 단계는 `NOT_RUN`이다. 별도의 파일 확인으로 의존성이 유지됨을 확인했지만, 예정 단계를 실행한 것으로 바꾸지 않았다.

## 종료와 보존

소유 범위의 PID 25개를 조회해 부재를 확인했고 실제 시작 식별자 다섯 개를 보존했다. 실행 중 관측 수 135개를 모두 개별 시작 기록으로 취급하지 않는다. esbuild 자식 한 개의 개별 종료 callback은 없으므로 종료 코드를 추정하지 않는다. 직접 자식과 controller의 종료 코드 1, 잠자기 방지 프로세스의 회수 결과는 별도로 확인했다.

단조 시계 약 134.502초의 검사·정리 구간에 겹치는 전원 사건 기록은 없었다. 이 구간은 wrapper 전체 약 137.126초보다 좁으며 시스템 전체의 연속 감시를 뜻하지 않는다.

원본 응답·요청·체크포인트·실패·종료 기록은 무시되는 `.local/research/reference-official-jobs-2026-10-25/`에 보존한다. 첫 두 실제 실행의 누적 사용량은 공개 catalog 두 건, 출처 요청 46건, 재실행 출처 요청 0건이다. 종료한 실행을 다시 시작하거나 기존 결과를 덮어쓰지 않는다.

## 적용한 수정

호스트 요청 간격은 단조 시계로 계산하고, 타이머가 깨어날 때마다 남은 시간을 다시 검사한다. 실제 요청을 동기적으로 호출한 뒤 기준 시각을 저장해 호출 준비 시간이 다음 간격을 줄이지 않도록 한다. 최소 3초와 더 큰 robots 지연은 유지한다. HTTP `Retry-After`의 절대 시각과 cooldown은 기존 벽시계 의미를 유지한다.

독립 테스트 담당은 원래 제품 코드에 새 검사 다섯 개만 설치해 다음 현상을 모두 재현했다.

- 벽시계 3000ms에 단조 시계가 2999.75ms이면 아직 요청하지 않아야 한다.
- 요청 전 동기 작업에 25ms가 쓰여도 실제 다음 요청의 간격은 최소 3000ms여야 한다.
- 벽시계를 앞으로 옮겨도 요청 간격이 짧아지지 않아야 한다.
- 벽시계를 뒤로 옮겨도 단조 시계의 정상 요청 시각이 늦어지지 않아야 한다.
- HTTP 날짜 형식의 `Retry-After` 만료는 벽시계를 따르되, 만료 뒤 다음 요청의 최소 간격은 단조 시계를 따라야 한다.

새 다섯 검사는 모두 예상한 첫 요청 관측 지점에서 실패했다. 모듈·hook·시간 초과·정리 오류로 실패한 것이 아니다. 선택하지 않은 기존 HTTP 검사 53개는 건너뛴 상태이며 통과로 세지 않았다. 실패한 첫 단언 뒤의 후속 단언에도 실행 실적을 부여하지 않는다. 이 재현의 원본 상태는 `FAILED`, 종료 코드는 1로 보존했다. 주 구현 담당과 Astra가 같은 최종 보고서와 인덱스 해시에 동의한 뒤 승인된 제품 수정을 적용했다.

소유 PID 13개의 부재를 확인했으나 실제 시작 식별자는 잠자기 방지 프로세스 한 개만 남아 있다. 외부 시작 조회는 원본 실행 종료 약 1.993초 뒤였으므로 시작 시점 증거로 쓰지 않는다. 약 7.150초의 검사·정리 전원 기록 구간은 wrapper 전체 약 9.761초보다 좁다. 두 Vitest 자식의 종료는 `SIGTERM`으로 기록됐으며 정상 코드 0으로 바꾸지 않았다.

수정 후 검증은 단위 검사 208개, 독립 수집 자료 검증기 검사 37개, 1440px·320px E2E 두 개와 타입·빌드·Worker 번들 경계를 포함한다. 첫 전체 실행의 타입 오류와 수정 후 새 전체 실행을 아래에서 구분한다.


## 첫 수정 후 검증의 실패

요청 간격 제품 수정을 적용한 첫 전체 검증은 단위 검사 208개와 수집 자료 검증기 검사 37개를 모두 통과했다. 새 요청 간격 검사 다섯 개도 각 후속 반환값·시각 단언까지 통과했다. 단위 검사의 파일·전체 이름 조합은 185개이며, 매개변수에 따른 중복 이름을 제거하지 않은 실제 검사 수는 208개다.

그 뒤 루트 타입 검사에서 `tests/unit/daangn-http.test.ts`의 테스트 보조 함수가 `TS2322`로 실패했다. 공통 요청 함수는 `Promise<unknown>`을 반환하는데 테스트의 결과 타입이 문자열을 요구했다. 실행 과정에서 타입 검사를 생략하는 Vitest 결과만으로 빌드 통과를 판단하지 않는다. `tsc --noEmit` 뒤의 Vite·서버 빌드는 실행되지 않았다.

Worker 자산·타입, Worker 번들, E2E, 마지막 의존성·브라우저 보존 단계 다섯 개는 `NOT_RUN`이다. 원본 전체 실행은 `FAILED`, 종료 코드는 1로 보존한다. 처음 보존한 생성물 다섯 폴더의 파일 926개는 실행별 보관 위치에 있고, prebuild가 새로 만든 `public/pdf`의 파일 198개는 별도로 구분한다.

Main·Astra가 같은 후보 해시에 동의한 뒤 테스트의 지역 결과 타입에서 `value: string`을 `value: unknown`으로 바꾸는 한 줄을 적용했다. 요청 API, 제품 구현, 시계 제어, 실제 반환값·요청 간격 단언은 그대로 유지했다. 이전 실행에서 통과한 단계도 새 전체 실행에서 다시 검사했다.

## 타입 수정 후 전체 로컬 검증

독립 테스트 담당이 수정된 소스 파일 631개와 검증 제어 파일 77개의 해시를 묶어 새 전체 실행을 한 번 시작했다. 실행 시각은 2026-10-25 21:11:31–21:12:56 UTC이며, 재시도는 0회다. 12개 단계 모두 실제 종료 코드 0으로 끝났고 미실행 단계는 없다.

- 단위 검사 208개가 모두 통과했다. 목록·JSON·JUnit의 파일과 전체 이름을 중복 횟수까지 대조했다. 서로 다른 이름 조합 185개와 실제 검사 208개를 구분한다. 요청 간격 회귀 다섯 개는 모든 후속 단언까지 통과했다.
- 독립 수집 자료 검증기 검사 37개가 모두 통과했고 TAP·JUnit의 전체 이름과 개수가 일치했다.
- 루트 타입 검사, production 클라이언트·서버 빌드, Cloudflare 자산·Worker 타입 검사와 실제 Worker dry-run 빌드가 통과했다. dry-run은 배포가 아니다.
- production E2E 두 개가 1440px·320px에서 통과했다. 가상 자료는 132개 회사·게시판과 7개 공고이며 새 두 회사의 국가만 확인된 공고가 검색·지역 전환·상세 창·원문 링크에 표시됐다. 네 화면과 실제 dialog 치수에서 비어 있지 않은 본문과 수평 범위를 확인했다. 외부 원문으로 이동하지 않았고 요청은 모두 가상 응답이었다.
- E2E 원본 단계 546개에는 기본 서버를 기다리는 두 성공한 poll 안의 실패 표본 여섯 개가 있다. 이를 숨기거나 테스트 재시도로 세지 않았다. 두 테스트의 최종 실패·전역 오류·skip·flaky·retry는 모두 0이다.
- 시작과 종료의 의존성 항목 13,611개 및 브라우저 파일 358개가 일치했다. 설치나 다운로드는 실행하지 않았다.

Worker의 실제 의존성 그래프는 입력 111개·import 간선 360개다. Node 수집기, HTML 파서 `parse5`·`entities`, `async_hooks`가 Worker 그래프에 포함되지 않았다. Worker JavaScript는 944,332바이트, gzip 160,255바이트이고 제공 자산 367개의 합계는 14,892,289바이트다. 로컬 산출물의 일치만으로 원격 활성 Worker 버전이나 배포 상태를 단정하지 않는다.

실행 전·E2E 전후의 포트 5173 조회에서 남은 소켓이 없었다. controller의 종료 코드 0과 잠자기 방지 프로세스의 회수(-15)를 구분한다. 전원 기록은 단조 시계 약 81.366초의 검사·정리 구간이며 wrapper 전체 약 84.161초보다 좁다. 원본의 시각 있는 행 36,904개와 요약 12개를 검토했고 그 구간에 겹치는 전원 사건은 없었다. 시작·종료·해제 시점의 소유 assertion을 확인했으며 연속 pmset 감시로 보고하지 않는다.

소유 범위 PID 84개에 대한 최종 조회에서 남은 프로세스가 없었다. 내부 시작 식별자 26개와 외부 초기 식별자 세 개는 겹칠 수 있다. 등록된 spawn 43개 중 종료 callback은 40개다. esbuild 자식 세 개의 개별 종료 코드는 기록되지 않았으므로 추정하지 않는다. Vitest 자식 열 개의 `SIGTERM`과 기본 서버 한 개의 `SIGKILL`도 그대로 보존했다. 테스트별 production 서버 두 개는 종료 코드 0과 정리를 확인했다.

이번 실행이 옮긴 기존 PDF 파일 198개와 intent·moved·completed 기록 세 개를 보존했다. 새 생성물 다섯 폴더에는 파일 926개가 있다. E2E 보관 자료는 파일 758개·루트 포함 폴더 31개·심볼릭 링크 두 개이고 합계 33,225,032바이트다. 별도 원본 실행 기록 1,138개 파일·36,534,789바이트도 대조했다. 이는 작성 시점의 보관 목록이며 이후 최종 보고서·합의 기록은 별도다. 이전 실패 실행의 보관물을 덮어쓰거나 삭제하지 않았다.

Main과 Astra는 같은 최종 보고서·인덱스·소스 해시를 독립적으로 검토하고 명시적으로 승인했다. 합의는 검증한 로컬 범위의 다음 단계 진행에 대한 결정으로, 실제 출처 수집이나 운영 반영을 완료했다는 뜻이 아니다. 원본·관측 기록과 현재 검증 자료는 다음 실제 수집 및 운영 검증이 끝날 때까지 로컬에 보존하며 최종 정리 기록을 별도로 남긴다.
