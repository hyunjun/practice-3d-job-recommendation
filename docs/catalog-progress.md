# 공개 카탈로그의 수집 진행 API

브라우저는 완료된 회사의 공고부터 탐색하고, 아직 진행 중인 회사의 결과를 이어서 받습니다. 한 회사의 목록·본문 검증은 기존 수집기에서 모두 끝낸 후 반영합니다. `shared/catalog-progress.ts`의 타입이 응답 계약입니다.

## 시작과 캐시

```http
GET /api/catalog?source=public
Prefer: respond-async
```

- 정상 캐시로 바로 응답할 수 있으면 기존 형태의 `200 Catalog`입니다.
- 조회가 필요하거나 같은 수집이 이미 진행 중이면 `202 { catalog, progress }`입니다. `catalog`는 현재 사용 가능한 회사별 결과를 담습니다. 첫 조회에서 아직 정상 결과가 없으면 `fetchedAt: ""`, `jobs: []`로 시작합니다.
- `progress`는 `{ id, revision, total, completed, done }`입니다. `total`은 **이번에 재조회가 필요한 회사 수**이고 `completed`에는 성공과 실패가 모두 포함됩니다. 기존의 정상 캐시만 사용하는 회사는 이 수에 들어가지 않습니다.
- `202`에는 `Preference-Applied: respond-async`, 다음 진행 URL인 `Location`, 최소 조회 간격인 `Retry-After: 1`을 제공합니다. 이 응답은 `Cache-Control: no-store`입니다.
- `refresh=1`은 기존과 같이 회사별 최소 간격·오류 재시도 시각을 따릅니다. 이미 진행 중이면 그 수집에 합류합니다.
- `Prefer`가 없는 클라이언트는 전체 수집을 기다리는 기존 `200 Catalog`를 받습니다. 완료 응답은 `Vary: Accept-Encoding, Prefer`와 필수 HTTP 재검증을 유지하며, 서버의 수집·만료 정책을 확인한 후에만 `304`가 가능합니다.

## 진행과 회사별 교체

```http
GET /api/catalog/progress?id=<collection-id>&after=<last-revision>
```

이 경로는 현재 프로세스의 수집 상태만 읽습니다. 새 외부 조회나 재시도를 예약하지 않습니다. 수집 도중 먼저 실패한 회사의 재시도 시각이 지나도 진행 요청만으로 다시 조회하지 않습니다.

| 응답 | 의미 |
| --- | --- |
| `204`, `Retry-After: 1` | 해당 번호 이후 변경이 없습니다. 본문을 보내지 않습니다. |
| `200 { progress, companyIds, jobs, catalog }` | 변경된 회사의 결과와 전체 집계·게시판 상태를 보냅니다. `catalog`에는 `companies`, `cities`, `jobs`를 중복으로 넣지 않습니다. |
| `progress.done: true` | 이번 수집이 끝났습니다. 브라우저는 진행 확인을 종료합니다. |
| `400` | 잘못된 ID 형식·진행 번호입니다. |
| `410`, `CATALOG_PROGRESS_GONE` | 프로세스 재시작 또는 다른 수집으로 진행 정보가 교체됐습니다. 사용자가 다시 조회해 현재 결과에 연결할 수 있습니다. |
| `503`, `CATALOG_UNAVAILABLE` / `CATALOG_EXPIRED` | 수집 종료 후 사용할 정상 결과가 없거나 모두 보존 기간을 넘겼습니다. 기존 오류·재시도 규칙을 적용합니다. |

진행 응답은 모두 `no-store`입니다. 클라이언트는 직전에 받은 `revision`을 전달하며 요청을 겹치지 않습니다. `companyIds`에 든 회사의 기존 공고를 제거한 뒤 `jobs`를 넣습니다. **회사 ID는 있고 새 공고가 없는 변경분도 적용**하므로 정상 빈 목록이 이전 공고를 남기지 않습니다. 변경이 없는 회사는 공고 본문을 다시 보내지 않으며, 합친 목록은 설정된 회사 순서를 유지합니다.

`BoardStatus.status: "pending"`은 이번 조회가 진행 중인 회사입니다. 실패·미확인 게시판으로 집계하지 않으며 `dataStatus`는 현재 보유한 기록의 상태를 계속 나타냅니다. 정상 기록의 30분·24시간 경계, 원래 조회 시각, 오류의 재시도 제한은 수집 중에도 유지됩니다. 진행 상태는 디스크 캐시에 저장하지 않습니다.

## 응답 검증과 실패 복구

브라우저는 `200 Catalog`, `202` 최초 상태, 이후 변경분을 화면에 전달하기 전에 검증합니다. JSON 해석에 성공한 응답도 도시·회사·공고·게시판 내부의 값이 잘못되면 거부합니다.

- 공고에는 캐시·저장 기록과 공유하는 `JobSchema`를 사용합니다. 회사·도시·게시판의 필드, 좌표 범위, 날짜, 열거값과 음수가 아닌 정수 집계도 확인합니다.
- 회사·도시·게시판·공고 ID의 중복, 회사별 게시판의 누락·출처 불일치, 공고의 회사·현재 도시 참조를 확인합니다. 전체 응답의 게시판별 `included`는 해당 회사의 공고 수와 일치해야 합니다.
- 변경분의 새 공고 본문을 검증한 뒤 기존 공고와 합친 결과의 참조·집계를 확인합니다. 변경분에는 일부 회사의 공고만 들어 있으므로 전체 게시판 집계를 변경분의 길이와 비교하지 않습니다. 정상 빈 교체와 보존 기간이 지난 회사의 제거도 반영합니다.
- 이전 응답의 선택적 필드, 아직 해석하지 않는 추가 필드, 내용 없이 개수만 남은 과거 누락분과 `unmappedCount: null`은 유지합니다. 검증에서 값을 보정하거나 기본값을 채우지 않으며, 검증 뒤 기존 공고 변환을 적용합니다. 최초 상태의 회사·도시 목록은 변경분으로 덮어쓰지 않습니다.

잘못된 응답이나 변경분은 전체를 반영하지 않습니다. **마지막 정상 결과와 원래 조회 시각을 유지**하고 조회 오류와 재조회 버튼을 보여줍니다. 아직 정상 결과를 받지 못했다면 추천을 표시하지 않고 같은 화면에서 다시 조회할 수 있습니다. 자동 진행 확인을 종료하며 프로필·검색 조건·저장 기록·메모·지원 상태는 보존합니다. 정상 결과도 기존 30분·24시간 표시·만료 규칙을 따릅니다.

## 브라우저 동작과 운영 범위

- 서버가 제공한 임의의 URL을 따라가지 않고 같은 서버의 고정 진행 경로를 사용합니다. 수집 ID·진행 번호 외에 프로필·검색 조건·저장 공고 ID·메모를 보내지 않습니다.
- 회사·게시판·공고 출처, 교체 회사 목록, 진행 번호와 완료 수를 확인한 뒤 변경분을 적용합니다. 다른 수집이나 잘못된 회사의 결과를 현재 목록에 섞지 않습니다.
- 샘플 전환·화면 종료는 진행 타이머와 요청을 취소합니다. 이미 응답 중이던 이전 요청도 화면을 덮어쓰지 않습니다. 서버의 수집은 다른 탭과 공유하므로 계속 진행될 수 있습니다.
- 연결 실패 시 먼저 받은 결과는 남기고 자동 재시도를 멈춥니다. 사용자가 다시 조회하면 사용 가능한 캐시와 현재 진행 정보부터 받습니다. 보존 기간을 넘긴 공고는 추천에서 제외합니다.
- 최초 요청은 150초, 진행 요청은 건당 30초, 하나의 진행 연결은 최대 10분을 기다립니다. 오래 멈춘 연결은 종료하고 재연결을 안내합니다.
- 현재는 한 프로세스에서 수집과 진행 정보를 공유합니다. 최근 수집 하나와 회사별 완료 번호만 보유하며, 전체 카탈로그의 변경 이력을 반복 저장하지 않습니다.
- 진행 확인은 최소 1초 간격의 HTTP 요청입니다. 많은 동시 사용자나 여러 서버로 운영할 때는 공유 수집 저장소, 프로세스 간 요청 제한, 진행 전달 방식의 별도 검토가 필요합니다.

`/api/posting-status`는 기존의 전체 목록 응답을 유지합니다. 이 변경은 탐색용 카탈로그에 먼저 적용했습니다.
